# cys 터미널 v0.14.24

## 부트가 **자기 워커를 못 띄우던** 문제와, 마스터 창에 **Enter 가 가끔 안 먹던** 문제를 고쳤습니다

v0.14.23 이 "부서를 만드는 순간" 걸리던 일곱 가지를 고친 판이었다면, 이번 판은 그 직후 드러난
두 가지 — **부트 스크립트가 자기 워커 좌석에 지침을 넣다가 거부당하던 결함**(v0.14.23 발행 직후
관측)과, **다른 노드의 보고가 마스터 프롬프트에 타이핑은 되는데 제출(Enter)이 가끔 안 되던 결함**을
고쳤습니다. 둘 다 "신원 판정이 사람·시스템·자동응답을 한 등급으로 뭉뚱그려서" 생긴 종류입니다.

> **확정과 미확정을 먼저 밝힙니다.** 아래 수리는 코드와 자동 테스트로 검증했습니다. Windows
> 실기 확인 범위는 맨 아래 **[확정과 미확정]** 절에 그대로 적었습니다.

## 1. 부트가 **자기 워커 좌석에 지침을 넣다가 거부당하던** 문제 (결함 8)

부서 부트 로그에 이렇게 찍혔습니다.

```
[launch-agent] surface:3 created (role=worker)
error: acl_denied: acl denied: external → worker (pack/acl.json)
[launch-agent] failed surface surface:3 closed
boot 완료: 신규 기동 3 · 실패 1 (의무 실패 1)
```

CSO 와 리뷰어 둘은 정상 기동했는데 워커만 실패했습니다. 부서 ACL 에는 "바깥(external)에서
워커 좌석에 직접 입력하지 못한다"는 규칙이 있고(부서장을 건너뛴 조종을 막는 **의도된** 규칙), 그
규칙이 워커에게만 걸려 있기 때문입니다.

**원인**: 부트 스크립트는 그룹 종료에 살아남으려고 세션을 분리한 채(`setsid`) 백그라운드로
돕니다. 훅 셸이 끝나는 순간 그 프로세스는 어느 pane 의 자손도 아니게 되고, 데몬의 발신자 판정
(커널이 알려준 pid 에서 조상을 거슬러 pane 을 찾는 방식)은 그것을 **external** 로 분류합니다.
v0.14.23 이 만든 **오너 등급**은 GUI 만 받는 표식 기반이라 명령줄 `cys launch-agent` 를 구해
주지 못했습니다. 결국 `surface.create` 로 좌석을 만든 바로 그 프로세스가, 그 좌석에 첫 기동
명령을 넣는 단계에서 거부당하고 좌석을 도로 닫았습니다.

**고친 방식** — **"자기가 방금 만든 좌석에 자기 지침을 넣는 것"을 정당한 발신으로 인정합니다.**
- 데몬은 `surface.create` 를 호출한 프로세스의 (pid, 프로세스 시작 시각) 을 좌석별로 기억합니다.
- 같은 프로세스가 **그 좌석**에 입력을 넣으면 새 신원 등급 **`creator`** 로 평가합니다. 의미론은
  오너 등급과 같습니다 — 규칙 표에서 `from` 이 문자열 `"creator"` 인 규칙만 적용하고, 매칭이 없으면
  허용이 기본이며, 막고 싶으면 `{"from":"creator", ..., "allow": false}` 를 **명시**해야 합니다.
- 경계는 좁습니다: 같은 프로세스 · 같은 좌석 · 그 프로세스가 살아 있고 시작 시각까지 일치할 때
  (pid 재사용 방어) · 기록 후 30분 안 · 어느 pane 에도 귀속되지 않은 발신자일 때만입니다. 다른
  좌석에 보내면 종전대로 external 로 평가됩니다.
- `creator` 도 `owner` 처럼 **예약어**라 pane 이 자칭할 수 없습니다.
- 판정을 뒤집은 승격은 `acl.creator_granted` 이벤트로 **감사**됩니다.

> **이 등급의 성격을 정직하게 밝힙니다.** 오너 등급과 같은 **거버넌스 구분**입니다. 같은 사용자
> 계정의 프로세스가 `surface.create` 를 직접 불러 창작자가 되는 것까지 막지는 않습니다. 이 등급이
> 실제로 고치는 것은 "지침을 따르는 정상 부트 스크립트가 자기 좌석에 지침을 넣는 경로"이며,
> 막을 수 없는 것은 보이게 한다는 원칙으로 감사 이벤트를 남깁니다.

## 2. 마스터 창에 **Enter 가 가끔 안 먹던** 문제 (결함 3)

다른 노드가 마스터에게 보고를 올리면 프롬프트 창에 글은 들어오는데, 자동으로 눌러져야 할
Enter 가 가끔 눌리지 않아 마스터의 컨텍스트에 들어가지 못했습니다.

**원인 — 세 겹이 겹쳤습니다.**

① **사람이 아닌 입력이 '사람 타이핑'으로 계산됐습니다.** Claude Code 는 켜질 때 터미널에
"포커스가 바뀌면 알려 달라"(`?1004h`)고 요청하고, 커서 위치·터미널 종류 같은 것도 묻습니다.
화면 쪽 터미널(xterm.js)은 그 요청대로 **자동 응답**을 보냅니다 — pane 을 클릭하거나 벗어날
때마다 `ESC[I`/`ESC[O`, 질의에는 `ESC[?r;cR` 같은 짧은 응답이 나갑니다. GUI 는 이 자동 응답을
사람이 친 키와 구별하지 않고 데몬에 넘겼고, 데몬은 그때마다 "사람이 방금 타이핑했다"고 기록해
**3초 동안** 프로그램 주입을 막았습니다(타이핑 가드 — 사람의 미완성 입력을 보호하는 의도된
장치). 즉 오너가 마스터 창을 **클릭해서 보고를 읽는 순간부터 3초간** 노드의 Return 이 거부됐습니다.

② **거부된 Return 을 다시 보내는 길이 없었습니다.** `cys send` / `cys send-key` 는 거부를 그대로
오류로 돌려주고 끝났습니다(같은 저장소의 다른 주입 경로는 이미 "사람 입력이 멈추면 큐가 배달"
하는 1회 전환을 갖고 있었는데, 노드 보고가 쓰는 이 두 명령만 없었습니다).

③ **본문과 Enter 의 간격이 보장되지 않았습니다.** 본문은 원시 바이트로, Enter 는 별도 요청으로
수십 ms 뒤에 들어갑니다. Claude Code 의 입력 처리기는 긴 본문을 붙여넣기로 취급하고, 붙여넣기를
처리하는 도중 도착한 Enter 를 보류했다가 특정 경로(본문에 이미지 경로가 섞인 경우)에서는
**버립니다**. 저장소 자체 E2E 실측("raw `\r` 동봉은 Claude CLI 가 paste 로 삼켜 미제출")과
Anthropic 자체 주입 코드(붙여넣기 종료 뒤 `\r` 을 지연 전송)가 같은 사실을 가리킵니다.

**고친 방식**
- ① **터미널 자동 응답은 사람 입력이 아닙니다.** 데몬 한 곳(`is_pure_terminal_autoreply`)에서
  포커스 보고·커서 위치 응답·장치 속성 응답·버전 응답·색 질의 응답을 식별해, 수신 내용 **전체가**
  그런 응답의 연접일 때만 타이핑 기록을 건너뜁니다. 사람 글자가 한 글자라도 섞이면 종전대로
  기록합니다(판단이 애매하면 **사람 쪽**으로 — 가드가 한 번 더 걸리는 것이 보고가 사람 입력을
  덮는 것보다 낫습니다).
- ② **Return 은 잃어버리지 않습니다.** `cys send-key Return` 과 `cys send` 가 타이핑 가드에
  막히면 **큐로 1회 전환**합니다(대상이 조용해질 때 배달). 데몬이 일시정지(kill-switch) 상태면
  "큐는 resume 후 배달"이라고 한 줄 알립니다 — 기다림은 보이게.
- ③ **본문 직후의 Enter 는 최소 간격을 둡니다.** 프로그램 본문이 **실제로 PTY 에 쓰인 시각**을
  그 창의 쓰기 스레드가 기억하고, 프로그램 Return 은 그 시각으로부터 150ms(`CYS_CR_MIN_GAP_MS`,
  0 이면 끔)가 지나야 씁니다 — 요청이 들어온 시각이 아니라 **쓴 시각** 기준이라, 쓰기 스레드에
  앞선 요청이 밀려 있어도(적체) 간격이 무너지지 않습니다(이종 리뷰가 찾아낸 경계 — 아래 검증 절).
  같은 창의 쓰기 순서는 그대로 보존됩니다(창마다 단일 쓰기 스레드). 사람이 친 Enter 는 이 지연을
  받지 않습니다.

## [어떻게 검증했는가]

- 구현이 끝난 뒤 **이종 검토자 둘**(Gemini 계열·Codex 계열)에게 "승인하지 말고 깨뜨려라"는 임무로
  같은 평가 기준 6항목을 주었습니다. 한 검토자는 통과시켰고, 다른 검토자는 **통과시키지 않았습니다**
  — ③의 최소 간격이 "요청이 들어온 시각" 기준이라 쓰기 스레드가 밀려 있으면 실제 간격이 0 에
  가까워질 수 있다는 경계를 찾아냈습니다. 그 지적대로 기준을 "실제로 쓴 시각"으로 옮기고, 적체를
  일부러 만든 뒤 간격을 재는 회귀 검사를 붙였습니다(옛 구현에서는 그 검사가 실패함을 먼저 확인).

- 결함 8 의 재현 로그(부트 로그 4줄)와 발신자 판정 코드를 대조해 원인을 확정했고, 부서 ACL 을
  깐 격리 데몬에서 **실제 프로세스 pid** 로 좌석을 만들고 입력하는 테스트를 붙였습니다 — 자기
  좌석은 통과, 남의 좌석은 종전대로 거부, 시작 시각 불일치·관측 실패는 거부(fail-closed).
- 결함 3 은 Claude Code 2.1.239 바이너리의 입력 처리기(상수 `NORMAL_TIMEOUT=50`·
  `PASTE_TIMEOUT=2000`·붙여넣기 판정 800자·`?1004h` 포커스 보고 요청)와 xterm.js 의 포커스 보고
  발화 코드(`ESC[I`/`ESC[O`)를 직접 읽어 인과를 확정했습니다. Windows 실기(Parallels) 의 워커
  pane 에도 "send-key Return 은 typing_guard 에 막혀 --queued 로 큐잉" 기록이 남아 있었습니다.

## [확정과 미확정]

- **확정**: 두 수리 전부 코드로 들어갔고 자동 테스트가 붙었습니다. 자동 검사(병합 레인 13887ea):
  데몬 669 · CLI 141 · 라이브러리 286 — 전부 통과, 신규 테스트 22종(결함 8: 7 · 결함 3: 15),
  clippy 경고 집합 이전 판과 동일(신규 0), 빌드 무오류. 시간 단정이 들어간 쓰기 스레드 검사는
  3회 연속 실행으로 흔들림 없음을 확인했습니다.
- **미확정**: Windows 실기 확인은 이 판에서도 CI 게이트에 의존합니다. 실제 데몬을 띄운 E2E(부트 →
  워커 기동 → 보고 → Enter)는 코드 검사와 결정론 테스트로 대체했습니다. 150ms 라는 간격 값은 Claude
  Code 입력 처리기 분석과 저장소의 앞선 실측에서 유도한 값이지 이번 판이 실기에서 새로 잰 수치가
  아닙니다(`CYS_CR_MIN_GAP_MS` 로 조정 가능).
- **알려진 기존 문제(이번 판 범위 밖)**: 데몬 테스트 하나(`corrupt_topology_isolated_not_silently_empty`)가
  격리된 임시 폴더가 아니라 실제 홈의 세대 스냅샷을 읽어, 기계 상태에 따라 통과·실패가 갈립니다.
  이번 변경과 무관하며 다음 판 과제로 남깁니다.
- **수리하지 않은 것**: 같은 날 들어온 Windows 사용자 제보(pane 크기 조절·마스터 외 창 입력 불가)는
  오너가 자기 Windows 기계에서 실측해 **재현되지 않음**을 확인했습니다 — 그 사용자 기계 환경의
  문제로 판정하고 이 판에서는 코드를 바꾸지 않았습니다.
- **되돌리기**: `creator` 등급은 추가 허용만 만들고 새 거부를 만들지 않습니다. 자동 응답 면제는
  "사람 글자가 섞이면 종전 동작"입니다. Return 지연은 환경변수 0 으로 끌 수 있습니다. CLI 큐
  전환은 거부되던 경우에만 발동합니다.
