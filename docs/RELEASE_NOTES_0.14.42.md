## 1. 팀 만들기 확인 창이 눌리지 않던 것

**증상**: Control Center 의 승인 Feed 카드에서 [확인 창 열기]를 누르면 창은 보이는데 [만들기]를 눌러도
아무 일이 없었습니다.

**원인**: 확인 창과 토스트의 겹침 순서(z-index)가 Control Center 패널보다 낮아, 보이는 것은 확인 창인데 클릭은
그 위의 투명한 패널이 받았습니다. 키 큰 창 위에 뜬 토스트도 같은 방식으로 클릭을 가로챘습니다.

**해법**: 겹침 순서를 한 표(층서 토큰)로 모으고 "확인 창·토스트는 패널보다 위" 관계를 검체로 못박았습니다.
실제 Chrome 렌더에서 수정 전에는 [만들기] 클릭이 패널에 먹히고, 수정 후에는 버튼에 닿는 것을 확인했습니다.
팀 카드에는 대화 경로 안내문이 조건부로 붙습니다(대화 승인이 가능한 자리에서만).

## 2. 대화로 팀 만들기 승인 (macOS·Linux)

대표(본부 master·CEO)가 제안을 올린 뒤 "이 내용으로 만들까요? **만들어**라고 말씀해 주시면 바로 만들겠습니다."라고
여쭈면, 그 창에 **직접** "만들어"(또는 "네"·"응"·"그래 만들어"·"승인" 같은 짧은 긍정)라고 치시면 됩니다.
그 한 번의 답에만 **한 번 쓰면 사라지는 생성 허가(1회용 토큰)** 가 나오고, 대표가 그것으로 팀을 만든 뒤
팀원 자리까지 이어서 띄웁니다. 화면 카드의 [확인 창 열기] → [만들기] 경로는 그대로 남아 있습니다.

**안전장치**
- 대표가 질문을 연 뒤 **5분 안의 첫 답** 하나만 봅니다. 부정·질문·조건이 섞인 답("예를 들면…?"·"만들지 마"·
  "나중에 만들어")이나 긴 문장은 승인으로 읽지 않습니다.
- 다른 에이전트가 보낸 문장(기계 배달)은 배달 기록과 대조해 걸러 내므로 승인이 되지 않습니다.
- 토큰은 **그 제안·그 창·그 본문**에만, **2분 안에 한 번** 유효합니다. 발급자는 훅(UserPromptSubmit)뿐이고,
  검증·소비는 데몬이 합니다. 토큰 없이 부서 생성 동사를 부르면 단일소유 가드가 종전처럼 거부합니다(`exit 7`).
- 승인 카드 정리(`cys feed reply … allow --team-token …`)는 **생성 성공 기록 뒤 30분 안**에만 됩니다.
- 적대 검토에서 찾은 위조 통로 4개(공개 발급 API 가 호출자 증거를 믿던 것 등)를 막았습니다.

**팀을 만든 뒤**: 종전에는 "부서장 전원 각성 → 첫 과제 → 보고"가 대표의 기억에 달려 있어 빠질 수 있었습니다.
이제 편성 도구가 결판(완결·일부·보류·실패)을 **이벤트로 1회씩** 알리고, 부서장에게 각성 지시를 한 번 보냅니다
(부서장 좌석에 에이전트가 관측됐을 때만 · 빈 자리는 깨우지도 기동하지도 않습니다). 대표는 그 턴에서
기다리지 않습니다 — 편성·각성은 비동기이고, 대표가 턴을 붙들면 회신이 큐에 적체되기 때문입니다.

**이 경로가 동작하지 않는 곳**(화면 경로로 안내합니다)
- **Windows**: 아직 대화 승인이 없습니다(`platform_gui_only`). 화면 카드로 만들어 주세요.
- 대표 지침을 병합하지 않은 기계(`directive_stale` — 맨 위 「먼저 하실 것」).
- 제안을 올린 자리가 바뀐 경우(`surface_not_publisher`).

## 3. 사이드바 사용량 — 모든 계정 · Antigravity · cys 창 밖 세션

**무엇이 빠졌었나**(원인 6가지를 실측으로 확인): 기본 `~/.claude` 프로필은 "어느 계정인지" 적힌 파일이 폴더
밖 `~/.claude.json` 에 있어 신원을 못 읽었고 · agy 는 실제 데이터 폴더(`~/.gemini/antigravity-cli`)가 아니라
예전 경로만 봤고 · 값이 아직 없는 계정은 화면에서 개수로만 접혔고 · 요금제 값이 비어 있는(plan null) 계정 처리가 빠졌고 · 부서 데몬
조회가 직렬이라 느렸고 · agy 포트 조회(`lsof`)가 조건을 잘못 묶었습니다.

**이제**
- 이 컴퓨터에서 찾은 계정이 **값이 없어도 한 줄씩** 나옵니다. 값이 없으면 `관측 전 · (이유)`, 읽는 길이
  고장났으면 `관측 실패 · (이유)` 로 구별합니다(0% 로 적지 않습니다).
- **Antigravity(agy)**: agy 1.2 부터 내부 서버가 쿼터 조회에 보안 토큰(CSRF)을 요구합니다. cys 는 그 토큰을
  읽지 않습니다(agy 로컬 기능 전체를 여는 열쇠이기 때문입니다). 대신 **agy 공식 상태줄 기능**으로 값을
  받습니다. macOS·Linux 에서는 설치·업데이트 때 `~/.gemini/antigravity-cli/settings.json` 의 `statusLine` 이
  **비어 있거나 없을 때만** cys 가 연결을 넣습니다(표지 `--cys-autolink` · 직접 넣은 설정은 덮지 않습니다).
  이미 떠 있는 agy 는 다시 켜야 적용될 수 있습니다.
- **cys 창 밖(외부 터미널) Claude 세션**: 상태줄이 cys 로 연결된 프로필이면 그 계정 줄에 값이 모입니다
  (`usage.report_account`). 데몬을 새로 띄우지 않고 0.4초 안에 닿지 않으면 그 한 번은 버립니다.
  **창 밖 값은 표시용입니다** — 계정 한도 경보(80%·95%)의 근거로 쓰지 않습니다. 이 구분은 오판 방지 장치이지
  보안 경계가 아닙니다(USER-MANUAL §4 「집계 범위」에 한계를 적었습니다).
- 좌석 상태줄 보고가 데몬이 멈춘 동안 **최대 40초 기다리며 데몬을 새로 띄우려던** 것을 없앴습니다 — 이제
  데몬을 띄우지 않고 1초(Windows 2초) 안에 포기합니다(실측 40.01s → 1.01s). 데몬이 멈춘 동안 상태줄마다
  cys 프로세스가 쌓이던 경로가 닫혔습니다.

**무엇을 바꿨나(요지)**

  지 80ms 가 안 됐으면 본문을 받지 않고**(`submit_settling` · 쓰기 0), 그 거부에 "곧 빈다" 증명을 붙입니다. 새
  `cys send` 는 증명이 있을 때만 큐로 가지 않고 잠깐(기본 최대 3초) 기다렸다가 직접 넣습니다. 사람 초안·질문
  창·타이핑 가드에는 기다리지 않고 종전처럼 곧바로 큐로 갑니다.
- **짝 Return 흡수(A2·B)**: 기본 `send` 가 타이핑 가드·초안 게이트에 막히면 CLI 가 본문을 큐로 1회 돌리고,
  큐 배달이 CR 까지 제출합니다. 뒤따르는 관례적 `send-key Return` 은 빈 줄·초안·질문 창에 떨어지면 오승인이
  되므로, 데몬이 **같은 발신자의 첫 Return 1회**를 흡수합니다(다른 소켓의 CEO 발신자 포함). 승인 창이 떠 있는
  좌석에서는 반사 창(기본 2초) 안의 짝 Return 만 흡수합니다 — 대표의 승인 Return 을 삼키면 워커가 멈추기
  때문입니다. 첫기동 관문(폴더 신뢰·면책 등)은 이 좁힘의 예외입니다(관문 기본 선택지가 `No, exit` 라서).
- **데몬이 스스로 넣는 글의 화면 판정(H)**: 하트비트·wakeup·채널(오너 원격 지시)·CEO 자동결재·부트 감독자
  통보·좌석 승계 고지가 쓰기 직전에 질문 창·초안·사람 입력(30초)·사이클 창·kill-switch 를 봅니다. 막히면
  경로별로 큐로 돌리거나(스케줄) · inbox 에 두고 15초마다 재시도하거나(채널) · 사람에게 넘기거나(CEO 결재) ·
  그 pane 한 줄만 생략합니다. 기계가 남긴 초안(Return 이 빠진 기계 본문)은 막는 근거로 보지 않아
  하트비트·wakeup 이 멈추지 않습니다.
- **사이클 창 동안 큐 보류(H1)**: `/clear`~RESUME 사이에는 `--queued` 항목을 배달하지 않습니다(상한 600초).
  사이클을 세운 `cys cycle-agent` 가 해제 없이 죽으면 데몬이 곧바로 풉니다(주기 신호 정지 방지).
- **채널 재배달 기본 0(H3)**: 채널 메시지 1건은 주입 1회입니다. 종전에는 ack 가 없으면 10분마다 끝없이 다시
  넣었습니다(계약 변경 — §5·§9).
- **채널 메시지 사이 1초 간격의 빈틈(H3 · 발행 직전 수정)**: 쌓였던 원격 메시지는 한 건씩, 앞 메시지의 Enter 가
  들어가고 1초 뒤 새로 판정해 내보냅니다. 그런데 이 1초를 "좌석 writer 가 앞 메시지를 **쓰기 시작한 뒤**"부터 재서,
  앞 메시지가 writer 대기열에만 있는 순간(워커 push 의 Return 이 최소 간격을 기다리는 중 · 부하 중 스레드 깨움 지연)에
  다음 판정이 돌면 두 메시지가 간격 없이 이어 들어갔습니다 — 뒤 메시지의 판정은 앞 메시지를 쓰기도 전의 화면을 본
  것이라 앞 메시지가 띄운 질문 창에 뒤 메시지의 Enter 가 떨어질 수 있었습니다. 이제 채널은 넘긴 시각을 남겨 writer 가
  그 메시지를 끝낼 때까지 다음 메시지를 판정하지 않습니다. 데몬 내부 주입의 초안 판정(H0)은 바꾸지 않았습니다.
- **긴 본문·CRLF(C · macOS·Linux)**: 본문 안의 붙여넣기 봉투 종료 문자열(`ESC[201~`)을 살균하고, 직접 `send`
  의 1000바이트 초과 평문을 괄호붙여넣기 봉투로 보내며, CRLF 본문이 여러 번 나뉘어 제출되던 것을 한 번으로
  고쳤습니다.
- **데몬 비용(D·E·F·FATAL-1·R3)**: 호출자 신원 판독을 전체 프로세스 표 순회에서 조상 깊이만큼으로 · fd soft
  한도를 기동 때 `min(8192, hard, maxfilesperproc)` 로(내리지 않음) · accept 오류를 분류해 표본 로그 ·
  동시 조회 폭주에서의 비정상 종료(SIGABRT)를 조회 입장 상한 128 로 차단 · 좌석 셸 cwd 를 pid 단위로 판독 ·
  임베드 팩 해시를 프로세스당 1회로 · 응답을 읽지 않는 연결을 무진행 쓰기 30초로 회수.
- **훅 지연(R3-4)**: 프롬프트 훅의 100ms 계단 대기 제거 · 능력 프로브 캐시 · 입력 GC 게이트 · 도구 훅
  빠른 길(오버레이가 없으면 stdin 을 cys 로 직행).
- **재개·복원(R3-1·R3-2)**: `/clear` 뒤 재기동하면 옛 대화가 아니라 **새 대화로** 재개합니다(좌석 최상위
  claude 의 SessionStart 훅이 알린 경우만 · 새 세션 증거 필수). phoenix 복원 상한을 고정 90초에서 기동 단위
  수에 비례하도록(무출력이 상한을 넘을 때만 끊음) 바꿔 느린 재개의 역할 유실을 없앴습니다.

## 5. 부트 체인·치명위험 게이트에서 더 닫은 것

통합 트리에 게이트 재검토를 돌려 잡은 것들입니다(요지).
- **clear 직후 바닥 가드**: 200K 창 대표(master·CEO)가 clear 뒤 지침을 다시 붙여 넣으면 바닥이 이미 70%대라,
  유휴여도 경보 쿨다운마다 clear·재주입을 되풀이하던 고리를 닫았습니다 — clear 뒤 정착 창에서 바닥을 재고,
  바닥 위로 실제로 자란 뒤에만 다시 통보하며(히스테리시스), 여유가 없는 좌석은 1회만 다시 clear 해 보고 그래도
  같으면 자동 clear 를 멈춥니다(Claude Code 자체 압축이 받습니다 · 오너 feed 경보).
- master·CEO 의 clear 신호가 경보 라우터 예약분 때문에 시간당 5번째부터 최대 약 1시간 보류되던 것.
- 대표의 `cycle-agent` 는 백그라운드로 — 전경 대기로 대표 턴이 한 사이클(최대 약 8.5분) 멈춰 회신 큐가
  적체되던 것. CSO 는 대표의 사이클이 도는 동안(`quiescing` 좌석) 대표를 clear 하지 않습니다.
- clear 뒤 좌석이 지침 전문 없이 앉던 경로(훅 출력 1만 자 상한) · 같은 지침을 부트·사이클마다 한 번 더 읽던
  이중 적재.

- 팩 하한(`PACK_MIN_BINARY`): **0.14.41 → 0.14.42**(release.yml · pack-release.yml · docs/RELEASE.md 세 곳 동시
  상향). 근거: 위 새 CLI 넷이 v0.14.41 에 없다 — 릴리스 0.14.41 바이너리 사본에 `--help` 만 써서(상태 변경 0)
  넷 다 rc 2(`unrecognized subcommand` / `unexpected argument`)를 확인했습니다.

## 9. 알려진 한계 — 정직하게

**1) 여러 발신자 동시 제출(S21) — 통합 측정의 악화는 고쳤습니다(§4-1 · 13.9% → 91.6%).** 남은 한계: 줄이 비지
않으면 `cys send` 가 최대 3초 기다린 뒤 종전처럼 큐로 가고(큐 상한 100 · 약 10초 간격은 그대로), 그렇게 큐로 간
본문은 뒤에 직접 들어간 같은 발신자의 본문보다 늦게 도착할 수 있습니다(발신자 8 경쟁에서 run 당 순서 역전 29 ·
`queue.order_inverted` 로 보임). 경쟁이 심하면 대기 중 거부가 여러 번 나므로 배달 원장(`delivery-*.jsonl`)에 실제
쓰기보다 많은 `send` 행이 남습니다(원장 선기록 뒤 게이트 안 재확인에서 거부된 행 — 기존 한계의 빈도가 늘었다 ·
원장 8MB 회전은 그대로). 큐 배달(봉투 본문)이 직접 CR 바로 뒤에 붙는 경우는 이 수정의 범위 밖입니다(S21 에서 1건).
herdr·cmux-tui 의 직렬 원자 전달과는 여전히 구조가 다릅니다.

**2) 같은 발신자의 연속 `send`+`send-key Return` 쌍이 실제 Claude 에서 합쳐지던 기존 결함**(v0.14.41 부터 · CLI 는 OK)은
macOS·Linux 에서 고쳤습니다(§4-1 · 실측 20/20 별개 제출 ×2). **Windows 는 제출 정착이 켜지지 않아 종전 그대로입니다**
(ConPTY 실측 전).

**3) 데몬이 강제 종료되면 모든 pane 이 함께 죽습니다**(세션 연속성 0/25 · cmux-tui 25/25). PTY 호스트 분리는
로드맵 항목입니다. 발신자 6×10 배출은 제출 정착 뒤 49.8초(1 run)로 줄었지만 herdr(18초)·cmux-tui(2초)와는 아직 차이가 있습니다.

**4) 늦게 따로 보내는 짝 Return 은 승인 창을 누릅니다.** 승인 창이 떠 있는 좌석에서 흡수는 반사 창(2초) 안의
짝 Return 에만 적용됩니다(대표의 승인 Return 을 삼키지 않기 위한 절충). 모달 전환 경고가 나오면 Return 을
보내지 마세요.

**5) 보류가 길어진 대가**: 질문 창·초안이 있는 좌석에는 큐 항목·feed 가 늦게 나가거나 관찰 창 안에 나가지
않습니다(사고는 0 이 되었지만 전달이 늦습니다).

**6) Windows**
- 대화 승인으로 팀 만들기가 없습니다(화면 경로).
- 직접 경로 긴 본문 울타리·CRLF 한 번 제출 수리는 macOS·Linux 전용입니다 — Windows 직접 경로는 v0.14.41 과
  같은 바이트이고 CRLF 본문이 여러 번 나뉘어 제출되는 종전 결함이 그대로 있습니다(ConPTY 실측 전).
- 데몬 내부 주입 판정의 초안 축은 Windows 기본에서 꺼져 있습니다.
- agy 상태줄 자동 연결은 macOS·Linux 전용입니다.
- 이번 판의 Windows 분기는 교차 타입체크(오류 0)와 CI 레인으로 확인했고, **실기(NSIS 설치·Git Bash·named pipe)
  확인은 아직입니다**.

**7) 원인 미확인 신호 1건**: 단일 연결 ping 처리량이 주·보조 측정 모두에서 14~17% 낮았습니다(후보: 조회 입장
상한 · accept 오류 분류 · 연결당 시작 시각 판독 — 확인 안 함).

**8) 창 밖 사용량 값은 표시용이며, 좌석 보고의 경보 구분도 보안 경계가 아닙니다**(같은 사용자 계정의 프로그램은
믿는다는 전제 · USER-MANUAL §4).

**9) 오너 결재가 남은 문안**: 팀 만들기 대화 승인 지침 문안(MASTER §4-A-2 등) 확정 · CEO 합성 지침 크기
(제출 단위 상한 근접) · 채널 재배달 기본 0 계약 변경.

**10) 측정으로 확인하지 못한 것**: `/clear` 뒤 새 대화 재개(R3-1)는 벤치의 가짜 claude 가 새 훅 계약을 흉내 내지
않아 이 측정으로 효과를 잴 수 없었습니다. 실제 Claude Code 좌석·UI(WKWebView·WebView2) 실기 확인이 남았습니다.

**11) 병렬로 진행 중인 수정**: clear 직후 바닥 가드의 잔여 2건(복원 뒤 배달이 바닥에 섞여 여유 있는 대표가
"자동 clear 정지"로 오판될 수 있는 경로 · ②무clear 계열)을 별도 브랜치(`perf/0.14.42-clear-floor`)에서 고치는
중입니다. 발행 전에 병합되면 이 절과 §5 를 갱신합니다.

**12) 원격 채널 메시지가 거의 동시에 두 건 들어올 때의 간격 — 발행 전에 고쳤습니다(§4 · §10).** 채널 행 사이 1초
간격을 "앞 행을 좌석 writer 가 쓰기 시작한 뒤"부터 재서, 앞 행이 writer 대기열에만 있는 순간에 다음 배달 판정이 돌면 두
행이 간격 없이 이어 들어갔습니다(v0.14.41 에는 이 간격 장치 자체가 없었습니다). 발행 준비 중 검체
`h3_flush_rejudges_each_row_after_own_paste_settles` 의 간헐 실패(버전 범프 전 `fba29db0` 12회 중 3회)로 드러났고,
이제 채널이 넘긴 시각부터 간격을 잽니다. 남은 것: 앞 행을 10초 넘게 쓰지 못하는(에이전트가 입력을 읽지 않는) 좌석에서는
뒤 행을 더 넘기지 않고 15초마다 다시 시도합니다(`hold_reason: "writer_busy"` · 행은 inbox 에 그대로).

## 11. Windows

- 새 코드의 Windows 분기는 최소로 뒀습니다 — 대화 승인은 Windows 에서 질문을 열지 않고 화면 경로로 접히고,
  직접 경로 울타리·CRLF 수리와 agy 자동 연결은 Windows 에서 켜지지 않습니다(§9-6).

  수정 전과 같은 바이트입니다.
- 채널 메시지 간격 빈틈 수정(§4 · §9-12)은 **Windows 에도 똑같이 적용됩니다** — 좌석 writer 는 운영체제 공통 경로이고
  수정은 채널이 넘긴 시각 기록 하나뿐입니다(쓰는 바이트 무변경). 교차 타입체크 오류 0 으로 확인했고 실기 확인은 아직입니다.

  않습니다.

### Windows Defender / SmartScreen 안내 (유지)
