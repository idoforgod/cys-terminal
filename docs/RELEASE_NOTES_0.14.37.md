# v0.14.37 — 컴퓨터를 껐다 켜도 팀이 화면에서 사라지지 않습니다

이번 판을 한 문장으로 줄이면 이렇습니다 — **재부팅 후에 "데몬 안에는 살아 있는데 화면에만 없는"
워크스페이스가 더는 생기지 않습니다.**

부서를 하나라도 만든 뒤 컴퓨터를 껐다 켜면, 부서 팀은 화면에 그대로 돌아오는데 **본부(기본
워크스페이스)의 5팀만 사라졌습니다.** Control Center 의 「오피스」를 열면 CEO 를 포함한 5명이
멀쩡히 일하고 있는 것이 보이는데, 터미널 화면에는 그 탭 자체가 없었습니다. 앱을 다시 켜도
돌아오지 않았습니다. 이번 판이 그 결함을 고칩니다.

---

## 1. 무엇이 잘못돼 있었나

세 가지가 겹쳐야 일어나는 일이었고, 셋 다 제품에 있었습니다.

| # | 사실 | 확인처 |
|---|---|---|
| 1 | pane 번호는 데몬을 다시 켜도 **이어서** 발급됩니다(재사용 없음) | `src/bin/cysd/state.rs` `next_id` · `recall.rs` `max_surface_id` |
| 2 | 재부팅하면 launchd 가 GUI 보다 **먼저** 데몬을 띄우고, 데몬이 팀을 **새 번호로** 되살립니다 | `src/bin/cysd/main.rs` 콜드부트 auto-restore |
| 3 | 그래서 저장해 둔 본부 pane 번호는 전부 죽은 번호가 되고, 복원 필터가 **본부 탭만** 버렸습니다 | `ui/src/main.ts` 세션 복원 |

문제의 조항은 한 줄이었습니다.

```
return ws.socket != null && lb?.ok === true;   // 본부는 socket 이 없어 항상 false → 드롭
```

부서 워크스페이스에는 부서 데몬 소켓이 붙어 있어 이 조건을 통과했고, 본부 워크스페이스는
기본 데몬이라 소켓 값이 없어 **예외 없이 버려졌습니다.** 버린 직후 화면을 다시 그리면서 그
삭제가 디스크에 그대로 저장됐고, 3초마다 도는 자동 입양 루프는 남은 워크스페이스의 소켓만
순회하므로 **본부 데몬을 다시는 조회하지 않았습니다.** 앱을 껐다 켜도 돌아오지 않은 이유입니다.

**부서를 만들기 전에는 왜 멀쩡했나.** 본부 탭이 버려지면 워크스페이스가 0개가 되고, 그때는
복원 말미의 폴백이 새 탭을 만들어 거기에 팀이 입양됐습니다. 부서 탭이 하나라도 살아남으면
0개가 아니라서 그 폴백이 동작하지 않습니다. **부서를 만든 순간부터 예외 없이 재현**됩니다.
맥과 윈도우가 똑같이 겪은 것도 이 때문입니다(UI 코드는 두 플랫폼이 같습니다).

## 2. 무엇을 고쳤나

### ⓐ 본부와 부서를 같은 규칙으로 봅니다

판정을 순수 함수로 떼어내 `ui/src/wsreconcile.ts` 에 두고, **소켓 유무를 판정에 쓰지 않습니다.**
데몬이 살아 있으면 빈 워크스페이스라도 보존하고, 데몬이 일시적으로 대답하지 않으면 판정을
보류합니다(일시 미가동으로 탭을 영구 삭제하지 않는다는 기존 계약은 그대로입니다).

### ⓑ 저장본은 "배치 기억"이지 "존재 진실원"이 아닙니다

이번 판부터 **본부 워크스페이스와 레지스트리에 등재된 부서는 저장본에 없어도 탭을 만듭니다.**
이 한 곳이 세 가지를 한꺼번에 덮습니다.

- 본부 탭이 사라진 상태로 저장된 기존 설치본 — **앱을 한 번 켜면 자동으로 돌아옵니다.**
- 브라우저 저장소가 통째로 비었을 때(프로필 초기화·캐시 삭제)
- GUI 밖에서(CLI·에이전트가) 만든 부서 — 이제 다음 기동에 탭이 생깁니다

삭제 의도가 기록된 부서(묘비)는 **여전히 되살리지 않습니다.** 부서 삭제 계약은 그대로입니다.

### ⓒ 빈 탭을 빈 화면으로 두지 않습니다

입양할 노드가 없는 워크스페이스는 본부·부서 구분 없이 셸 하나로 채웁니다(신규 설치의 기본
모습과 같습니다). 한 탭의 셸 생성이 실패해도 나머지 탭의 복원은 계속됩니다.

### ⓓ 먹통 데몬 하나가 화면 전체를 볼모로 잡지 못합니다

복원 과정의 모든 데몬 호출에 시간 상한이 생겼습니다. 종전에는 상한이 없어서, 응답을 주지 않는
부서 데몬이 **하나**만 있어도 복원이 영원히 멈추고 **탭이 하나도 그려지지 않았습니다.** 상한은
넉넉히 잡았습니다(재부팅 직후 Windows Defender 검사 등으로 느려진 기계를 "죽었다"고 오판해
불필요한 재기동을 부르지 않기 위해서입니다). 상한을 넘긴 데몬의 탭은 삭제되지 않고 보존됩니다.

### ⓔ 3초 자동 입양이 한 데몬 때문에 멈추지 않습니다

종전에는 소켓 순회 전체가 하나의 예외 처리로 묶여 있어, 앞 순서의 데몬 하나가 대답하지 않으면
**그 뒤 순서의 모든 데몬이 매 틱 건너뛰어졌습니다.** 이제 소켓마다 격리됩니다.

### ⓕ 화면 밖 유령을 정리합니다

- 붙일 워크스페이스가 없으면 pane 런타임을 만들지 않습니다. 종전에는 화면 밖 런타임이 남아
  **같은 세션에서의 재입양을 영구히 막았습니다**(실측 34개).
- 데몬이 기록 자체를 모르는 pane(데몬 재기동으로 소멸)은 트리에서 치웁니다. 다만 **2회 연속
  같은 판정일 때만** 집행합니다 — 데몬이 한 틱만 이상한 목록을 돌려줘도 화면이 통째로 비는
  일을 막기 위해서입니다.
- **종료된(`[exited]`) pane 은 그대로 둡니다.** 마지막 출력을 읽으실 수 있어야 하기 때문입니다.

### ⓖ 되살아나면 안 되는 것은 되살리지 않습니다

"저장본에 없어도 등재된 부서는 탭을 만든다"는 새 규칙에는 **반대 방향의 위험**이 있습니다.
삭제 의도(묘비)를 읽지 못한 상태에서 탭을 만들면, 그 탭이 부서 데몬을 다시 띄우고 그 과정에서
묘비까지 지워져 **지운 부서가 영구히 되살아납니다.** 그래서 묘비를 **읽지 못하면 부서 탭을 아예
만들지 않습니다.** 늦게 뜨는 대가는 한 번 더 켜면 사라지지만, 지운 부서가 팀까지 데리고
돌아오는 것은 되돌릴 수 없기 때문입니다. 본부 탭은 삭제 개념이 없으므로 이 규칙과 무관하게
항상 보장됩니다.

같은 이유로 **그룹째 삭제**에도 삭제 의도를 먼저 기록합니다. 종전에는 탭 하나를 지울 때만
기록했고, 그룹 삭제 경로에는 그 기록이 없었습니다.

### ⓗ 응답 없는 데몬을 "죽었다"고 단정하지 않습니다

시간 상한을 넘긴 것은 "죽었다"가 아니라 **"모른다"** 입니다. 모를 때 데몬을 다시 띄우면 살아
있는 데몬 옆에 또 하나가 생기고 좌석을 두고 다툽니다. 그래서 무응답은 재기동 사유에서 뺐습니다.
같은 소켓에 요청이 쌓이지 않도록, 앞 요청이 끝나기 전에는 새 요청을 보내지 않습니다.
Windows 는 재부팅 직후가 느리므로 모든 상한을 두 배로 엽니다.

### ⓘ 기동이 실패해도 화면은 뜹니다

저장본이 손상되는 등으로 복원이 예외로 죽으면, 종전에는 탭이 하나도 그려지지 않고 3초 자동
복구마저 켜지지 않아 **그 상태로 앱이 잠겼습니다.** 이제는 부분 상태라도 그리고 자동 복구를
켭니다. 안내가 한 줄 뜨고, 살아 있는 노드는 몇 초 안에 스스로 붙습니다.

---

## 3. 이미 사라진 화면은 어떻게 되나

**따로 하실 일이 없습니다.** 이 판을 설치하고 앱을 켜면 본부 탭이 자동으로 만들어지고, 데몬
안에서 일하고 있던 팀이 그 탭으로 들어옵니다. 지금까지 쓰시던 수동 복구(워크스페이스를 새로
만들고 앱을 다시 켜기)는 더 필요하지 않습니다.

## 4. 검증

- 배포될 복원 코드를 **원문 그대로 추출**해 15개 시나리오로 재현했습니다. 본부 탭 소실이
  **현행 8/13 → 수정 후 0/13**, 화면 밖 유령 pane 이 **34개 → 0개** 입니다.
- 새로 생길 수 있는 위험을 따로 쳤습니다 — 닫은 탭이 3초마다 되살아나는 무한 재생성 없음,
  탭이 0개가 되면 복구됨, 단발 이상 응답으로 pane 이 사라지지 않음, 종료된 pane 은 보존됨,
  먹통 데몬이 있어도 복원이 끝남.
- 판정 함수에 회귀 테스트를 붙였습니다(`ui/src/wsreconcile.test.ts`). 이 결함이 오래
  살아남은 이유가 **그 판정을 고정하는 테스트가 하나도 없었기 때문**이라, 음성 대조까지 함께
  박았습니다.
- **배선**도 기계가 셉니다(`ui/src/wswiring.test.ts`). 판정이 옳아도 그 함수를 부르지 않거나
  상한 하나를 빠뜨리면 화면은 그대로 사라집니다. 실제로 이번 검토에서 나온 가장 심각한 결함이
  '복원 끝의 두 줄만 상한을 빠뜨린 것'이었고, 사람이 한 줄씩 세는 방식으로는 다시 빠집니다.
  그래서 옛 결함 한 줄의 부재·모듈 호출·상한 누락·무응답 처리 네 가지를 소스에서 직접 단언합니다.
- 세 차례 성찰(적대 검토)로 이 수정 자체를 다시 쳤고, 거기서 나온 **차단급 1건과 주요 항목
  다수를 이 판에 함께 반영**했습니다. UI 테스트는 772건에서 820건이 됐습니다.
