# v0.14.28 — Windows 업데이트가 잠긴 파일 앞에서 무너지던 판을 갈았습니다

지난 판까지 Windows 업데이트에는 구조적인 약점이 하나 남아 있었습니다.
**실행 중인 `cys.exe` 는 잠겨 있습니다.** 설치기는 그 잠긴 파일을 만나면 **조용히 건너뛰었고**,
건너뛴 채 마지막 검증에 걸리면 설치를 **중단**했습니다. 사용자에게는 "업데이트가 안 된다"로,
더 나쁜 날에는 **구버전이 그대로인데 성공한 얼굴**로 나타났습니다.

이번 판은 그 판정과 배치의 기계를 통째로 바꿨습니다. 사용자 입장에서 바뀌는 것 세 줄:

- **잠긴 CLI 때문에 업데이트가 실패하지 않습니다** — 새 파일을 옆자리에 먼저 받아 검증한 뒤 이름 교체로 갈아끼웁니다.
- **반쯤 끝난 설치가 성공으로 둔갑하지 않습니다** — 못 바꾼 파일은 이름·이유가 남고, 구버전은 무손상으로 남습니다.
- **데몬이 마지막 동작본 CLI 를 지우지 못합니다** — 청소가 삭제 전에 "정식이 실제로 있는가"를 먼저 확인합니다.

macOS 쪽에서도 앱 봉인(코드서명)이 스스로 깨지던 마지막 경로를 막았습니다(아래 5번).

---

## 1. 잠긴 파일을 만나도 업데이트가 됩니다 (핵심 — 잠금 무관 배치)

지금까지 설치기는 실행 중인 `cys.exe` 를 **그 자리에서 덮어쓰려** 했습니다. Windows 에서
실행 중인 파일은 덮어쓸 수 없으므로, 훅은 "크기와 수정시각이 같으면/다르면 면제"라는
**지문 비교 면제 기계**로 그 파일을 조용히 건너뛰었습니다. 이 면제가 바로
"구버전이 남았는데 성공"의 구멍이었습니다.

이번 판의 배치는 순서가 다릅니다. 파일마다:

1. 새 파일을 **옆자리**(`<이름>.new.exe`)에 먼저 받습니다 — 잠긴 파일을 건드리지 않습니다.
2. 받은 파일을 검증합니다(존재·크기·**파일에 새겨진 버전**).
3. 그 다음 **이름 교체(rename) 두 번**으로 갈아끼웁니다: 구버전 → 백업 자리, 새 파일 → 정식 자리.
   실행 중이라 잠긴 보통의 잠금(이미지 잠금)은 **rename 을 막지 못합니다.**
4. 어느 단계든 실패하면 **이 절차로 갈아끼운 파일은 전부 되돌립니다(undo).** 이미 갈아끼운
   앞 파일까지 역순으로 되돌립니다. 정직한 한계 하나: 잠겨 있지 않던 파일은 이 절차 **이전에**
   설치기 본체가 이미 새 판으로 덮었을 수 있어, 드문 실패 조합(예: 일부 백신이 `cys.exe` 만
   특수하게 붙잡은 경우)에서는 "옛 cys + 새 데몬"이 남을 수 있습니다. 이 경우도 **조용히
   지나가지 않습니다** — 아래 2번의 실패 기록·종료코드로 크게 알리고, 잠금을 풀고 설치기를
   다시 실행하면 그대로 치유됩니다(구판과 새 판이 잠시 섞여도 이번 판은 서로 호환됩니다).

"이번 빌드인가"의 판정도 바꿨습니다. 크기·수정시각 지문(추정) 대신 파일에 새겨진
**버전 정보(VERSIONINFO)를 절대 기준**으로 비교합니다. 읽을 수 없으면 통과가 아니라
"미확인"으로 처리합니다 — 측정 불능은 통과가 아닙니다.

## 2. 실패는 실패라고 말합니다 (침묵 면제 구멍 봉합)

이제 어떤 파일을 왜 못 바꿨는지가 세 곳에 **똑같이** 남습니다: 설치 폴더의
`cys-install-failure.txt` 파일, 설치 화면, 그리고 종료코드.

- 종료코드 4 = **구버전 무손상 + 새 판 미반영** (파일이 배타적으로 잠겨 있던 경우 등).
  이때의 올바른 행동은 딱 하나입니다: **제거(언인스톨)하지 말고**, 앱에서 cys 를 종료한 뒤
  10초 기다렸다가 설치기를 다시 실행하고 "제거하지 않음"을 선택하십시오.
- 실패한 설치는 성공 마커를 남기지 않습니다 — 버전 기록 파일은 **전 검증을 통과한 뒤에만** 갱신됩니다.

설치기가 세션을 죽이던 경로도 이번에 제거했습니다. 옛 훅에는 최후 수단으로 데몬을
강제 종료(taskkill)하는 폴백이 있었고, GUI 를 닫을 때 **자식 프로세스까지 트리로** 죽여
데몬과 전 세션이 함께 죽는 실측 결함이 있었습니다. 두 경로 모두 삭제했습니다 —
**업데이트가 여러분의 창(세션)을 죽이지 않습니다.**

## 3. 데몬이 마지막 동작본을 지우지 못합니다

데몬은 부팅할 때 지난 업데이트의 잔해(`*.prev*` 백업 등)를 청소합니다. 지금까지 이 청소는
**이름 규칙만 보고** 지웠습니다. 설치 중 전원이 나가는 등으로 "정식 파일은 없고 백업만 있는"
상태가 되면, 청소가 그 백업 — **유일한 동작본** — 을 지워 CLI 가 영구 소실됐습니다.

이제 청소는 삭제 전에 **정식 파일의 존재를 먼저 확인**합니다.

- 정식이 있으면: 종전대로 청소합니다(달라지는 것 없음).
- 정식이 없으면: **아무것도 지우지 않고 복구**합니다 — 새 파일(`.new`)이 있으면 그것을,
  없으면 가장 최신 백업을 정식으로 승격합니다. 복구 재료조차 없으면 아무것도 지우지 않고
  크게 기록을 남깁니다.

설치기가 실패한 채 끝나도, 다음 부팅에서 데몬이 이 복구선으로 이어받습니다 —
**파일이 조용히 사라지는 경로가 없어졌습니다.**

## 4. 설치를 방해하던 프로그램 자신의 버릇 두 가지를 껐습니다

**재스폰 스톰.** 데몬이 재시작되면 화면 관측 브리지가 이벤트를 이어받지 못하는 순간이
있는데(격차 신호 `replay_gap`), CLI 가 이를 치명 오류로 취급해 **종료**했고, 브리지는
죽은 CLI 를 **2초마다 영원히 새로 띄웠습니다.** 설치 중에는 이것이 `cys.exe` 를
**계속 다시 잠그는** 결정론적 원인이었고, 평시에도 CPU 를 낭비했습니다. 이제 CLI 는
종료하지 않고 "지금부터"로 이어받으며(과거 전량 재생 금지 — 이벤트 폭주 없음),
브리지는 지수 백오프(2초→4→8→…→최대 60초)로 물러섭니다.

**라이벌 데몬.** 데몬 소켓이 죽어 있으면 모든 `cys` 호출이 디스크의 `cysd.exe` 를 **그 순간의
바이트로** 자동 기동합니다. 설치 중이면 반쯤 추출된 바이너리로 엉뚱한 데몬이 뜹니다.
GUI 와 도구·관측용 호출에는 자동 기동을 봉인했습니다(`CYS_NO_AUTOSTART=1`).
**여러분이 직접 치는 `cys` 는 그대로입니다** — 첫 호출의 자동 부팅 경험은 바뀌지 않습니다.

## 5. macOS: 앱 봉인이 스스로 깨지던 마지막 경로를 막았습니다

이 맥에서 실제로 일어난 사고입니다. 점검 도구가 부서용 명령(`cys-dept`) 링크를
**앱 번들 안에** 만들었고, 그 순간 코드서명 봉인이 깨졌습니다. 봉인이 깨진 번들을
브라우저로 받아 설치하면 첫 실행에서 "손상되었기 때문에 열 수 없습니다"로 차단됩니다 —
공증이 멀쩡한데도 그렇습니다.

- 링크는 이제 **번들 밖**(`~/.local/bin`)에만 만듭니다. Windows 에서는 만들지 않습니다.
- 과거에 잘못 만들어진 번들 안 링크는 점검(fix 모드)이 **먼저 지우고 새 자리로 옮깁니다**(자가치유).
- 안내 문구도 정정했습니다. 종전에는 봉인이 깨지면 "재설치만이 해법"이라고 단정했지만,
  어긋남이 전부 **원래 설치에 없던 '추가된 파일'뿐이면 그 파일만 지워도 봉인이 복구**됩니다
  (재설치 불요). 수정·누락이 하나라도 있으면 종전대로 번들 통째 교체입니다.

## 6. 업그레이드하실 때 알아두실 것

- **설치가 실패해도 제거(언인스톨)하지 마십시오.** 구버전은 무손상으로 남아 있습니다.
  앱에서 cys 를 종료하고(세션을 저장합니다) 10초 뒤 설치기를 다시 실행해
  "제거하지 않음"을 선택하면 됩니다. 제거는 세션·데이터까지 걷어냅니다.
- 설치 폴더에 `<이름>.new.exe`·`<이름>.prev*.exe` 가 **잠깐 보였다 사라질 수 있습니다** — 새 배치
  방식의 정상 동작입니다. 손으로 지우실 필요 없습니다(데몬이 안전 조건에서만 청소합니다).
- 구버전과의 호환은 유지됩니다. 프로토콜 버전을 올리지 않았고 기존 원격 호출을 제거하지
  않았으므로, 업데이트 직후 "새 CLI + 옛 데몬"이 잠시 공존해도 통신이 끊기지 않습니다.

## 정직하게 — 이번에 **실기로 확인하지 못한** 것

아래는 코드·자동 검사·구조 논증으로 확인했고, **실제 Windows 기계에서 돌려 보지 못했습니다.**
"됩니다"라고 말하지 않겠습니다.

- **Windows 실물 설치·업그레이드를 직접 보지 못했습니다.** 이 작업 기계는 macOS 입니다.
  설치기 훅은 로컬 `makensis`(v3.12) 컴파일 통과 + 정적 단언(정식 이름이 비는 분기 0 ·
  강제종료 경로 부재 · 실패 토큰 스키마 일치)까지 확인했고, 데몬·CLI 수리는 단위 테스트
  (부팅 가드 8종 · 재스폰 3종 등)로 잠갔습니다. **최초의 실기 검증은 CI 의 Windows 설치
  레인**이며 — 특히 "구버전 `cys.exe` 를 잠근 채 업그레이드 → 성공 + 신버전" 시나리오가
  신설됐습니다 — 그 결과 없이는 발행하지 않습니다.
- **설치 중 재잠금이 실제로 사라지는지**(4번의 재스폰 스톰 소멸)는 모의 스트림·단위
  테스트로 대체했습니다. 실물 재현은 위 CI 레인과 실기 체크리스트의 몫입니다.
- 배타적 잠금(공유 불가 핸들)이 걸린 드문 경우는 이번 판에서도 업데이트가 되지 않습니다 —
  다만 이제 **조용히가 아니라 정직하게**(종료코드 4 + 구버전 무손상 + 재실행 안내) 실패합니다.

## Windows Defender / SmartScreen 안내 (유지)

Windows용 설치 파일은 Authenticode 서명이 없어(인증서 미보유) 실행 시 SmartScreen
"알 수 없는 게시자" 경고가 뜰 수 있습니다(**추가 정보 → 실행**으로 진행).
홈페이지의 `SHA256SUMS.txt` 와 대조해 무결성을 확인할 수 있습니다.
Defender 오탐은 WDSI 신고로 낮춰 갑니다(`docs/WDSI_SUBMISSION.md`).

### Defender가 `cys.exe` 를 격리한 경우 — 복구는 **순서**가 생명입니다

드물게 Defender의 행동 휴리스틱이 명령줄 실행 파일만 격리합니다.
GUI는 살아 있어 정상으로 보이지만 CLI가 사라져 팀이 서지 않습니다.

```powershell
# ① 제외 먼저 (복원 즉시 재격리 방지)
Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\cys"

# ② 그 다음 복원
& "$env:ProgramFiles\Windows Defender\MpCmdRun.exe" -Restore `
    -Name "Program:Win32/Contebrew.A!ml" -All
```

순서를 바꾸면 복원하자마자 다시 격리됩니다.
동봉 실행환경이 격리된 경우에도 시작할 때 빠진 파일과 복구 절차를 알려 줍니다.
그리고 이번 판부터는, Defender 가 CLI 를 격리해 정식 파일이 사라진 상태에서도
데몬의 부팅 복구선(3번)이 백업본을 정식으로 승격해 **CLI 영구 소실을 막습니다.**

## Windows 설치 전 — `claude` 는 따로 설치해야 합니다

프로그램은 대부분을 스스로 담고 있지만 `claude` 명령만은 예외입니다. PowerShell에서:

```powershell
irm https://claude.ai/install.ps1 | iex
```

git·node를 따로 깔 필요는 없습니다. 자세한 절차는 `docs/INSTALL-Windows-KR.md` 를 보시면 됩니다.

## macOS 설치

`.dmg` 를 열고 **"Install cys"** 를 더블클릭하면 설치가 원자적으로 끝납니다.
Apple 공증(notarization)을 마쳤으므로 "확인되지 않은 개발자" 차단 메시지는 나오지 않습니다.

- Apple Silicon: `cys_0.14.28_aarch64.dmg`
- Intel: `cys_0.14.28_x64.dmg`
