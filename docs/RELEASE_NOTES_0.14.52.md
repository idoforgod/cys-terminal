## 1. 들어간 것

### 1-1. F-01 — 탭 점은 CLI 가 실제로 일할 때만 깜박입니다(화면 표시 전용)
- **무엇이 바뀌었나**: 역할 점이 늘 깜박이지 않습니다. 관찰된 「일하는 중」만 깜박이고, 「기다림」은 채운 원, 권한·질문 입력 대기는 같은 역할 색의
  채운 마름모, 「알 수 없음」은 빈 원, 움직임 줄이기 설정에서의 「일하는 중」은 이중 고리입니다. 역할 색과 죽은 좌석 처리는 그대로입니다
  (`4a1e390d`, `741dc605`).
- **어떻게 아나**: 데몬에 관찰자 스레드 하나를 두고 좌석마다 1초에 한 번, 잠금을 기다리지 않는 방식(try-lock)으로 화면의 제한된 창(15행 × 256열)과
  창 제목을 복사합니다. 판정은 잠금을 놓은 뒤에 합니다(`6b53ed5c`, `ace01afb`, `ee36e06b`). 문법은 채집한 실제 화면에서만 만들었습니다 —
  Claude Code 2.1.301 · Codex CLI 0.162.1(`c318a4d0`). 바쁨 단어 검색(「esc to interrupt」 등)은 스트리밍 중에는 없고(codex 0 % · claude 13 %)
  초안에는 있어서(45–93 %) 쓰지 않았습니다(`c318a4d0`).
- **잠금 아래의 일을 줄임**: 관찰자가 파서 잠금 아래에서 하는 복사를 행 단위 한 번의 복사로 바꿨습니다. 경합 없는 미세 측정(release)에서
  24×80 p50 3.13 → 0.29 µs, 60×256 p50 8.92 → 1.21 µs 입니다(`aa7f8369`).
- **목록 전달**: `surface.list` 를 끝점마다 3초에 한 번 보내고, 응답의 `display_activity` 는 나이를 보수적으로 셉니다. 관찰 나이가 임대 + 목록
  주기 한 번(9초)을 넘으면 깜박임을 멈추고 낡음 표시로, 요청 시작부터 맥 31초 · 윈도우 47초가 넘으면 만료입니다(`4a1e390d`). 데몬 전선의
  키와 UI 해석기의 키가 같은지는 교차 고정 시험이 잡습니다(`16e0de58`).
- **알아 둘 한계** (U 레인 절에서 그대로 옮김):
  - **어떤 CLI 가 「일하는 중」을 보일 수 있나.** 지원: Claude Code 2.1.301 · Codex CLI 0.162.1(그 판에서 화면 문양을 채집). **Gemini / agy
    좌석은 이 판에서 지원하지 않는 계열이라 점이 깜박이지 않습니다**(늘 「알 수 없음」 표시). 그 CLI 를 따로 떼어 채집할 수 없었고, 살아 있는
    gemini 좌석을 세 시간 읽기 전용으로 기록했지만 리뷰 트래픽이 없었습니다. 다른 CLI 판에서는 「알 수 없음」이 더 자주 보일 수 있습니다.
    쉬는 좌석을 「일하는 중」으로 보이게 할 수는 없습니다 — 문법이 CLI 자신의 바쁨 제목을 열쇠로 삼기 때문입니다.
  - **화면이 멈추면 「일하는 중」이 끝나지만, 시계가 돌면 끝나지 않습니다.** 정지 상한(같은 표본 N = 120 개)은 관찰하는 화면 전체가 멈췄을 때만
    걸립니다. 실제로는 멈췄는데 경과 시간 카운터(예: "1m 23s")가 계속 도는 CLI 는 자기 바쁨 제목이 바뀔 때까지 「일하는 중」을 계속 갱신합니다 —
    시계가 도는 멈춤은 상한이 잡지 못합니다. 부서장 판정 D2(N = 120)는 이 한계를 알고 그대로 섰습니다(`ee36e06b`). 반대쪽 한계: 기록이 짧은 큰
    창에서 Codex CLI 0.162.1 은 「Working」 줄을 데몬이 읽는 화면 아래쪽 범위보다 위에 그리므로, Codex 의 조용한 구간이 약 120 초를 넘으면 화면이
    다시 바뀔 때까지 「알 수 없음」 표시가 됩니다(안전한 쪽 · 화면 표시만).
  - **아직 확인하지 않은 상황.** 이 판에서 채집·측정하지 않은 것: 하위 에이전트나 백그라운드 작업을 기다리는 master, 예약된 깨움 사이의 쉼과
    그 뒤 실제 깨움, 비동기 출력이 들어오는 동안의 사람 초안, 실제 좌석 위 역할 × CLI 칸(시험 픽스처만 돌림), 데몬·앱·화면을 거치는
    시작·멈춤·만료 시간(모의 시계 UI 시험만 돌림). 이런 때 점은 「알 수 없음」일 수 있습니다. **master 와 CSO 역할의 F-01 범위는 주장하지
    않습니다.** 이 항목들은 다음 판 백로그로 넘깁니다(§2).
- **그대로인 것**: 화면 표시 전용입니다 — 큐 · 배달 · clear · 사이클 결정을 바꾸지 않습니다(`6b53ed5c`). 측정에서도 세 측정의 모든 팔에서

### 1-4. S-a — 에이전트 좌석으로 가는 기계 입력은 확인된 한 번의 쓰기이고, 「전달됨」은 Return 이 쓰인 뒤에만 셉니다
- **무엇이었나**: 큐 · 직접 보내기 · 예약 push · 채널 수신함 · CEO 자동 경로 · 부트 감독자 알림이 넘기는 순간(「쓰겠다」)을 전달로 세었습니다.
  쓰기가 거부되거나 중간에 멈춰도 전달로 기록될 수 있었습니다.
- **새 쓰기 경로**(`84a96f7f`): 한 작업 안에서 「쓰는 중」 기록을 디스크에 먼저 남기고, 그 뒤 수신자 확인, 그 뒤 OS 호출입니다. 호출 한 번에
  최대 4,096 바이트, 본문은 UTF-8 경계에서 자릅니다. 결과는 여섯 가지로 나뉩니다 — 쓰지 않고 거부 · 쓰기 전 취소 · 본문만 씀 · 본문과
  Return 씀 · 바이트 단위로 정확한 중간 멈춤 · 어디까지 썼는지 모르는 중간 멈춤. 기록(`writer-journal.jsonl`)에는 식별자 · 요약값 · 바이트
  수만 있고 **본문 글은 없습니다**.
- **생산자마다**:
  - **큐**(`bc82915e`): Return 까지 쓰인 뒤에만 꺼내고 영수증 · `queue.delivered` 를 냅니다. 거부되면 항목을 그대로 두고 그 좌석을 1 · 2 · 4 · 8 ·
    30 초 간격으로 잡아 둡니다(잡을 때마다 알림 한 번). UI 낱말은 바뀌지 않았습니다.
  - **직접 보내기**(`82a261d7`, `a295f0b5`): 자기 Return 이 없는 자동 본문은 **치지 않고** 잡아 두고, 같은 호출자의 Return 이 같은 좌석 세대에서
    본문을 다 받은 때부터 **60,000 ms** 안에 오면 본문 + Return 을 한 작업으로 씁니다. 창은 처음 10,000 ms 였다가 실제 호출 기록(나뉜 보내기·Return
    짝 22개, 최대 간격 34.1초)을 재고 60,000 ms 로 고쳤습니다. 같은 호출자의 새 본문은 옛 본문을 대신합니다(`surface.submit_undelivered`
    reason=superseded). 만료 · 에이전트 바뀜 · clear 는 잡아 둔 본문을 치지 않고 같은 이벤트로 처리합니다. 셸 좌석 · 사람 키 · GUI 경로 삽입은 옛
    경로 그대로입니다(바이트 단위).
  - **예약 push**(`bc34ad1d`): Return 이 쓰인 뒤에만 입력 수를 0 으로 되돌리고, 넘긴 뒤에 들어온 사람 입력은 지우지 않습니다. 0 바이트로 거부되면
    그 글을 좌석 큐로 한 번 돌립니다(`schedule.push_refused`). 판정은 최대 2,000 ms 기다립니다.
  - **채널 수신함**(`5ba2b520`): 거부되면 그 행을 넘기기 전 상태로 되돌려 다음 차례에 다시 시도합니다. 응답의 `action:"delivered"` 는 그대로 두고
    `written:"pending"` 과 `request_id` 를 더했습니다.
  - **CEO 자동 경로 · 부트 감독자 알림**(`936a6aac`): CEO 좌석에 쓰기가 거부되거나 중간에 멈추면 사람에게 올라갑니다(피드 항목은 그대로 대기).
    늦은 감독자 알림은 Return 이 쓰인 뒤에만 「늦게 전달됨」으로 알립니다.
  - **좌석 탈취 · npm 접두 경고**(`984e579a`): 셸에 줄을 치지 않고 이벤트(`role.takeover` · `env.advisory`)로만 냅니다. **눈에 보이는 변화**: 옛 셸
    pane 에서 그 줄이 더는 보이지 않습니다(이벤트의 GUI 표시는 C11 범위 · 이 판에 없음).
- **중간에 멈춘 쓰기는 다시 치지 않습니다**:
  - 데몬이 재시작해도 이미 일부가 쓰인 큐 항목을 다시 넘기지 않습니다. 잡아 둔 상태를 `queue-write-holds.json` 에 남기고(본문 글 없음), 재시작 뒤
    입력창이 프롬프트 경계에서 **비어 있다고 측정되고** 잡은 지 2,000 ms 이상이면 그 항목을 미전달로 내보내고 다음 항목으로 갑니다. 입력창에 글이
    보이면 계속 잡습니다(알림 한 번) — 그 좌석의 lane master 가 입력창을 비우거나 제출하면 풀립니다(`39b325e3`).
  - 바이트 단위로 정확히 멈춘 큐 쓰기는 첫 멈춤부터 30,000 ms 안에서만 **같은 요청**으로 이어 씁니다. 그사이 다른 입력이 있었거나 세대가 바뀌었으면
    잇지 않습니다(`75e26d88`).
  - 보류된 Return 은 바이트 수와 세대에 묶어서만 다시 냅니다(`0e0e40d0`).
