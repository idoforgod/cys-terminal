## Retained changes since the public v0.14.54 release

- **Windows daemon rotation:** before an in-app update drains work, writes restoration markers or stops the serving daemon, the retained rotation check runs the replacement `cysd` and `cys` pair with bounded version checks. If the selected pair fails, that rotation is refused. This protection belongs to the new app code once it is running; it does **not** establish that the older .54 updater protects the first .54 → .56 installation. That initial update path remains unmeasured here. [S16]
- **Route-scoped refusal:** a missing or failed department route refuses that department route without preventing an otherwise healthy base rotation. Refusal of the base pair locks both routes. The resolution record now starts on a new line, preventing startup-banner bytes from being glued to a valid record and making resolution fail. The banner-byte mechanism was tested in the earlier work; which startup files MSYS Bash reads inside the Windows Tauri process was not established there. [S16]
- **Protection boundary:** the rotation check covers only the selected `cysd` + `cys` executables, not `cys-app.exe`, the installer or uninstaller. The .55 installer pre-install probe and Phoenix deployment probe were deferred. At this preparation tree, the installer hook and Windows rotation files remain byte-identical to `9da2418d`; the later optional Phoenix hook does not itself establish a deployment run-check. No new final-.56 disposition or native end-to-end protection is claimed for those deferred paths. Native Windows rotation coverage and Smart App Control acceptance remain pending. [S16, S17]
- **Phoenix stale-marker verification:** fresh-session markers carry the daemon boot epoch. A different, absent or unreadable epoch discards the marker and prevents it from producing a false `VERIFIED_FRESH` or `VERIFIED` result in that restoration. When that stale marker was the last condition turning the entire restoration into success, refusing it also prevents a false success from resetting the repeated-failure breaker. Two boots receiving the same epoch value can still collide; setting the internal `PHOENIX_EPOCH_GATE=0` switch bypasses this epoch protection. [S18]
- **Independent Claude resume verification:** `VERIFIED` requires a live seat, a session ID independently registered by that pane matching the pre-restoration expectation, evidence that the registration belongs to this restoration, and an existing transcript. A warm reattachment with unchanged registration can remain `UNVERIFIED` because it cannot be distinguished from the previous occupant’s registration. The earlier work did not establish live Claude end-to-end verification through daemon registration; this draft does not upgrade that evidence to a pass. [S19]
- **Codex/Gemini restoration:** the retained verification path reports `VERIFIED_SEAT_ONLY`. A live seat is not evidence that the previous conversation resumed; conversation continuity is unmeasured on that path. This distinction is separate from the new optional pre-restore script and its plan checks. [S19, S12]
- **Release-service protection:** the copy-drift hard gate compares six release/tooling files against `main` and stops asset production on disagreement, missing files or unreadable comparison evidence. The deployment-ref policy check is fatal, not advisory. The daily watch checks for an existing open drift issue before creating another; its deduplication is implemented, but the .55 notes did not establish runtime idempotency. This changes the release service, not installed-app behaviour; it does not mean the current preparation has already cleared remote parity or publication gates. [S20]

## Changes present in the preparation tree

- **First department ticket:** manifest application queues the first ticket without holding the caller in a delivery wait. Status reports delivery separately from queue acceptance. Reapplying a task does not resend a pending or delivered first ticket; unreadable evidence produces an unknown state. Follow-up changes handle queue digests and ledger rotation. A daemon receipt proves delivery, not that the receiving agent has read the ticket. A real department end-to-end run and Windows runtime validation are not claimed here. [S2]
- **Event reporting:** a failed event-spool append now returns a nonzero status. Phoenix's old `_emit_evt` path and its nine calls were removed; the later restoration work supplies its own result handling. [S3]
- **Task addressing:** the optional `task-prompt --surface` form checks the addressed surface and tells its recipient to resolve its own TODO. The no-flag form preserves the earlier output and behaviour, including its known limitation for numbered/fresh workers. Missing or cross-daemon identity is stated rather than guessed. [S4]
- **Report timestamps and deadlock diagnostics:** timestamp parsing honours UTC offsets. Task writers publish their roots and lane stamps; deadlock evaluation records per-root evidence in shadow mode. Missing evidence is not reported as an empty task set. This is **not a claim that deadlock paging is enabled**. Lexically recognized cloud-managed roots are not read by this path; symlink aliases and redirected Windows cloud folders remain limitations. [S5]
- **Socket framing and attach cleanup:** a nonblank request ending at EOF without its terminating newline is refused instead of executed. A stalled attach can be released after its surface exits or leaves the daemon map; the change is designed to preserve live-surface streams and a reading client's final output. Windows named-pipe/ConPTY behaviour remains subject to native checks. [S6]
- **Event-spool transport:** producers and the bridge use one pack-relative spool-path definition. The bridge reads lanes separately, preserves rotated history, and reports failures to the owning lane's master. Returning files are not reread as new input. Rotation waits during a detected pack-install window; a spool over 8 MiB can rotate inside the startup grace once a poll is drained. This is not a hard bound on storage: repeated installs, an unreadable parent, a bridge dying before a drained poll, or a continuously busy spool can still prevent rotation. [S7]
- **Owned child processes and hook startup:** the C-03 work brings owned child-lifecycle handling and bounded skillscan pool stopping into this .56 candidate. “Restored” in its development history means reintroducing code removed from the unpublished .55 branch; it does not mean restoring a feature from a public .55 release. C-03 and the optional Phoenix hook below would be newly delivered to public users only if this .56 candidate passes its remaining release gates. [S15, S21] Follow-up changes end the cooperative grace when the leader is gone, resolve hook paths with either slash form, relay phase bytes unchanged, and separate managed Windows input from the private lifeline. **C-03 native results at the final candidate are PENDING**; cross-typechecking cannot validate Job Objects, process teardown or Windows hook execution. [S8]
- **Release preparation:** post-processing preserves an existing published checksum file, distinguishes draft and public mismatches, requires a matching asset digest for cache reuse, and uploads the exact candidate bytes it checked. A public checksum mismatch stops the operation before remote writes. [S9]
- **Download-page checks:** both download pages must match reviewed skeletons with their version/size slots filled. The homepage JavaScript import closure is pinned by names and hashes. Staging and remote verification use the shared checker; missing skeletons or unreadable inputs fail the check. This draft does not claim the live homepage has been updated. [S10]
- **Regression tests:** selected PTY, writer-handoff and recorder tests now observe the event being tested instead of relying on a short sleep. The bash-specific parked-reader hang has a bounded, named fixture reap. A wall-clock-premise ratchet checks newly introduced timing assumptions. These are test changes, not a claim that every Windows failure has been repaired. [S11]

## P1 — one composer verdict and checked delivery into master/CEO seats (integrated in the candidate)

P1 changes how the daemon decides whether a Claude seat's input line is empty, and how text and keys reach **master and CEO** seats — the seats whose input line the owner types into and that the context cycle clears. It was developed against the v0.14.55 code (pin `9da2418d`), merged at `77f66491`, and is present in `5bb5c2a4`. The behaviour below is what the lane's own commit messages and design record state and what the cited source shows at `5bb5c2a4`; those runs happened on the lane's Mac. **None of it has run on Windows, and the candidate's own native CI and full local battery are PENDING.** [S22, S23, S24, S25, S26, S27, S28, S29]

- **One composer verdict on Claude seats (D1).** The daemon classifies the input line once per observation as empty, placeholder, suggestion, draft or unknown. The queue gate, the stale-count reset, the partial-hold release, the slash-admission label, the direct-send draft gate, the machine-inject draft check and the operator's force-deliver/remedy text all read that one verdict. Two behaviour changes follow. A rendered Claude *suggestion* no longer holds a queued delivery. A draft the owner typed and then moved the cursor within (a "Home-moved draft") is no longer read as empty: it holds deliveries on Claude seats until it is submitted or cleared, and the `human_draft` remedy text now says to read the screen first, because the window may be a selection window rather than text. The verdict governs only the `claude` adapter; gemini, codex and grok seats keep their previous readings, so on those seats a Home-moved draft can still read as empty. [S22]
- **D1 is off on Windows, and its macOS basis is one measurement.** Whether Windows ConPTY passes the dim attribute (SGR 2) that marks a suggestion is **unmeasured**, so Windows seats keep the previous readings and a Home-moved draft still reads as empty there, as before. On macOS the suggestion rule rests on SGR 2 measured on one Claude 2.1.312 rig; a Claude version or theme that draws suggestions differently would read as a draft and hold ("input pending") until someone types. On alt-screen seats that equals the previous behaviour; on non-alt Claude seats it is a change from deliver to hold. This candidate has no Claude-version gate for that case, and the one-shot event that would make it visible is next-version backlog B-490. [S22, S30]
- **Non-owner sends into master/CEO are one queue job (D9).** A `cys send` into a master or CEO composer (an agent-backed seat whose role is master or ceo in that daemon) from a caller that is not the owner is converted into one queue job — body plus its own Return, audited once at delivery. `cys send` prints `QUEUED`; an old daemon still prints `OK`. The Return of a two-step send (`send`, then `send-key Return`) is absorbed by that send's live pair ticket, or refused with `composer_key_denied` and zero bytes typed. Any other unbound key from such a caller is refused with nothing typed. A key bound to the observed frame (`--expect-output-gen`, for modal windows) is accepted only if the frame still matches at the writer's claim, with no queued fallback; a persisted empty-text `send-key` queue item from an earlier version is retired when it reaches the head of a master/CEO queue. The launching operation answering its own folder-trust prompt on a new seat is allowed. A relauncher (`cys restore` in-seat, `node-recover`) is not the creator of an existing seat: once the watchdog has observed the relaunched agent (its tick is 5 s, so for up to one tick the key is still written, as at v0.14.55), its confirming key to a trust prompt is refused with zero bytes, `node-recover` exits 79 without the kill-and-reclaim escalation, and `restore` keeps the seat instead of launching a second agent. [S23, S27]
- **What a converted send now costs.** A converted send waits for an idle prompt instead of entering Claude's own mid-turn input queue, carries the queue TTL (6 hours by default, `CYS_QUEUE_TTL_SECS`) and is refused with `queue_full` at the 100-entry queue cap. A direct send into master/CEO had none of these at v0.14.55. At `5bb5c2a4` the `queue_full` text does not say that the send was a conversion. Agents and operators that pushed keys at a master/CEO composer to clear a blocking window lose that path unless the window is one the detector classifies as modal; **not established:** whether the Claude session-rating overlay (dismissed by `0`) or the usage-limit dialog is classified as modal on a current Claude release — the pre-tag review ruled that to be measured first. [S23, S30]
- **Cycle reinject order (authoritative jobs).** The context cycle's last step (the reinject of the directive and `[RESUME]` into the cleared seat) and boot directives are marked authoritative when their caller passes the daemon's authority check or is the seat's current cycle owner. The queue places them ahead of ordinary queued reports (FIFO among authoritative jobs), never merges them, and counts queue age from the oldest of the leading authoritative run and the first ordinary entry; `queue.order_inverted` names the oldest same-sender entry. At v0.14.55 the reinject was typed directly and was therefore first. **Limits:** an authoritative job does not move ahead of an entry that is part of the current hand-off or of the seat's queue hold, so a held partial write stays first; head placement is not kept across a daemon restart (restore re-sorts the queue by age — a named residual of the design); and this orders entries inside the queue only — its order against producers that write directly into the seat is the open finding below. `node-recover`'s directive still joins the tail of the queue (next-version backlog). [S24, S30]
- **Checks between hand-off and first byte.** For master/CEO jobs the writer's claim refuses — zero bytes, the item stays at the head, the next tick judges a fresh frame (if the writer's claim lands after the caller stopped waiting, the hold is instead retried after a backoff of 1, 2, 4, 8 up to 30 s) — if any write, input or human key reached the seat after the baseline taken at hand-off (`queue.inject_aborted`, why `foreign_since_handoff`); the baseline is read before the producer's frame judgment. The Return is withheld while a question or selection window is on screen, and the queue hold's resume then writes it once, within `PARTIAL_EXACT_RESUME_WINDOW_MS` (30,000 ms) — **residue:** past that window the body stays unsubmitted on the seat's line until it is cleared. The daemon's own one-job writers into master/CEO (CEO approval push, channel envelopes, boot-failure pane notices, schedule pushes) get the same claim check; their Return keeps the v0.14.55 behaviour with no window probe. A seat whose writers are still busy holds queue and channel deliveries (`writer_active` maps to the existing wait remedy). Queue and channel refusals are counted per producer, with bounded events, one escalation per streak and a read-only status view; the daemon's own CEO, boot-notice and schedule writers have the claim check but are not in that counting. Channel pacing rechecks the completion gap at hand-off. [S25]
- **Cycle clear and in-seat restore.** `cys cycle-agent`'s clear now requires the caller's own live cycle claim, otherwise it is refused before any write (`cycle_clear_unclaimed`). A valid clear admits a line proven to hold the daemon's own machine text and waits out the daemon's own paste (`own_paste_settling`). The output and input generations observed in one composer observation travel with the clear; a moved generation is a refusal (`guard_aborted`), zero bytes, and is not reported as sent. Human input holds the clear. Retries are limited to journal refusals and guard aborts — at most three attempts, each on a new observation, inside the original stage deadline; an unknown outcome is never retried. At the cap, only a history of three known-zero guard aborts becomes the existing non-destructive hold (exit 84, `[diag=guard_retry_exhausted]`), so the automatic cycle controller can retry after its existing cooldown. Exit 84 therefore covers both idle-wait holds and this post-observation guard exhaustion; it does not prove the target was busy throughout the wait. Any journal refusal in the history retains exit 1, and unknown/possibly-written outcomes are not replayed. The unsupported three-call fallback was removed. **Effect on a seat with no registered agent (no agent metadata):** per the head's re-measurement (S32), at v0.14.55 the fallback was reachable only with an explicit `--clear-cmd`, and every automated cycle (the detach runner, the autopilot and the CSO pass none) already stopped at step 0 with exit 1 ("agent 메타 없음 — --clear-cmd 명시 필요", `cys.rs` line 22450 at `9da2418d`, line 22579 at `5bb5c2a4`). The lack of registered agent metadata remains a refusal. In the current candidate, an explicit `--clear-cmd` on such a seat receives `cycle-target-unregistered:` (exit 1, not retryable), with zero bytes written and no split fallback; the daemon's `clear_first_unsupported` response is no longer labelled BUSY/exit 84. The step-0 guidance now directs registration through `cys launch-agent`, rather than advising an explicit clear command. The head's census of the running fleet (0.14.54 daemons) found no seat without agent metadata (0 of 66 role seats). [S26, S31, S32]
- **Held bodies and token Returns.** On non-master seats a held body is reserved at hand-off and settled by the write's outcome: zero bytes restore it with its receipt deadline, a written clear disposes of it as cleared, and an unknown outcome disposes of it as `clear_outcome_unknown` or `bound_outcome_unknown` and is never restored. A token Return binds only its own caller's held body, and the typing-guard retry of `cys send-key` keeps the first request's `from`. [S27]
- **Read-screen composer export.** `cys read-screen --composer` prints one JSON object — `text`, the daemon's `composer` verdict from the same one-frame observation, and `quiet_secs`; it is refused beside `--lines` or `--since`, and an old daemon yields `composer: null`. A poisoned parser lock exports verdict `unknown`. The `javis_actprobe.py` submit probe reads that object, which fixes C-24: a rendered suggestion on the caret row was a false FAIL, and a continuation-row draft under an empty caret row was a false PASS. [S22]
- **Windows and other residue.** P1 test specimens that need a POSIX recorder seat are ignored on Windows (the P1 branch grew the Windows ignore registry from 55 to 86 entries; the assembled candidate's registry pin is 92, the preparation baseline's 61 plus P1's 31), so those specimens give no Windows result; the Return withhold under a window is armed on unix only, as at v0.14.55. `PairKey::Process`'s native parent birth on Windows is **unmeasured**; without it there is no pair ticket and the Return is refused after the body was already submitted. Claude versions other than 2.1.312 need the suggestion rendering re-measured. [S28, S22]
- **Test and assembly commits in the candidate.** Selected P1 specimens observe a named completion event (scoped admission and completion receipts, receiver FIFO barriers) instead of a sleep; source pins cut at the exact tests-module header; cysd tests restore process environment through `governance::ReapEnvGuard` on unwind; the Phoenix gate (`849cd404`) observes the private pack's real side effects and independently gates its four required negative controls. `4cce6d23` adds `docs/HOMEPAGE_0.14.56.md` (release-day fill and refusal sequence; size slots stay unresolved until published assets are measured) and a test that an unfilled size slot refuses the homepage switch before any public move; no homepage publication is certified. `7c21a35a` regenerated the previous-vendor authority after final pack integration; `8bd287c5` refreshed the generated dormancy population (17 line-only moves, no row added, removed or relabelled); `5bb5c2a4` removed one stale id from the wall-clock baseline (327 to 326). Native CI and publication were not run for these commits. ## Optional script before automatic restoration

Before restoring seats, the daemon can run one user-selected Python script whose bytes match the `default` entry in `~/.cys/local/phoenix-allow.sha256`. It checks a read-only restoration plan before and after the hook, bounds the hook, and skips built-in restoration only when the post-hook plan certifies that nothing remains. Without the allow file, the existing built-in restoration path remains the default. [S12]

The same work adds the read-only Phoenix `plan` command, result-file handling, and a single later recheck when restoration yields to another active restoration. See `docs/INSTALL.md`, “사전 복원 스크립트”, for the configuration and exit contract. [S12]

**Residual risk:** on macOS/Linux, a helper spawned by the hook can retain `hook.run.lock` through inherited stdin after the hook exits, preventing automatic restoration on the next boot until that helper ends; hook authors must give helpers `</dev/null` or `stdin=DEVNULL`. Removing the allow-file entry disables the optional hook. [S12]

**Windows has no previous-boot hook detection.** The check for a hook still alive from the previous boot (the `hook.run.lock` probe) runs on unix only (`if cfg!(unix)` in `main.rs` at `5bb5c2a4`). If the daemon's Job assignment of a hook fails, a hook can outlive a daemon death, and the next boot can run a second hook with no previous-boot check; how the hook's Job nests inside the daemon's Job on Windows is **unmeasured**. [S12, S30]

Windows hook execution under Smart App Control, task-scheduler environment, Job nesting/spawn-to-assignment behaviour, stall cadence, and final-candidate native hook tests remain **UNMEASURED/PENDING** in this draft. The lane's reported macOS tests do not replace those checks. [S12]
