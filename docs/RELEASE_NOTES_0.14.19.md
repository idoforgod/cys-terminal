# cys 터미널 v0.14.19

## Windows 전체화면에서 **휠이 입력창을 헤집던 경로**를 봉인했습니다

Windows 에서 claude 를 전체화면(fullscreen)으로 쓰다가 마우스 휠을 굴리면, 스크롤 대신
**입력창의 내용이 지나간 프롬프트로 바뀌어 버리는** 증상이 있었습니다. 이번 릴리스는 그 경로를
UI 계층에서 막습니다.

> ★**"고쳤습니다"가 아니라 "봉인했습니다"** 라고 적는 이유는 이 문서 아래
> **[정직 고지 — 확정과 미확정](#정직-고지--무엇이-확정이고-무엇이-미확정인가)** 에 있습니다.
> 발현 조건 자체가 실기에서 확인되지 않았고, 그 확인은 **Windows 실기 스모크**의 몫입니다.
> 조건이 성립하지 않는 환경에서 이 변경은 **무해하지만 무력**합니다.

## 1. Windows 휠 가드 (이번 릴리스의 본체)

### 무슨 일이 있었나

Windows 에서는 마우스를 앱에 그대로 넘기는 길이 막혀 있습니다(ConPTY 가 마우스 보고를
깨뜨려 입력창에 `[555;98;34M` 같은 글자가 찍히기 때문 — 매뉴얼이 앱 마우스 킬스위치를
Windows 에서 켜지 말라고 못박아 온 이유입니다). 그래서 전체화면 앱에 휠을 굴리면 터미널이
그것을 **방향키로 합성해** 앱에 보냅니다. 대부분의 앱에서는 그게 정상 동작(vim 의 휠
스크롤)이지만, **claude 는 방향키를 프롬프트 히스토리 이동으로 씁니다** — 휠 한 번에 입력창이
통째로 바뀌는 것이 그 증상입니다.

### 무엇이 달라지나

- 그 **한 조합에서만** 휠을 소비합니다. 판정 기준은 "앱이 어떤 마우스 추적 모드를 켰는가"이며,
  claude 가 전체화면에 들어갈 때 켜는 모드(any-motion)를 켠 앱만 대상입니다.
- **`less` · `man` 처럼 마우스를 요청하지 않는 앱의 휠은 어떤 환경에서도 종전 그대로**입니다.
- **vim `mouse=a` 도 통상 대상이 아닙니다** — 휠→방향키 합성이 그대로 살아 있습니다.
- ⚠**대가(숨기지 않습니다)**: 억제가 걸린 창에서 그 휠 노치는 스크롤도 방향키도 아닌
  **무동작**이 됩니다. 전체화면에는 스크롤백이 없어 "대신 화면을 굴린다"는 선택지가 없습니다.

### 보호 범위 — "Windows 의 모든 전체화면 휠"이 아닙니다

가드는 **앱이 마우스 모드를 선언한 뒤**에 걸립니다. 그래서:

- **GUI 를 재시작해 이미 떠 있던 전체화면 앱에 다시 붙은 pane**(세션 복원·재부착)에서는 걸리지
  않을 수 있습니다. 재부착이 보내는 초기 화면은 글자 스냅샷뿐이라 앱의 모드 선언이 다시 오지
  않기 때문입니다. cys 는 세션 복원이 상시 동선이므로 이것은 예외가 아니라 흔한 경우입니다 —
  그 pane 에서 오염이 보이면 앱을 한 번 나갔다 들어가거나 pane 을 새로 여십시오.
- 전체화면 앱이 **비정상 종료**(강제 종료·크래시)해 이탈 신호조차 못 보내고 죽으면 판정이 남을
  수 있습니다. 그 pane 은 이미 전체화면 화면에 갇힌 상태라 **처방은 어느 쪽이든 "pane 을 새로
  여세요"** 로 같습니다.

즉 실제 보호 범위는 **"새로 붙인 pane 에서, 앱이 마우스 모드를 선언한 뒤, 전체화면인 동안"**
입니다.

## 2. Windows 에서 claude 를 전체화면 대신 inline 으로 — **옵트인(기본 off)**

휠 가드는 오염을 *막을* 뿐 화면 모드를 바꾸지는 않습니다. claude 자체를 inline 으로 띄우는
길(`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` 주입)은 이번에 **Windows 에서 옵트인**으로
들어갑니다 — **켜지 않으면 Windows 의 기본 동작은 이전 출고본과 완전히 같습니다**.

- **켜는 법**(PowerShell): `New-Item -ItemType File -Force $HOME\.cys\win-no-alt-screen`
  → 그 뒤 **`cys launch-agent` 로 새 pane 을 기동**해야 실립니다.
  되돌리기: `Remove-Item $HOME\.cys\win-no-alt-screen`.
- env `CYS_WIN_NO_ALT_SCREEN=1` 도 동등하지만 **GUI 가 기동할 때 상속한 값만** 읽습니다
  (`setx` 후 GUI 재시작 필요). **권장 수단은 파일**입니다.
- **왜 Windows 만 기본 off 인가**: 이 값이 Windows 의 claude 를 깨뜨리면 `cys boot` 로 띄운
  **모든 노드가 한꺼번에 죽는** 경로입니다. 실기 Windows 에서 그 확인(`cys boot` 4종 노드 정상
  기동)을 마치기 전에는 안전한 쪽을 기본값으로 둡니다. 켜지 않아도 **휠 오염은 위 1번 가드가
  막습니다** — 그쪽이 본체 방어이고 이 값은 덧대는 벨트입니다.
- ⚠**켜도 도달 범위가 좁습니다**: 새 surface 를 만들며 기동하는 `cys launch-agent` 로 연 pane
  에만 실립니다. 이미 열린 pane 의 재기동(node-recover)·GUI 에서 연 pane 에는 실리지 않습니다.
- 팩 `agents.json` 의 env 에 `"0"` 을 적어 두었다면 켜도 주입하지 않습니다(**사용자 값이 언제나
  우선**). macOS 는 이 스위치 없이 종전대로 늘 주입됩니다.

## 3. 입력이 안 들어갈 때, 이제 화면이 알려 줍니다

종전에는 pane 으로 보내는 입력이 데몬에서 거부되어도 **아무 흔적도 남지 않았습니다**. 권한 거부,
프로세스 종료, 입력 채널 포화, 소켓 절단 — 넷 다 조용히 삼켜졌습니다. 그래서 실제 결함이
"키를 쳐도 아무 일이 없다"로만 나타나고, 화면에도 알림 이력에도 근거가 없어 사용자도 조사하는
쪽도 원인을 볼 수 없었습니다.

- 이제 그 실패가 **토스트로 뜹니다** — pane 이름과 데몬이 준 사유가 함께 나옵니다
  (예: "surface process has exited", "surface input channel full (pane not consuming input)").
- 빠르게 타이핑할 때 매 키가 실패해도 화면이 도배되지 않습니다: **pane 당 한 줄**로 접히고,
  같은 창의 실패는 건수로 합산해 최대 3초에 한 번만 갱신됩니다(첫 실패는 즉시 뜹니다).

## 4. 눌러도 아무 일이 없던 승인 버튼을 고쳤습니다

승인 Feed 에는 두 종류가 섞여 있습니다. **앱이 직접 올린 승인 요청**과, **데몬이 화면을 보고
"승인 프롬프트가 떠 있는 것 같다"고 감지해 올린 항목**입니다. 후자에 대해 종전 UI 는
Allow/Deny 버튼을 그려 줬는데, **그 버튼은 앱에 한 바이트도 보내지 않습니다** — 목록에서
항목만 사라지고 pane 의 프롬프트는 그대로 남았습니다. 사용자를 속이는 버튼이었습니다.

- 그 항목의 버튼이 **'이 pane 에서 직접 응답'(해당 pane 으로 점프)** 과
  **'알림 치우기'(목록 정리 전용)** 로 바뀌었습니다. 두 버튼의 의미를 라벨과 설명에 명시합니다.
- '알림 치우기'가 하는 일도 숨기지 않습니다: 그 pane 에 승인 프롬프트가 **아직 떠 있으면** 데몬이
  잠시 뒤 다시 감지해 항목이 재등장할 수 있고, 치울 때마다 '사람 개입 필요' 경보의 방치 시계가
  처음부터 다시 갑니다. 즉 **이미 사람이 응답했거나 pane 이 죽은 항목**에 쓰는 정리 버튼입니다.
- **커맨드 팔레트의 '승인' 액션도 같은 판정을 씁니다** — 종전에는 팔레트가 패널에서 없앤 그
  무효 승인을 되살리고 있었습니다.
- 대기 목록이 길어도 **지울 수 없는 항목이 생기지 않도록** 대기 항목을 먼저 렌더하고, 상한을
  넘는 분량은 '더 보기'로 펼칩니다.
- ⚠**정직 고지**: 이 목록과 버튼은 **기본 데몬 하나**만 봅니다. 부서 데몬의 대기는 사이드바
  배지에는 잡히지만 이 목록에는 나오지 않습니다 — 이제 그 사실을 목록 위에 배너로 표시하고
  해당 워크스페이스로 전환하도록 안내합니다(근본 수리는 다음 범위).

## 5. 승인 항목 **위조 차단** (보안)

데몬이 스스로 올린 감지 항목은 `daemon-` 으로 시작하는 식별자를 씁니다. 종전에는 아무 프로세스나
그 접두를 지정해 항목을 밀어 넣을 수 있었고, 그러면 ①GUI 에서 승인 버튼이 사라져 오너가 승인할
수 없게 만들거나 ②그 pane 의 **진짜** 감지 승인이 올라오지 못하게 막을 수 있었습니다.

- 이제 데몬이 그 접두를 **예약 이름공간으로 거부**합니다(정품 발행 경로는 데몬 내부 전용).
- GUI 는 접두 문자열을 스스로 해석하지 않고 **서버가 실어 주는 판정값**을 읽습니다. 판정의
  정의처가 한 곳으로 모여, UI 와 데몬이 서로 다른 기준을 갖는 상태 자체가 사라졌습니다.

## 6. 휠 가드가 눌러붙던 경로 봉인

전체화면 앱이 끝난 뒤에도 "이 pane 은 억제 대상"이라는 판정이 남으면, 다음에 뜨는 앱이
`less` 든 `vim` 이든 그 pane 이 닫힐 때까지 휠이 죽습니다. 이번 릴리스는 **전체화면 이탈이
관측되면 그 기록을 지웁니다** — 재부착으로 시작해 진입 신호를 못 본 pane 까지 덮습니다.
출력 바이트는 한 개도 바뀌지 않습니다.

남는 경우는 앱이 **이탈 신호조차 못 내고 즉사**할 때뿐이고, 그 pane 은 이미 전체화면 화면에
갇혀 있어 처방이 "pane 을 새로 여세요"로 같습니다(§1 의 '보호 범위'와 동일).

## 정직 고지 — 무엇이 확정이고 무엇이 미확정인가

이 수리가 효과를 내려면 **"Windows 의 Claude Code 가 전체화면(alternate screen)으로 뜬다"**
는 조건이 실제로 성립해야 합니다. **그 조건은 실기에서 확인되지 않았습니다.**

**확정(실측으로 뒷받침됨)**

| # | 사실 | 근거 |
|---|---|---|
| 1 | 전체화면 버퍼에서는 터미널이 휠을 **방향키로 합성해** 앱에 보낸다 | 번들된 xterm 5.5.0 실측 |
| 2 | Windows 에서는 앱의 마우스 요청이 **전량 걸러진다**(그래서 앱이 휠 보고를 받을 길이 없다) | 저장소 코드 실측 |
| 3 | 수리 전 Windows 에는 **휠 핸들러가 아예 등록되지 않았다** | 수리 전 코드 실측 |
| 4 | claude 에서 방향키 위/아래는 화면 스크롤이 아니라 **프롬프트 편집·히스토리 이동**이다 | 실바이너리 2.1.233 키바인딩 실측 |

**미확정(모르는 채로 남습니다 — 숨기지 않습니다)**

1. **오너가 겪은 그 화면이 실제로 전체화면이었는가.** 확인하지 못했습니다.
2. **"마우스는 정상이다"라는 보고가 정확히 무엇을 뜻했는가.** 해석이 갈립니다.
3. **vim `mouse=a` 가 이 가드의 판정 기준(any-motion)을 켜는가.** 저장소에 vim 의 실제 캡처가
   **0건**입니다 — 문헌·관례 근거일 뿐입니다. 켜는 vim 설정·플러그인 조합이라면 **그 앱의
   전체화면 휠도 무동작이 될 수 있습니다**(그때가 아래 롤백을 쓸 때입니다).

**그래서 이 릴리스가 주장하는 것과 주장하지 않는 것**

- 주장합니다: 그 오염 경로를 **UI 계층에서 봉인했다**. 조건이 성립하면 오염이 일어나지 않는다.
- 주장하지 않습니다: "Windows 의 휠 문제가 고쳐졌다". 조건이 성립하지 않는 환경에서 이 변경은
  **무해하지만 무력**합니다.
- **발현 여부의 확인은 아래 Windows 실기 스모크**가 합니다 — 자동 테스트는 어느 것도 그 축을
  대신하지 못합니다.

## 스위치 두 개 — 롤백(§1 끄기)과 옵트인(§2 켜기)

이번 릴리스가 새로 들이는 **사용자 스위치는 두 개**이고, **서로 반대 방향**입니다. 이름이 비슷해
헷갈리기 쉬우니 한 표에 나란히 둡니다.

| 스위치 | 무엇을 끄나 | 켜는 법(Windows · PowerShell) | 적용 시점 |
|---|---|---|---|
| **`CYS_WIN_WHEEL_GUARD_OFF`** / `~/.cys/win-wheel-guard-off` | **§1 Windows 휠 가드**를 통째로 끕니다 → 종전(휠→방향키 합성)으로 복귀 | `New-Item -ItemType File -Force $HOME\.cys\win-wheel-guard-off` | **파일 = 새 pane 부터 즉시** · env = GUI 재시작 필요 |
| **`CYS_WIN_NO_ALT_SCREEN`** / `~/.cys/win-no-alt-screen` | 반대로 **§2 를 켜는** 옵트인 스위치입니다(기본 off) | `New-Item -ItemType File -Force $HOME\.cys\win-no-alt-screen` | `cys launch-agent` 로 여는 **새 pane** 부터 |

- **되돌리기**는 그 파일을 지우는 것입니다 — PowerShell `Remove-Item <그 파일>`.
  macOS·Linux 셸이라면 만들기가 `touch <그 파일>`, 지우기가 `rm <그 파일>` 입니다.
  ⚠**`touch` 는 PowerShell·cmd 에 없는 명령**이니 Windows 에서는 위 `New-Item` 을 쓰십시오.
- ⚠**`CYS_WIN_WHEEL_GUARD_OFF` 는 결함을 되살리는 스위치입니다.** 끄면 claude fullscreen 에서
  휠이 다시 방향키로 합성돼 **입력창이 다시 오염될 수 있습니다**. "vim 등에서 휠→방향키가 꼭
  필요하다"는 이유로만 끄십시오.
- ⚠ 이 용도로 **`allow-app-mouse`(`CYS_ALLOW_APP_MOUSE=1`)를 대신 켜지 마세요** — 그것은 입·출력
  양측을 열어 Windows ConPTY 결함(입력창에 `[555;98;34M` 같은 글자가 찍히는 현상)을 되살립니다.
- ⚠ 기존 정합기 스위치 `localStorage.cysMouseReconcilerOff="1"` 로는 **Windows 휠 가드가 꺼지지
  않습니다.** 그것은 macOS 정합기(출력 소비)의 스위치입니다. 종전에는 Windows 에 휠 핸들러가
  아예 없어 이 구분이 없었습니다.
- 릴리스 빌드에는 devtools 가 없으므로 **파일이 Windows 의 정본 수단**입니다
  (`localStorage.cysWinWheelGuardOff="1"` 은 devtools 가 있는 빌드용).

사용자 매뉴얼 정본: `USER-MANUAL.md` §4.6b 와 부록 env 표.

## Windows 실기 스모크 게이트 — 릴리스 게이트와 승격 게이트

이번 릴리스는 Windows 전용 코드를 새로 들입니다. 자동 검증(CI)이 답할 수 있는 것은
**"코드가 그렇게 배선돼 있는가"** 까지이고, **"claude 가 실제로 그렇게 동작하는가"** 는 어느
자동 테스트도 답하지 않습니다. 그래서 사람이 Windows 기계에서 통과시켜야 하는 항목이 있고,
그 항목은 **두 등급**으로 나뉩니다.

**① 태그(출고) 전 필수 — 이번 출고본의 기본 경로를 밟는 항목**

| 항목 | 통과 기준 |
|---|---|
| **A-1** GitHub Actions → `windows-health` 를 릴리스 브랜치로 **1회 수동 실행**(그 워크플로는 릴리스 브랜치 push 로 자동으로 돌지 않습니다) | Windows 전용 파이프라인 핀 스텝이 **존재하고 초록** |
| **B-1** 새 pane + claude fullscreen 에서 휠 굴리기 ← **발현 여부를 직접 답하는 항목** | 휠 무동작 · **입력창이 바뀌지 않음** |
| **B-2** vim `:set mouse=a` 에서 휠 굴리기 | 종전대로 휠→방향키 합성이 살아 있음 |
| **B-3** `less` / `man` 에서 휠 굴리기 | 종전대로 페이지가 굴러감 |
| **B-4** 휠 가드 롤백 파일 생성 후 새 pane | B-1~B-3 이 모두 **종전(무가드) 동작**으로 복귀 |
| **B-5-b** **옵트인 없이** `cys boot`(4종 노드) | 전원 정상 기동 · pane 안 `$env:CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN` 이 **비어 있음**(= 기본 미주입 · 이전 출고본과 동일) |
| **B-6** GUI 재시작 후 기존 claude pane 재부착 | 가드 발화 여부를 **관측·기록만**(현 코드 기준 예상 = 발화하지 않음 — §1 '보호 범위') |

**② 승격 전 필수 — 이번 출고본의 기본 경로에 없는 항목**

| 항목 | 지위 |
|---|---|
| **B-5** **옵트인 후** `cys boot`(4종 노드) — pane 안 D5 값이 `1` 이고 claude 정상 표시 | **태그를 막지 않습니다.** §2 가 기본값에서 빠져 있기 때문입니다. 이 항목은 §2 를 **기본 on 으로 올리기 전에만** 요구되는 유일한 해제 조건입니다 |

**B-1~B-3 이 실패하면**: B-1 실패(오염 재현)는 판정 기준을 넓혀야 한다는 뜻이므로 가드 재설계가
필요합니다. B-2·B-3 실패(휠 무동작)는 그 앱이 any-motion 을 켠다는 뜻이므로 판정 오판이
확정입니다 — 우선 위 롤백 파일로 사용자 탈출구를 안내하고, 다음 라운드에서 그 앱의 실제 출력을
캡처해 기준을 좁힙니다.

절차·근거의 정본은 `docs/plans/v0.14.16-release-notes.md` 의 '★릴리스 전 Windows 실기 스모크'
절입니다(파일명은 v0.14.16 이지만 그 절은 이번 판번 것입니다 — 그 문서 머리말의 판번 고지 참조).

## Windows Defender / SmartScreen 안내 (유지)

Windows 설치 파일은 코드 서명 평판이 쌓이기 전까지 SmartScreen 경고("알 수 없는
게시자")가 뜰 수 있습니다. **"추가 정보" → "실행"** 으로 진행하시고, 다운로드한 파일은
홈페이지의 `SHA256SUMS.txt` 와 대조해 무결성을 확인할 수 있습니다. Defender 오탐은 WDSI
신고를 거쳐 릴리스마다 최소화합니다.

### Defender가 `cys.exe` 를 격리한 경우 — 복구는 **순서**가 생명입니다

드물게 Defender의 행동 휴리스틱(`Behavior:Win32/Execution.A!ml`)이 명령줄 실행 파일만
오탐 격리할 수 있습니다. 이때 앱과 데몬은 살아 있는데 CLI만 사라져 부팅 체인이 멈춥니다.
**제외를 먼저 등록하고, 그 다음 복원하세요** — 순서를 바꾸면 실시간 보호가 복원 직후
다시 격리합니다.

```powershell
# ① 제외 먼저 (관리자 PowerShell)
Add-MpPreference -ExclusionPath "$env:LOCALAPPDATA\cys"
# ② 그 다음 복원
& "$env:ProgramFiles\Windows Defender\MpCmdRun.exe" -Restore `
    -Name "Behavior:Win32/Execution.A!ml" -Path "$env:LOCALAPPDATA\cys\cys.exe"
```
