### 1. 부서 이름 검증 — 유령 부서·껍데기 승격 차단

부서 이름에 화이트리스트(`영숫자 시작·영숫자/_/- ·40자 이하`)가 걸립니다. `--help` 같은
플래그 문자열이 이름으로 오인돼 유령 부서가 생기는 경로, 점(`.`)만 다른 이름이 Windows
상태 저장소를 병합시키는 경로가 막힙니다. 기존의 정상 부서는 이름 그대로 재기동됩니다
(자기 제외 규칙 — 재-launch/rotate 무회귀). CEO 승격 판정은 '승격 영수증 + 표지 핀' 으로
결정론화됐고, 승격 백업(`.pre-ceo`)을 파괴하는 명령은 기계가 거부합니다.

### 2. 마우스 정합기 — 스크롤백과 앱 마우스의 양립 (macOS)

- 일반 pane·inline TUI: 휠 = 이 pane 의 스크롤백(종전과 동일).
- **마우스를 요청하는 전체화면 TUI**(claude fullscreen·codex·vim `mouse=a`·tmux `mouse on`
  등): 휠이 **앱 자체 스크롤**로 들어갑니다 — claude 라면 트랜스크립트가 굴러가고, 입력
  히스토리는 더 이상 오염되지 않습니다.
- 전체화면 마우스 TUI 안의 텍스트 복사는 **Option+드래그 → ⌘C** 입니다(일반 드래그는 앱으로
  갑니다 — 의도된 트레이드오프).
- 문제가 생기면 롤백 스위치 한 개로 구동작 복원: `localStorage.cysMouseReconcilerOff="1"`.
  Windows 휠 가드는 **별도 스위치**입니다(`~/.cys/win-wheel-guard-off` 파일 또는
  `CYS_WIN_WHEEL_GUARD_OFF=1` — 아래 '알려진 제한'의 Windows fullscreen 휠 항목).
- 방어층: **macOS** 에서 claude 는 기본적으로 inline 으로 뜨도록 env 를 주입합니다
  (`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` — 사용자가 `agents.json` 에 `"0"` 을 적으면
  절대 덮지 않습니다). ⚠ 이 env 는 **벨트**입니다 — 본체는 UI 쪽 휠 가드입니다.
- ★**Windows 의 D5 는 이번 릴리스에서 '옵트인'입니다(기본 off)** — 켜는 스위치는
  `~/.cys/win-no-alt-screen` 파일(또는 `CYS_WIN_NO_ALT_SCREEN=1`)이고, 켠 뒤 **새 pane 을
  `cys launch-agent` 로 기동**해야 실립니다(USER-MANUAL §4.6b · env 표).
  · **왜 기본이 아닌가**: 이 env 가 Windows 의 claude 를 깨뜨리면 `cys boot` 로 띄운 4종 노드가
  **전부** 죽습니다(아래 실기 스모크 B-5 가 그것을 확인하는 유일한 수단인데, 이번 라운드에
  물리 Windows 기계가 없어 수행하지 못했습니다). 그래서 기본값을 미주입으로 두었습니다 —
  **Windows 사용자 입장에서 이 항목의 동작은 이전 출고본과 동일**하고(회귀 0), 전체화면 휠
  오염은 §2-W 의 휠 가드가 그대로 막습니다.
  · **기본 on 승격 예정**: 실기 스모크 **B-5 를 1회 통과**하면 기본 on 으로 올립니다. 코드에서
  바꿀 곳은 `src/lib.rs` 의 `d5_gate_for_os` 한 줄이며, 그 함수 doc 에 승격 조건·동반 개정
  목록이 전부 적혀 있습니다.
  · ⚠ 옵트인해도 **새 surface 를 만들며 기동한 pane 에만** 도달합니다(기존 pane 재기동·GUI 에서
  연 pane 에는 실리지 않습니다). fullscreen 을 이것만으로 막았다고 보면 안 됩니다.

### 2-W. Windows 휠 가드 — fullscreen 휠이 입력창을 헤집는 것 차단 (Windows)

Windows 에는 마우스를 앱에 넘기는 경로가 없습니다(아래 ConPTY 항목 — 앱 마우스 킬스위치는
Windows 에서 금지). 그래서 전체화면 TUI 에 휠을 굴리면 터미널이 그것을 **방향키로 합성해**
앱에 보내고, claude fullscreen 은 그 방향키를 **프롬프트 히스토리 탐색**으로 소비합니다 —
휠 한 번에 입력창이 지나간 프롬프트로 바뀌는 것이 사용자가 겪던 증상입니다.

- 이번 릴리스는 **그 조합에서만** 휠을 소비합니다(그 노치는 스크롤도 방향키도 아닌 무동작 —
  alt 화면엔 스크롤백이 없어 대안이 없습니다). 판정은 "앱이 어떤 마우스 추적 모드를 켰는가"로
  하며, vim `mouse=a` 처럼 휠→방향키가 정상 UX 인 앱은 대상이 아닙니다.
- **적용 범위(정직 고지)**: 가드는 **앱이 마우스 모드를 선언한 뒤**에 걸립니다. 그래서
  ①GUI 를 재시작해 **이미 떠 있던 전체화면 앱에 다시 붙은 pane**(세션 복원·재부착)에서는
  걸리지 않을 수 있고(재부착이 보내는 초기 화면 스냅샷에는 앱의 마우스 모드 선언이 들어 있지
  않습니다), ②전체화면 앱이 **비정상 종료**한 직후에는 판정이 잠시 남을 수 있습니다(그 pane 은
  이미 alt 화면에 갇혀 있으므로 처방은 어느 쪽이든 **pane 을 새로 여는 것**입니다).
  즉 실제 보호 범위는 "**새로 붙인 pane 에서, 앱이 마우스 모드를 선언한 뒤, 전체화면인 동안**"
  이지 "Windows 의 모든 전체화면 휠"이 아닙니다.
- **롤백(끄는 법)** — 아래 중 하나 후 **새 pane**(이미 열린 pane 은 그대로):
  · PowerShell(Windows 기본 셸): `New-Item -ItemType File -Force $HOME\.cys\win-wheel-guard-off`
    (되돌리기 취소 `Remove-Item $HOME\.cys\win-wheel-guard-off`).
    ⚠ `touch` 는 PowerShell·cmd 에 **없는 명령**입니다 — 이전 판 문안이 `touch` 하나만 적어
    Windows 사용자에게는 실행 불가능한 절차였습니다(수정됨).
  · macOS·Linux 셸: `touch ~/.cys/win-wheel-guard-off` (되돌리기 취소 `rm …`).
  · env `CYS_WIN_WHEEL_GUARD_OFF=1` 도 동등하지만 **GUI 프로세스가 상속한 값만** 읽으므로
    `setx` 후 **GUI 재시작**이 필요합니다(파일 게이트는 새 pane 마다 확인 — 재시작 불요).
    릴리스 빌드엔 devtools 가 없으므로 **파일이 Windows 권장 수단**입니다
    (`localStorage.cysWinWheelGuardOff="1"` 은 devtools 가 있는 빌드용).
- ⚠ **기존 정합기 스위치로는 이 가드가 꺼지지 않습니다.** `localStorage.cysMouseReconcilerOff="1"`
  은 macOS 정합기(출력 소비)의 스위치이고, Windows 휠 가드의 스위치는 위의 `win-wheel-guard-off`
  하나뿐입니다. 종전에는 Windows 에 휠 핸들러가 아예 없어 이 구분이 없었습니다.
- ⚠ **이 스위치는 결함을 되살립니다.** 끄면 휠→방향키 합성이 그대로 돌아오므로 claude
  fullscreen 에서 **프롬프트 입력창이 다시 오염될 수 있습니다.** vim 등에서 휠→방향키가 꼭
  필요할 때만 끄십시오.
- ⚠ 이 용도로 `~/.cys/allow-app-mouse`(env `CYS_ALLOW_APP_MOUSE=1`)를 대신 켜지 마세요 —
  그것은 입·출력 양측을 열어 Windows ConPTY 결함(입력창에 `[555;98;34M` 같은 리터럴이
  타이핑되는 현상)을 되살립니다. **휠 억제만** 끄는 전용 스위치가 위의 것입니다.
- 사용자 매뉴얼 정본: `USER-MANUAL.md` §4.6b + 부록 env 표(`CYS_WIN_WHEEL_GUARD_OFF`).

## 알려진 제한 (정직 고지)

- **Windows fullscreen 휠**: **Windows 에서도 claude 가 fullscreen 으로 뜰 수 있습니다.**
  이전 판의 "Windows 는 기본 inline 이라 문제2가 발현하지 않는다"는 서술은 실측으로
  **반증됐습니다** — Claude Code 2.1.233 의 fullscreen 판정에는 순수 Windows→inline 분기가
  없고 Windows 관련 분기는 `Windows ∧ SSH` 하나뿐이며, settings 에 `tui` 키가 없으면 최종
  판정은 서버측 기능 게이트가 합니다. 즉 **OS 가 아니라 계정·롤아웃이 결정합니다**(claude 쪽
  설정을 만진 적이 없어도 fullscreen 이 될 수 있습니다). Windows 에서 마우스 자체를 앱에 넘기는
  경로는 여전히 **비지원**입니다(아래 ConPTY 항목) — 이번 릴리스는 그 상태에서 남는 휠→방향키
  합성 오염 창만 Windows 전용 억제 술어로 막고, 기동 시 감지되면 힌트 1줄을 출력합니다.
  · **대가(정직 고지)**: 억제가 걸린 창에서 그 휠 노치는 스크롤도 방향키도 아닌 **무동작**이
  됩니다(alt 화면엔 스크롤백이 없어 대안이 없습니다).
  · **끄는 법(롤백)**: PowerShell `New-Item -ItemType File -Force $HOME\.cys\win-wheel-guard-off`
  후 새 pane(macOS·Linux 셸은 `touch ~/.cys/win-wheel-guard-off` — `touch` 는 PowerShell 에
  없습니다). env `CYS_WIN_WHEEL_GUARD_OFF=1` 동등이나 **GUI 재시작 후 유효**합니다(파일은 새
  pane 부터 즉시). 릴리스 빌드엔 devtools 가 없어 localStorage 는 탈출구가 되지 못하므로
  **파일을 정본 수단으로 둡니다**. 되돌리기 취소는 그 파일 삭제.
  ⚠ 끄면 위 오염이 그대로 돌아옵니다(**결함 복원 스위치** — 상세는 §2-W).
  ⚠ 이 용도로 `allow-app-mouse` 를 켜지 마세요 — 아래 ConPTY 결함이 되살아납니다.
  · **판정의 한계(정직 고지)**: 억제 대상 판정은 앱이 켜는 마우스 추적 모드(any-motion)로
  하며, 저장소에 vim 계열의 실제 캡처는 **0건**입니다 — 그 모드를 켜는 vim 설정·플러그인
  조합이라면 그 앱의 전체화면 휠도 무동작이 될 수 있습니다(그때가 위 롤백을 쓸 때입니다).
  · **억제 조건은 그 하나뿐입니다**: 초안에 있던 '창 엔진이 휠 노치를 페이지 단위로 보고하면
  앱 종류와 무관하게 무동작' 이라는 **안전 상한은 출고 전에 제거**했습니다. 그 항은 실측
  근거가 0건인데 값을 치르는 대상은 마우스를 요청하지 않는 페이저·에디터(vim·less·man)였고,
  그 피해의 유일한 탈출구가 '가드 전체 끄기'(=결함 복원)뿐이었기 때문입니다. 결과적으로
  **1003(any-motion)을 켜지 않는 앱의 휠은 어떤 환경에서도 종전 그대로**입니다.
  · **inline 로 띄우는 길은 옵트인입니다**: Windows 에서 D5 env
  (`CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`) 주입은 **기본 off** 이고,
  `~/.cys/win-no-alt-screen` 을 만든 뒤 새 pane 을 `cys launch-agent` 로 기동해야 실립니다
  (근거·승격 계획은 §2 의 'Windows 의 D5 는 옵트인' 항목). 즉 **이번 릴리스의 Windows 기본
  방어는 위 휠 가드 하나**이고, 화면 모드는 종전과 같습니다.
- **Windows vim `mouse=a` 비상구 없음**: 앱 마우스 킬스위치(`~/.cys/allow-app-mouse`)는
  Windows 에서 켜면 안 됩니다 — ConPTY 가 마우스 시퀀스를 깨뜨려 입력창에 리터럴이
  타이핑됩니다. 휠은 방향키 합성으로 동작하지만 클릭·드래그를 앱에 넘기는 경로는 없습니다.
- **재attach 시 마우스 모드 미복원**: 전체화면 앱이 떠 있는 pane 을 떼었다 다시 붙이면
  앱 마우스 상태 복원은 이번 범위 밖입니다(단일 attach 세션 내 보증 — 후속 게이트).
  · **따름정리(Windows 휠 가드에도 적용)**: 재부착이 보내는 초기 화면은 화면 내용 스냅샷
  하나뿐이라 마우스 DECSET 도 alt 진입 시퀀스도 다시 실리지 않습니다. 그래서 **GUI 재시작 후
  이미 떠 있던 claude fullscreen 에 다시 붙은 pane 에서는 §2-W 의 가드가 걸리지 않을 수
  있습니다**(앱이 마우스 모드를 다시 선언해야 걸립니다). cys 는 세션 복원이 상시 동선이므로
  이것은 예외가 아니라 흔한 경우입니다 — 그 pane 에서 오염이 보이면 앱을 한 번 나갔다 들어가거나
  pane 을 새로 여십시오. 근본 수리(attach 스냅샷 뒤 모드 재발행)는 macOS 회귀 표면이 커
  이번 범위 밖입니다.
- **ssh 절단 시**: 원격 전체화면 앱이 절단으로 죽으면 마우스 상태가 남을 수 있습니다 —
  `reset`(RIS) 실행으로 복구됩니다(정합기가 RIS 를 소등 전이로 처리).

## ★릴리스 전 Windows 실기 스모크 (태그 전 필수 게이트)

> **왜 게이트인가**: 이번 릴리스는 Windows 전용 코드를 새로 들입니다(휠 가드 · Tauri
> `win_wheel_guard_disabled` 커맨드 · D5 의 Windows **옵트인** 스위치). 자동 검증은 아래 세 레인까지가
> 한계이고, **claude 가 이 env 를 실제로 존중하는가 / vim 이 any-motion 을 켜는가**는 어떤 자동
> 테스트도 답하지 않습니다. 오너 지침("Windows 설치파일
> 업데이트에 신중에 신중을 기하라")에 따라, 아래를 사람이 통과시키기 전에는 태그하지 않습니다.
>
> ★**항목 등급 재조정(2026-08-17 · D5 Windows 옵트인 강등에 따름)**: 아래 B 표의 항목은 두 등급으로
> 나뉩니다. **[태그 전 필수]** = 이번 출고본의 **기본 경로**를 밟는 항목. **[승격 전 필수]** =
> 기본값이 off 라 이번 출고본의 기본 경로에 없는 항목으로, **그 기능을 기본 on 으로 올리기 전에만**
> 요구됩니다. **B-5(D5 env)가 [태그 전 필수] → [승격 전 필수] 로 내려간 것이 이 라운드의 변경**
> 입니다 — 근거는 §2 의 'Windows 의 D5 는 옵트인' 항목이고, 그렇게 되돌린 이유는 조건을 건너뛰기
> 위해서가 아니라 **조건이 걸린 변경 자체를 기본값에서 빼서** Windows 기본 동작을 이전 출고본과
> 동일하게(회귀 0) 만들었기 때문입니다.

**A. 자동 (CI) — 이번 라운드에 추가됨**

1. ★**태그 전에 사람이 1회 눌러야 하는 항목**(빠뜨리면 아래 2·3 은 이 핀을 대신하지 못합니다):
   GitHub Actions → `windows-health` → **Run workflow**(ref = 릴리스 브랜치) → 그 잡의
   **`cargo test --bin cys d5_env_injection` 스텝이 존재하고 초록**인지 확인.
   이 스텝은 `#[cfg(windows)]` 파이프라인 핀을 이 저장소에서 **처음으로 Windows 컴파일·실행**
   합니다 — 그전까지 그 블록은 한 번도 컴파일된 적이 없습니다(문법·타입 오류조차 여기서 처음
   드러납니다). `windows-health.yml` 은 `feat/**` push 와 `workflow_dispatch` 로만 돌기 때문에
   릴리스 브랜치 push 로는 **자동으로 돌지 않습니다**.
   · 그 핀은 강등에 맞춰 **두 행**을 고정합니다: ⓐ기본(미옵트인) = create env 맵에 D5 키 **없음**
     ⓑ옵트인 = `"1"` 실림. 즉 이 잡은 '이번 출고본의 Windows 기본 동작이 강등 전과 같다'를
     Windows 실기 컴파일로 증명하는 자리이기도 합니다.
   · 실패가 D5 관련이면 처방은 아래 **C** 의 5번과 같습니다(이제 '되돌리기'가 아니라 '옵트인
     경로 수리 또는 스위치 자체 제거' 입니다 — 기본 경로는 이미 무장 해제돼 있습니다).
   · 실패가 하네스 무관 사유(최초 Windows 컴파일에서 나오는 타 모듈 오류)면 그 자리에서 고치고
     로컬 게이트부터 다시 돌립니다. **어느 쪽이든 이 잡이 초록이기 전에는 태그하지 않습니다.**
2. `release.yml` Windows 레그: `cargo test --lib factory_reset::` **+ `cargo test --lib claude_alt_screen`**
   (D5 의 OS × 옵트인 매핑 핀 — `windows ∧ 미옵트인 = 미주입` 행을 포함합니다. 태그 push 로
   자동 실행 — 즉 **태그 후에야** 결과를 봅니다).
   · 강등의 부수 효과: 이 Windows 스텝은 이제 래퍼 배선의 **감시력이 있습니다**. 러너에는 옵트인
     스위치가 없으므로 게이트가 거짓이고, 누가 래퍼의 게이트 인자를 `true` 로 하드코딩하면
     이 스텝이 빨개집니다(강등 전에는 mac·Windows 두 레인 모두 게이트가 참이라 그 변이가
     어느 레인에서도 죽지 않았습니다).
   · 이 필터는 **테스트 2건**을 집습니다(2026-08-17 적대검증 2R 수리로 1건 추가):
     `claude_alt_screen_env_injection_pins`(OS × 옵트인 매핑·삽입 규칙)과
     `claude_alt_screen_win_opt_in_reader_pins`(**옵트인 판독기의 기본값이 거짓인가**).
     후자가 없던 동안에는 판독기의 기본값이 참으로 퇴행해도 mac·Windows 어느 레인도 빨개지지
     않았습니다(그 축의 유일한 감시선이 수동 B-5 하나였습니다). 이름에 `claude_alt_screen` 을
     넣은 것은 이 필터에 걸리게 하기 위한 의도이니, 개명 시 이 레인을 함께 확인하십시오.
3. `release.yml` Windows 레그의 `cd ui && bun test` 는 `if:` 가 없어 Windows 러너에서도 전건
   실행됩니다(휠 가드 술어·배선 핀·정합기 출력 파리티 핀 포함).

**B. 수동 실기 — 사람이 Windows 기계에서 6항** (등급은 위 '항목 등급 재조정' 참조)

| # | 등급 | 항목 | 통과 기준 |
|---|---|---|---|
| 1 | **태그 전 필수** | 새 pane + claude fullscreen 에서 휠 굴리기 | 휠 무동작 · **프롬프트 입력창이 바뀌지 않음** |

검증하는 D5 env 가 기본값에서 빠졌기 때문입니다. 대신 **기본 on 승격의 유일한 해제 조건**으로
남습니다 — B-5 를 1회 통과시키면 `src/lib.rs` 의 `d5_gate_for_os` 한 줄
(`"windows" => win_opt_in,` → `"windows" => true,`)로 승격하고, 그 함수 doc 의 동반 개정 목록
(핀 2곳 · USER-MANUAL env 표 · 이 문서)을 함께 처리합니다.
그 대신 **B-5-b 가 태그 전 필수로 새로 들어왔습니다**: 강등이 실제로 기본 경로를 비웠는지를
사람이 한 번 확인하는 항목입니다(자동 레인의 ⓐ행과 같은 주장을 실기에서 재확인).

추가 관찰(장시간): 옵트인한 pane 은 Windows 데몬이 mac 과 같은 inline 재드로우 볼륨을 받습니다 —
pane 1개를 오래 켜 두고 CPU·recall DB 증가가 종전과 다르지 않은지 봅니다(옵트인하지 않은 기본
경로에는 해당 없음 — 화면 모드가 종전과 같습니다).

**C. 실패 시 처방**: 1 이 실패(오염 재현)하면 판별자를 넓혀야 하므로 **가드 자체를 재설계**해야
합니다. 2·3 이 실패(휠 무동작)하면 그 앱이 any-motion(1003)을 켠다는 뜻이므로 판별자 오판이
확정입니다 — 우선 §2-W 의 롤백 파일로 사용자 탈출구를 안내하고, 다음 라운드에서 그 앱의 실제
DECSET 을 캡처해 술어를 좁힙니다(그 캡처가 저장소의 첫 vim 실측이 됩니다).
**5 가 실패하면 태그는 그대로 진행하고 승격만 보류합니다** — 그 경로는 이미 기본값에서 빠져 있어
사용자에게 도달하지 않기 때문입니다(옵트인한 사용자는 스위치 파일을 지우면 즉시 복귀). 다음
라운드에서 옵트인 경로를 수리하거나, 수리 가망이 없으면 스위치 자체를 제거하고 Windows 는 UI 휠
가드 단독 방어로 확정합니다.
**5-b 가 실패하면(= 옵트인하지 않았는데 env 가 실렸거나 pane 이 죽으면) 태그를 멈춥니다** —
강등이 코드에서 실제로 이뤄지지 않았다는 뜻이므로, `src/lib.rs` 의 `d5_gate_for_os` 가
`"windows" => win_opt_in,` 인지부터 확인하십시오(그 회귀는 mac 호스트에서도
`cargo test --lib claude_alt_screen` 이 즉시 잡습니다).

## Windows Defender / SmartScreen 안내 (유지)

Windows 설치 파일은 코드 서명 평판이 쌓이기 전까지 SmartScreen 경고("알 수 없는
게시자")가 뜰 수 있습니다. **"추가 정보" → "실행"** 으로 진행하시고, 다운로드한 파일은
홈페이지의 `SHA256SUMS.txt` 와 대조해 무결성을 확인할 수 있습니다. Defender 오탐은 WDSI
신고를 거쳐 릴리스마다 최소화합니다.
