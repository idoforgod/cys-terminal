# v0.14.41 — 화면이 사실대로 말하고, 지시가 한 번만 도착하고, 대표 자리는 제자리를 지킵니다

오너가 직접 올린 18개 항목(U1~U18)을 고친 판입니다. 한 문장으로 줄이면 이렇습니다 —
**사용량·업데이트·빈 자리 같은 화면 표시가 실제와 다르게 보이던 자리들을 정직하게 고치고,
팀원 자리에 지시가 두 번 겹쳐 붙어 뒤 지시가 막히던 사고(가장 심각했던 것)를 닫고, 대표(master)
자리가 재부팅·업데이트 뒤에도 제 칸을 지키게 했습니다.**

> ### ★ 먼저 하실 것 — 지침 병합 (`cys pack-merge`)
>
> 이번 판은 **사용자 소유(user-owned) 파일**을 고칩니다 — `directives/WORKER_DIRECTIVE.md` ·
> `directives/REVIEWER_DIRECTIVE.md` · `directives/MASTER_DIRECTIVE.md`. 이 등급은 매니페스트
> 해시가 맞아도, `--force` 여도 기존 설치에 **덮이지 않습니다** — 신버전이 `<파일>.new` 로
> 나란히 도착할 뿐입니다. 기존에 쓰시던 분은 아래를 한 번 돌려 주셔야 새 내용(팀원 착수 게이트 ·
> "말로 팀 만들기" 절차)이 발효됩니다.
>
> ```
> cys pack-merge                                                   # 병합 대기 목록
> cys pack-merge --file directives/WORKER_DIRECTIVE.md --take-new  # 손대지 않으신 파일
> cys pack-merge --file directives/MASTER_DIRECTIVE.md --keep-mine # 또는 3-way
> ```
>
> `directives/CEO_TEMPLATE.md` 도 이번 판에서 내용이 바뀌었지만(§4-A "말로 팀 만들기" 절 추가),
> 이 파일은 **시스템 소유**라 위 세 파일과 달리 병합 없이 **자동으로** 갱신됩니다. 다만 이미
> 대표(master)에서 CEO 로 승격된 기계는 로컬 `MASTER_DIRECTIVE.md` 가 (User 소유로) 그 순간의
> `CEO_TEMPLATE.md` 사본이 되어 있어서, 새 `CEO_TEMPLATE.md` 내용이 그 기계에 실제로 반영되는
> 시점은 **다음 부서 기동 때의 재승격 재주입(`_swap`)** 입니다 — 아래 「11. 알려진 잔여」와
> 「20. 이관 주의」에 그 1회성 동작을 자세히 적었습니다.
>
> 이 판의 팩 하한(`PACK_MIN_BINARY`)은 **0.14.31 → 0.14.41 로 올렸습니다**(9절 참고). 이 노트의

## 2. U2·U3 — 대표(master) 자리가 재부팅·업데이트 뒤에도 제 칸을 지킵니다

**무엇이 잘못돼 있었나.**

- **U3**: 새 좌석을 만들 때마다 "화면 전체의 오른쪽 절반"에 반씩 붙이는 규칙이었습니다. 그래서
  좌석이 하나 늘 때마다 대표 칸이 1/2 → 1/4 → 1/8 로 계속 줄었습니다. 「정렬」 버튼은 전체를
  N등분해 버려 대표 칸이 다른 칸과 같은 크기가 됐습니다.
- **U2**: 화면 배치가 좌석을 "번호(sid)"로만 기억했습니다. 재부팅·업데이트로 데몬이 다시 뜨면
  번호가 뒤바뀌어, 새로 뜬 창이 생성된 순서대로 무작위하게 오른쪽에 붙었습니다 — 대표가 있던
  칸에 다른 좌석이 들어가고, 대표는 엉뚱한 자리에 새로 생겼습니다.

**고친 것.**

- 좌석 배치 규칙을 순수 함수 하나(`ui/src/seatlayout.ts`)로 모았습니다. 대표 칸(master ·
  cso · cso-N)은 화면 왼쪽 **1/3 고정**, 나머지 좌석들은 오른쪽 2/3 를 균등하게 나눠 씁니다.
- 화면 칸에 "역할(role)"을 함께 기억시켰습니다. 재부팅 뒤 새로 뜨는 창은 먼저 "같은 역할이
  있던 칸"에 결속되고, 그 다음에야 배치 규칙이 적용됩니다. 그래서 대표가 다시 뜨면 항상 그
  자리로 돌아옵니다.
- 대표 좌석이 잠깐 죽으면 그 칸이 즉시 사라지지 않고 "대표(master) 자리 — 복원을 기다리는
  중입니다"라는 안내와 [새 셸 열기]/[칸 비우기] 버튼으로 남습니다(맥 240초 · 윈도우 480초
  대기). 그 시간 안에 대표가 다시 뜨면 같은 칸·같은 비율로 이어집니다.
- 예전 방식으로 저장된 화면(1/4·1/8로 눌린 배치)도 이번 판을 받으면 기동하자마자 자동으로
  1/3 로 교정됩니다. 사용자가 직접 드래그로 비율을 조정한 화면은(수동 표식) 건드리지 않습니다.

**정직하게.** 실기 재부팅·업데이트 E2E(맥·윈도우)는 GUI 자동화 금지 규약 때문에 실제 화면으로
확인하지 못했습니다. 가짜 백엔드를 붙여 헤드리스 브라우저로 실제 렌더는 확인했고(통합 성찰
§18), 순수 배치 로직은 6석 720가지 순열 전수 테스트로 검증했습니다. **업데이트 직후 첫 기동은
역할 기억이 비어 있어 표준 배치(대표 왼쪽 1/3)로 시작합니다 — 원래 칸으로 돌아오는 것은
두 번째 재부팅부터입니다**(아래 §20-3 참고).

## 3. U1 — 사이드바에 사용량이 보입니다

**무엇이 잘못돼 있었나.** 5시간·7일 사용률은 Control Center 를 열어야만 보였습니다. 평소
작업 중에는 얼마나 남았는지 알 방법이 없었습니다.

**고친 것.** 사이드바 바닥에 사용량 패널을 새로 넣었습니다(주 계정의 5h·7d 퍼센트 · 게이지 ·
리셋 시각). 기존에 쓰던 조회 함수를 그대로 재사용했고, 30초에 한 번 · 사이드바가 이미 도는
10초 틱 끝에 곁다리로 붙였습니다(새 타이머 0개). 100% 초과·정보 없음·리셋 지남·데몬 응답
없음도 숨기지 않고 정직하게 표시합니다. 다른 계정이 여럿이면 최대 4개까지 한 줄씩 보이고
나머지는 "외 N개"로 접힙니다. 라벨(어느 계정인지)은 이메일이 아니라 프로필 이름으로 보이고,
이메일은 마우스를 올렸을 때만 나오며 Control Center 의 🔒 가림 설정을 그대로 따릅니다.

**정직하게.** 기본 프로필(`~/.claude`)에서 낸 사용량은 이번 집계에 잡히지 않습니다(사이드바
툴팁에 그 범위를 적어 뒀습니다). 🔒 가림을 켜도 계정 라벨 자체(설정 폴더 이름)는 그대로
보입니다 — 이메일만 가려집니다. 다음 판 과제로 남겼습니다.

**무엇이 잘못돼 있었나.** ＋부서 단추가 사이드바 머리줄에 있어 오클릭하기 쉬웠고, 누르면

**고친 것.** ＋부서 단추를 없애고, 사이드바 바닥의 "전문가용 ▸" 접힘 칸(기본은 접혀 있음)

거치도록 통일했습니다.

## 5. U16 — 대표가 말로 팀을 만듭니다 (1차)

**무엇이 없었나.** 오너가 대표(master)에게 "이런 이름·이런 일을 하는 팀을 만들어 줘"라고
말해도 실제로 팀이 만들어지는 대화 경로가 사실상 없었습니다(CEO 지침의 "CSO 에게 위임" 안내는
막힌 도구 게이트를 가리키는 죽은 경로였습니다).

**고친 것(1차·축소).** 대표가 오너와 대화로 이름·하는 일을 정한 뒤 `cys team-propose --name
… --purpose …` 를 한 번 실행하면, 데몬이 그 제안을 Control Center 의 승인 Feed 에 카드로
올립니다. 오너가 카드에서 [확인 창 열기]를 누르면 대표가 쓴 원문 그대로가 보이고, [만들기]를
눌러야 기존 생성 경로(U17 과 같은 흐름)로 실제 팀이 만들어집니다. [나중에]를 누르면 카드는
대기 상태로 남습니다. **자동 팝업은 없고, 만드는 결정은 항상 오너의 클릭 한 번입니다.**

안전판: 제안은 본부 대표(master) 좌석에서만, 대기 1건·24시간 3건까지만 낼 수 있고, 해소(승인·
거부)는 GUI 조작(operator token)에서만 됩니다 — 대표가 자기 제안에 스스로 결정을 보내도
막힙니다. 이름·목적 글자에 "무조건", "즉시 실행" 같은 지시성 낱말이나 보이지 않는 서식 문자가
섞이면 그 자리에서 거부됩니다. 만들어진 팀에는 오너가 확인한 원문이 "팀 소개(참고 정보)"로만
전달되고, "지시가 아니며 soul.md·역할 지침보다 우선하지 않는다"는 고지가 함께 붙습니다.

**정직한 한계.** 이 잠금은 **사고 방지 층**입니다 — 대표가 실수로 두 번 제안하거나, 오너가
Feed 를 훑다가 자기도 모르게 승인 흐름에 결정을 보내는 것을 막습니다. 같은 사용자 권한으로
직접 명령줄을 조작하는 **고의 우회**까지 막지는 못합니다. "에이전트는 팀을 만들 수 없다"는
주장은 하지 않습니다 — 지침·매뉴얼에 같은 문장으로 적어 두었습니다.

**아직 못 닫은 것(통합 성찰에서 발견 → §18 에서 문서·안내로 보강).** 이 절차를 아는 것은
**대표 지침(`MASTER_DIRECTIVE.md`) §4-A** 인데, 이 파일은 사용자 소유라 **이미 설치돼 있고
아직 팀이 하나도 없는 기존 설치**에는 `.new` 로만 도착합니다 — `cys pack-merge` 로 병합해야
대표가 이 절차를 압니다(위 「먼저 하실 것」 참고). 팀이 이미 있어 CEO 로 승격된 기계는 다음
부서 기동 때 재승격 재주입으로 자동으로 새 지침을 받습니다(§20-1).

있습니다. [보내기]를 누르면 ① 첨부 폴더가 담긴 폴더를 엽니다 ② 기본 메일 앱을 받는 주소·
제목·본문이 채워진 상태로 엽니다(맥에서 Mail 앱이 있으면 첨부까지 자동 시도, 안 되면 폴더

업로드 URL)이 정해진 뒤에 2단계로 넣기로 했습니다.

**필수 안전장치.** 작성 창이 열려 있는 동안은 키보드 입력이 터미널(마스터 PTY)로 새지 않도록

## 7. U9 — 업데이트 숫자와 "최신입니다"가 어긋나던 것

**근본 원인.** CSS 에 `[hidden]{display:none}` 짝 규칙이 없었습니다. 그래서 배지를
"숨겨라"라고 코드가 지시해도 화면에는 계속 보였습니다 — 이 결함 때문에 **Control Center 의
승인 대기 빨간 배지가 "0건"인 상태로도 Update 버튼 옆에 상시 떠 있었습니다.** 배지에 뜨는
숫자(경보)와 실제로 눌렀을 때 나오는 결과("할 일 없음")가 서로 다른 곳을 보고 있었던 것도
같은 계열 결함이었습니다 — 배지는 하나의 지표를, 클릭했을 때 뜨는 창은 다른 지표를 읽고
있었습니다.

**고친 것.** `.badge[hidden]{display:none}` 짝 규칙을 넣어 숨김이 실제로 동작하게 했습니다
— **승인 대기 0건이면 이제 빨간 0이 사라집니다.** 배지·클릭 시 뜨는 상태 창·토스트가 전부
하나의 상태값(`UpdateState`)에서 파생되도록 통일했습니다. 상태 창을 열면 본체·팩 각각의
현재→새 버전, 실패 사유, 설치 버튼, 마지막 확인 시각이 보입니다. "최신입니다"는 본체·팩
**두 확인이 모두 성공했을 때만** 뜹니다 — 하나라도 확인에 실패했으면 "?"(확인 불가)로
정직하게 남습니다.

**오너 고지.** 최신 표시 기호가 `0`(숫자)에서 `✓`(체크)로 바뀌었습니다 — 2026-07-03 에
지시하신 "숨김 대신 0" 의 글자와는 다릅니다. 다만 그 지시의 목적("확인 전"과 "확인했고
0건"을 구별)은 숨김/…(확인 중) 대 ✓(확인 끝) 로 그대로 유지됩니다.

**통합 성찰에서 추가로 잡은 것.** pro 채널 설치 사용자가 공개(무료) 팩이 자신의 버전과 같거나
더 낮은데도 빨간 "!" 와 "업데이트가 있다"는 거짓 경보를 보는 회귀가 있었습니다(수정 과정에서
새로 생겼다가 같은 라운드에서 잡힘) — 버전 비교를 채널 검사보다 먼저 하도록 순서를 바꾸고,
색도 빨강 대신 호박색으로 낮췄습니다.

## 10. U5 — 윈도우에서 "1분마다 검은 창"이 번쩍이던 것

**고친 것.** 위 3곳에 창 숨김 정책을 걸고, 1분 주기 캡처 전용 호출(화면에 보여줄 필요가 없는
호출)에만 윈도우의 "창 없이 실행" 플래그를 추가했습니다. 사람이 보는 터미널 화면(ConPTY 자식)

자체가 안 뜨는 사고(④ pane 전멸)로 이어질 수 있기 때문입니다. 앞으로 같은 실수(콘솔 없는
프로세스가 창 정책 없이 자식을 띄우는 것)가 재발하면 새 검사(census)가 자동으로 잡습니다.

**정직하게 — 원인 확정은 아직입니다.** 이번 조사 자체가 "현재 1분 잡의 공식 규칙상으로는
창이 뜨지 않아야 한다"는 결론이었습니다. 즉 이번 수정은 **가장 유력한 후보 경로들을 차단**한
것이지, 실기 윈도우에서 "정말 이게 원인이었다"를 확인한 것은 아닙니다. 오너의 윈도우 실기
확인이 필요합니다(§21).

## 11. U10 — 켤 때마다 승인 알림이 쌓이던 것

## 12. U8 — 지시가 붙기만 하고 실행되지 않던 것 (가장 심각한 원인)

오너가 이번 18개 항목 중 가장 무겁게 보신 증상입니다. 팀원 자리 화면에 지시가 올라오긴
하는데 실제로 실행되지 않는 문제였습니다. **실제 좌석 대화 기록 473건을 전수 대조한 결과,
Claude 의 이상 동작이 아니라 cys 자신의 버그가 주범으로 확정됐습니다.**

**주범(P0-M1) — 지침이 한 좌석에 두 번 따로 제출됩니다.** 사이클·복원 재주입 로직이 지침
전문(약 58KB)과 `[RESUME]` 표식을 **두 번 나눠서** 제출했습니다. 두 번째 제출이 Claude 의
입력 큐 맨 앞으로 끼어들어 턴 중에는 접히지 않고, 그 뒤에 오는 부서장의 실제 지시가 최대
7~17분 동안 그 뒤에 막혔습니다. **고친 것**: 이미 쓰던 "한 제출" 규약(`adoption_payload`)
하나로 4개 제출 지점을 전부 합쳤습니다 — 지침과 이어지는 지시가 한 번에 도착합니다.

**부트 체인 재주입 폭주(P0-M2) — 확정된 원인.** 각성 확인 핑을 Claude 가 아직 처리하지 못한
채 큐에 대기시켜 놓으면, 데몬이 이를 "응답 없음"으로 오판해 지침 전문(58KB)을 반복 재주입했습니다.
**2026-09-23 실측으로 워커 좌석 +2회·CEO 좌석 +3회 재주입이 확인됐고, 그 결과 5분 만에 컨텍스트
사용량 64%에 도달해 강제 정리(clear)가 발동했습니다.** 고친 것: 핑이 큐에 실제로 들어간 것이
관측되면 "전달됨·바쁨"으로 판단해 재주입을 멈춥니다. 판정이 불가능하면 — 재주입하지 않고
보고합니다(안전한 쪽). 재주입 자체도 좌석·세션마다 파일 기반의 원자적 잠금으로 **한 번만**
나가도록 상한을 걸었습니다.

**추가 안전판(P1) — 승인·선택 창이 떠 있는 화면에는 본문 텍스트를 쓰지 않습니다.** 질문·선택
창이 열려 있는데 지시 텍스트를 바로 쓰면 그 창의 아무 선택지나 눌리는 사고로 이어질 수
있습니다. 이제 그 경우 텍스트는 큐로 넘어가 창이 닫힌 뒤 배달됩니다. Return(제출) 키·강제
Clear 키는 이 안전판 밖입니다 — 승인 대기 중에도 Return 은 여전히 갈 수 있고, 사이클의
`/clear` 도 그대로 보존됩니다.

**축소·제외한 것.** 사람이 입력줄에 쓰다 만 글자가 있는 상태에서 기계가 자동으로 눌러
제출시켜 사람 문장과 기계 문장이 붙어버리는 문제(P2, `machine_draft` 개념)는 **이번 판에서
손대지 않았습니다** — 이 경로는 과거에 실제로 사고(RC1·RC3)가 났던 자리라, "안전하면"이라는
조건부 우선순위에 비해 새 위험을 감수할 이유가 부족하다고 판단했습니다. 자동 재누름 루프,
괄호 붙임 입력 처리, 에코 적응 간격 등도 설계 단계에서 이미 제외 목록에 있었습니다.

## 13. U7 — 폴더 신뢰 창 (오너 질문에 대한 답)

**오너 질문**: "팀원별 폴더를 쓰면 이 신뢰 확인 창이 없어지는 것 아니었나?"

파일에 그 작업 폴더가 신뢰 기록으로 적혀 있는가**로 결정됩니다. 맥에서는 홈 폴더가 이미
신뢰된 상태로 시드되기 때문에 대체로 창이 안 뜹니다. **윈도우는 다릅니다** — 사전에 등록해
둔 키의 표기(`C:\...`, 백슬래시)와 Claude Code 가 실제로 읽는 키의 표기(`C:/...`, 슬래시)가
서로 달라서, 신뢰를 미리 시드해도 Claude 가 그것을 "신뢰 기록 없음"으로 읽고 창을 다시
띄웁니다.

**고친 것.** 윈도우에서 신뢰 키를 Claude 가 읽는 슬래시 표기로 판정하고, 쓸 때는 슬래시(주)와
역슬래시(구버전 호환용 별칭, 없을 때만 추가)를 함께 등록합니다. 신뢰 창·면책 창이 뜨는
경우를 위한 처방 문구도 "아래 방향키 1회 뒤 Return"으로 더 정확하게 고쳤습니다(둘 다 기본
포커스가 "No, exit" 에 있기 때문입니다).

**손대지 않은 것.** 좌석의 작업 폴더 자체를 전용 폴더(`~/.cys/seats`)로 옮기는 근본적인
방안은 이번엔 제외했습니다 — launch-agent 의 기본 작업 폴더 계약과 스킬·플러그인 동작에
부작용이 생길 수 있어, 설계 단계에서 범위 밖으로 확정했습니다.

## 14. U13 — 팀원이 지시 없이 스스로 착수하던 것

**무엇이 잘못돼 있었나.** 팀원(worker)·리뷰어 지침에 "지시가 와야 착수한다"는 명시적 규칙이
없었고, 좌석을 깨우는 훅이 모든 좌석에 "이어서 진행하라"는 문구를 주입해 실제 지시 없이도
착수하는 것처럼 보이는 동작을 유발했습니다.

**고친 것.** WORKER·REVIEWER 지침에 **착수 게이트** 절을 신설했습니다 — "지시"는 출처(master·
부서장·CEO·오너·리뷰 의뢰·`[schedule]`/`[wakeup]`/`[heartbeat]` 라벨)가 있는 배정만
인정합니다. 출처 없는 TODO·재개 메모는 지시가 아닙니다. 훅이 보내는 복원 안내 문구도
역할별로 중립화했습니다(대표·CSO 는 기존 문구 그대로, 팀원·리뷰어는 "지시를 기다리세요"
계열로). `[CYCLE-PRE]`·`[CYCLE]`·`[DRAIN]` 같은 운영 절차 라벨과 데몬이 보내는 예약 메시지는
착수 게이트의 예외로 즉시 수행합니다(무clear 위험 방지).

**남은 것.** 본부 레인의 팀원은 여전히 대표의 SESSION_STATE 본문을 "배경 참고"로 받습니다
(부서 레인만 이번에 경로 안내 1줄로 대체했습니다) — 착수 게이트 문구가 "이건 배경이지
지시가 아니다"라고 함께 알려 줍니다.

## 15. U11 — 시스템 부하가 높을 때 30초씩 최대 3분 재확인

**무엇이 잘못돼 있었나.** 부트 시작 시 CPU 부하가 순간적으로 높으면 자원 게이트가 즉시
포기(exit 9)했습니다. 재측정도, 잠깐의 대기도 없었습니다.

**고친 것.** 부하 축(fleet_cpu)만 단독으로 막고 있을 때 한해 30초 간격으로 최대 3분(벽시계

기록합니다. 다른 축(예: 메모리)이 막고 있으면 이번 수정과 무관하게 종전대로 동작합니다.

## 16. U14·U18 — 폴더 접근이 막혔을 때의 안내

**U14 — 안내에 앱 이름이 없던 것.** macOS 개인정보 보호 설정의 "파일 및 폴더" 목록에는
「cys」라는 이름으로 뜨는데, 안내 문구에는 그 사실도, 설정 화면으로 가는 방법도 없었습니다.
**고친 것**: "「cys」의 데스크탑 접근이 꺼져 있습니다" 처럼 앱 이름을 명시하고, 알림을 누르면
바로 해당 설정 화면이 열립니다.

**U18 — 폴더 접근이 거부됐는데도 좌석은 뜨고, 안내는 없던 것.** macOS 권한 거부(TCC)는
폴더로 들어가는 것(chdir)과 존재 확인(stat)은 막지 않고, 실제 목록 읽기·파일 열기만 막습니다
— 그래서 좌석은 정상적으로 뜨지만 그 안의 에이전트는 폴더를 읽지 못합니다. 사전 판정도,
사용자 안내도 없었습니다. **고친 것**: 역할이 있는 좌석을 만들 때(맥 한정) 그 폴더를 읽을 수
있는지 짧게(최대 1.5초) 관측해 막혀 있으면 화면에 알리고, 그 좌석의 첫 화면에도 "이 폴더를
시작 시 읽지 못했다"는 1줄을 고지합니다(그 고지를 사람에게 자발적으로 보고하거나 다른 곳에
대신 저장하지 말라는 규칙과 함께).

두 안내 모두 실제 macOS 권한 거부 기기에서 재현하지 않고 `sandbox-exec` 로 같은 방식(파일
읽기 거부)을 흉내 낸 실험으로 검증했습니다(§21).

## 17. U15 — 개발자 도구(Xcode Command Line Tools) 없는 맥의 설치 창

**무엇이 잘못돼 있었나.** macOS 는 CLT 가 없는 상태에서 `/usr/bin/python3` 같은 도구를
처음 실행하면 "설치할까요?" 창을 띄웁니다. 좌석·훅·부트 자식 프로세스의 PATH 에서 이
셔임(shim) 이 동봉 python 보다 먼저 잡히는 경로가 여럿 있어서, CLT 가 없는 맥에서는 부트
체인이 도는 중간중간 이 창이 계속 튀어나올 수 있었습니다.

**고친 것(1단계).** CLT 부재를 셔임을 **직접 실행하지 않고** 파일 존재만으로 판정한 뒤(개발자
디렉터리 → xcode-select 링크 → Xcode.app → CLT 순서), CLT 가 없을 때만 부트 감독·훅·회수
경로에서 동봉된 python 을 PATH 맨 앞에 세웁니다. CLT 가 있는 맥은 바이트 단위로 동작이
그대로입니다.

**손대지 않은 것.** 에이전트(Claude)가 Bash 도구로 직접 `python3`·`git` 을 치는 경우와,
Claude Code 자신이 내부적으로 git 을 확인하는 경우는 여전히 셔임을 부를 수 있습니다 — 이
경로(에이전트 Bash 환경변수 주입)와 git 동봉 전환은 이번 설계 범위 밖으로 확정됐습니다. 안내
문구가 이 한계를 정직하게 알립니다.
