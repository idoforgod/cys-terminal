# v0.14.43 — 큐가 막혀도 이유와 처방이 보이고, 로그인을 바꾸면 옛 계정이 내려가고, 팀 만들기와 업데이트가 말을 합니다

다섯 갈래를 한 판에 묶었습니다. 한 문장으로 줄이면 이렇습니다 —
**좌석 큐가 몇 시간 막혀도 아무도 몰랐던 것을 화면 알림·처방 코드·사유 파일로 드러냈고(입력 추천이 떠 있을 때 빈 입력줄의 Esc 한 번이 큐를 멈춰 세우던 결함도 고쳤고),
다른 계정으로 다시 로그인하면 옛 계정이 주 계정과 한도 경보에 남던 것을 정리했고(별명·`● 사용 중`·오래됨·숨기기), 「팀 직접 만들기」가 경과와 단계를 말하게 했고,
업데이트가 설치되지 않았을 때 알려 주고, 데몬 로그를 채우던 거짓 'critical' 줄을 없앴습니다.** 이번 판은 역할 지침(CSO·MASTER·CEO_TEMPLATE)의 크기를 **늘리지 않는다**는 규칙으로
문서 작업을 했고, 측정하지 못한 것(윈도우 실기 · 실제 화면 · 지침 축소의 실제 효과)은 §13·§14 에 숨기지 않고 적었습니다.

그 뒤 같은 판에 다섯 가지를 더했습니다 — 윈도우 11 의 스마트 앱 컨트롤 때문에 말없이 닫히던 업데이트를 GitHub Actions 의 Windows 11 러너에서 실측하고 막히면 즉시 알리게 한 것(§6-1), 스케줄이 직접 보낸 글이 제출됐을 때 입력줄 계수를 0 으로 계상하는 것(§2-1), 좌석 밖에서 보낸 메시지에 발신 표시를 다는 것(§7-1), 데몬을 켤 때 선언 계정 파일을 막히지 않게 읽는 것(§3), NPU 전력 표시가 비공개 라이브러리에 묶여 있던 것을 풀어 앞으로의 macOS 에서 데몬이 못 뜰 위험을 없앤 것(§7-2).

> ### ★ 먼저 하실 것 — 지침 병합 (`cys pack-merge`)
>
> 이번 판도 **사용자 소유(user-owned) 지침 두 개**를 고칩니다 — `directives/MASTER_DIRECTIVE.md` 와 `directives/CSO_DIRECTIVE.md`. 디렉티브(`*_DIRECTIVE.md`)는 사용자 소유 등급이라
> 기존 설치에 **덮이지 않고** `<파일>.new` 로 나란히 도착하므로, 한 번 병합해 주셔야 새 문안이 발효됩니다. 무엇이 바뀌었는지(직접 고치신 분이 3-way 로 합치실 때 보실 것):
>
> - **`MASTER_DIRECTIVE.md`**: ① 부서장의 `--detach` 사이클 문단을 줄였습니다(1,972 → 1,337 B — 지시 조항 10개는 그대로) ② `queue.starved` 대응 문장: `CYS_QUEUE_STARVE_ALERT_SECS` 기본을 "0=비활성"이라 잘못 적던 것을 **600초**로 정정하고,
>   종전의 "대응은 원인 해소(연속 출력·사람 입력·queue pause)다" 를 경보 요약의 처방 코드(`remedy=<코드>` · 코드가 없으면 같은 요약의 `blocked_by`)를 사람에게 그대로 전달하라는 문장으로 바꾸고, LLM 에이전트는 자동 조치(강제 배달·드레인·키 주입·동결 해제·항목 삭제)를 하지 않는다고 적었습니다 — 종전의 "사람 운영자 전용" 단정은 그대로 두고 `depth_high` 와 겹쳐도 같다고 덧붙였습니다 ③ 군말 한 곳('수신 시 해당' 의 '해당')을 걷었습니다('(Return 한정 큐잉)' 은 제약 고지라 남겼습니다).
> - **`CSO_DIRECTIVE.md`**: ① 같은 `queue.starved` 행(기본값 정정 · 종전의 "원인을 해소하거나 master 보고" 를 처방 코드(없으면 `blocked_by`)를 master·오너(사람)에게 그대로 전달하라는 문장으로, "자동 강제배달 금지" 를 위 MASTER 와 같은 자동 조치 금지 목록으로 바꾸되 "사람 운영자 전용"(`depth_high` 와 겹쳐도)은 남기고 "경보는 발행뿐" 괄호만 걷음) ② 한도 경보 본문이 `in_use=0 ∧ age>1800` 또는 `reset<0` 이면 신규 작업 제한 판단의 근거로 쓰지 말고 `cys status --json` 의 `alert_eligible` 로 다시 확인하라는 **한 줄**(오너 결재 문면 그대로 — 그 조건의 경보는 데몬이 이미 걸러 냅니다, §4) ③ 사유 설명 한 문장과 개정 근거 주석의 군말 정리(지시 내용 변화 없음).
> - `directives/CEO_TEMPLATE.md` 는 시스템 소유라 병합 없이 자동 갱신됩니다(MASTER 와 같은 바이트를 생성기로 다시 합성). 이미 CEO 로 승격된 설치(`directives/MASTER_DIRECTIVE.md.pre-ceo` 가 있는 설치)는 `MASTER_DIRECTIVE.md` 를 병합하지 않아도 됩니다 — 다음 부서를 켤 때 새 템플릿으로 다시 승격·재주입되고(0.14.42 와 같은 방식) 기존 '승격 드리프트' 안내가 뜰 수 있습니다. 그런 설치에서는 아래 `--take-new` 가 거부됩니다(승격본을 덮어쓰지 않으려는 안전장치 — `--force-vendor` 는 승격 파괴 승인이라 쓰지 마십시오). 대기 중인 `.new` 를 정리하고 싶으면 도구가 안내하는 순서대로 하십시오: 먼저 `MASTER_DIRECTIVE.md.new` 를 `MASTER_DIRECTIVE.md.pre-ceo` 로 복사한 다음 `--keep-mine`(순서를 바꾸면 안 됩니다).
>   승격 전 설치에서 MASTER 를 `--keep-mine` 으로 정리하면 `.new` 가 지워져, 새 CEO 템플릿이 옛 MASTER 를 통째로 품지 못하므로 다음 CEO 승격이 보류됩니다(`cys-dept` 의 상위집합 검사). 새 문안을 받지 않으실 거라면 `.new` 를 그대로 두십시오.
>
> ```
> cys pack-merge                                                    # 병합 대기 목록
> cys pack-merge --file directives/MASTER_DIRECTIVE.md --take-new   # 손대지 않으신 파일(CEO 로 승격된 설치는 거부됨 — 위)
> cys pack-merge --file directives/CSO_DIRECTIVE.md --keep-mine     # 내 문안 유지(새 문안 포기) — 합치려면 `--keep-mine` 없이 같은 명령(3-way · `--ai` 도 가능)
> ```
>
> 병합하지 않은 자리는 **옛 문안 그대로** 동작합니다(다만 CEO 로 승격되는 좌석은 병합과 상관없이 새 CEO 템플릿의 문안을 받습니다) — 이번 지침 변경은 문안 정정과 축소, 그리고 한 줄 가산이고(바꾼 문장은 위에 모두 적었습니다), 설치 점검(preflight)의 지침 문구 핀도 이번 문안을 건드리지 않습니다. 다만 옛 문안은 기아 경보의 기본을 0(꺼짐)이라고 잘못 적고 있고,
> 처방 코드를 전달하라는 말이 없으며, 부서장 `--detach` 문단이 635 B 더 깁니다(§8). 이 판의 팩 하한(`PACK_MIN_BINARY`)은 **올리지 않았습니다**(0.14.42 유지 — 이번 팩 변경은 새 CLI·RPC 를 부르지 않습니다. 다만 0.14.42 본체에서는 새 지침이 읽는 경보 표시 일부가 오지 않습니다 — §11).

## 1. 큐가 몇 시간 막혀도 몰랐던 것 — 이제 화면에 뜨고, 무엇을 하면 풀리는지 알려 줍니다

**무슨 증상이었나**
- 좌석 큐(`cys send --queued` 로 쌓여 대상이 조용할 때 배달되는 메시지)가 몇 시간씩 막혀도 아무도 알아채지 못했습니다. 데몬은 `queue.starved` 경보를 냈지만 화면이 그 이벤트를 받지 않아 아무것도 뜨지 않았습니다.
- 경보 안내문은 "운영자 판단으로 `cys queue deliver` 강제 배달 가능" 이라고만 했는데, 강제 배달은 입력줄 초안·질문 창·승인·전체화면·작업 중 게이트를 면제하지 않아 따라 해도 거부됐습니다.
- 막힌 이유는 좌석 메모리에만 있어 데몬이 내려가면 사라졌습니다 — 나중에 왜 막혔는지 알 수 없었습니다.

**무엇이 바뀌었나**
- **화면 토스트**: `⏳ 큐 막힘 — <역할> surface:<번호>` + `<N분째> · <사람이 할 일>`. 사람이 해야 할 일이 있는 사유에서는 OS 알림 배너도 함께 뜹니다. 같은 좌석은 한 장이 갱신되고(쌓이지 않음), 막힘이 풀리거나 좌석이 끝나면 거둡니다. **눌렀을 때만** 그 좌석으로 이동하고 키는 절대 보내지 않습니다.
- **처방 코드 13종**: 경보(`remedy_code`·`remedy`)와 `cys queue list`(막힌 좌석마다 stderr 한 줄)·`cys status --json`(좌석 `queue_remedy_code`)이 "왜 막혔나 → 사람이 무엇을 하나"를 알려 줍니다. 모든 처방 문장 끝에 "LLM 에이전트는 자동 조치(강제 배달·드레인·키 주입·동결 해제·항목 삭제) 금지" 가 붙습니다.
- **사유 파일 `queue-blocked.json`**(데몬 상태 폴더): 막힘 사유를 바뀔 때만 원자 기록하고, 직전 부팅의 마지막 사유는 `queue-blocked.prev.json` 으로 1세대 보존합니다. 메시지 본문은 싣지 않고 상태 복원에 쓰지 않는 사후 분석용입니다.
- **직접 `cys send` 거부 문구**: 입력줄이 비어 보이는데 입력줄 점유로 거부되면 문구 끝에 "그 창에서 사람이 Ctrl-U 한 번" 이 붙고, CLI 는 `--queued` 전환 안내 뒤 stderr 에 같은 처방을 한 줄 더 알립니다. ⌘K '역할별 재기동' 이 보류·거부되면 토스트에 사람이 할 일이 나옵니다.
- **경보 `hint` 문구 정정**: 강제 배달이 건너뛰는 것은 quiet 대기와 사이클 창 보류뿐이라는 사실로 바로잡았습니다.

**알아 두실 것**
- 경보 임계는 기본 600초(10분)입니다. `CYS_QUEUE_STARVE_ALERT_SECS=0` 으로 끌 수 있고 같은 좌석에는 5분 쿨다운이 있습니다(그 사이 배달이 한 건 성공하면 풀립니다). 배달 최소 간격·인계 결판 예산 소진 같은 몇 초짜리 보류와 kill-switch 동결 중에는 나지 않습니다.
- 토스트는 60초 뒤 닫히지만 앱을 켜 둔 동안(최대 200건) Control Center 알람 탭에 남고, 막힘이 이어지면 5분 뒤 다시 뜹니다. 알림 권한이 거부돼 있으면 배너 없이 토스트만 보입니다(아직 묻지 않았다면 첫 배너에서 시스템이 권한을 물을 수 있습니다).
- 되돌리기: 옛 `hint` 문구가 꼭 필요하면 데몬 env `CYS_QUEUE_STARVED_HINT_LEGACY=1`(데몬 재시작 필요).
- 새 화면 + 구 데몬: 구 데몬의 경보에는 `remedy_code` 가 없으므로 화면은 `막힘 사유: <blocked_by>` 만 보이고 모르면 알린다는 원칙으로 OS 배너도 겸합니다.
- CSO 좌석 자신의 경보는 경보 라우터가 폐기하므로(자기 좌석 제외) 그 경우에는 이 화면 알림이 사람이 볼 수 있는 표면입니다. 설계에 있던 'CSO 자기 경보를 master 로 우회' 는 넣지 않았습니다(LLM 좌석 입력으로 가는 경보를 늘리지 않으려는 결정).

## 2. 빈 입력줄의 Esc 한 번·Backspace 에 큐가 멈추던 것 (macOS·Linux)

**무슨 증상이었나** — 데몬은 사람이 쓰던 글 위에 기계 본문을 덧쓰지 않으려고 "제출·선정리를 아직 보지 못한 입력 바이트 수(계수)"를 셉니다. 종전(v2)에는 빈 입력줄에서 사람이 Esc 를 한 번 누르거나 Backspace 를 눌러도 계수가 1 로 남았고, Claude Code 의 입력 추천(커서 뒤 회색 제안)이 떠 있으면 데몬이 계수를 스스로 풀지 못해 그 좌석의 큐 배달·강제 배달·직접 `send` 가 `input_pending` 으로 거부됐습니다(v0.14.31 부터 · 0.14.42 노트 알려진 한계). 0.14.42 노트가 우회법(그 창을 클릭하고 Ctrl-U 한 번)을 적고 "0.14.43 첫 과제" 라고 했던 바로 그 항목입니다.

**무엇이 바뀌었나(계수 모델 v3)**
- 붙여넣기 봉투 밖에서 한 번에 들어온 입력이 **단독 Esc(정확히 1바이트)** 이거나 **Backspace(0x7f·0x08)만**이면 계수에 더하지 않습니다(빼거나 0 으로 되돌리는 것이 아니라 '더하지 않음' · 키를 따로 누르면 입력도 따로 들어옵니다). 글자를 남길 수 있는 키(한 덩어리의 `Esc Esc`·`Esc Backspace`·글자+Backspace·화살표·Tab·Ctrl-Y·앞으로 지우는 Delete 키 등)는 종전처럼 셉니다.
- **좌석 단위로 적용**: 에이전트가 등록돼 있고 엄격한 증거로 살아 있는 에이전트 + 프롬프트 마커를 선언한 어댑터 + 지금 PTY 전경이 셸이 아닌 작업인 좌석에서만 v3 입니다. 맨 셸·등록 없이 손으로 띄운 에이전트·죽거나 Ctrl-Z 로 멈춘 에이전트·마커 없는 어댑터는 종전(v2)입니다 — 맨 셸의 줄 편집기는 단독 Esc 를 다음 키를 기다리는 접두로 받아서, 계수를 0 으로 두면 큐 본문이 그 접두와 합쳐져 붙여넣기가 깨지기 때문입니다.
- 계수가 이미 0 보다 큰 줄(기계 잔여 포함)에 사람이 Backspace 를 치면 계수는 그대로 두고 '사람이 손댄 줄'로 표시해, 기계의 뒤늦은 Enter 가 사람이 고친 줄을 제출하지 못하게 합니다.
- **Windows 는 기본이 v2 입니다**(실기 확인 전이라 종전 유지) — Windows 에서는 같은 증상이 그대로이고, 막히면 그 창에서 Ctrl-U 한 번입니다.

**알아 두실 것**
- 되돌리기: 데몬 env `CYS_PENDING_INPUT_MODEL=v2`. 데몬이 프로세스 시작 때 **한 번만** 읽으므로 **데몬을 재시작해야** 반영됩니다. 값은 `v2`·`v3`(대소문자·앞뒤 공백 무시), 그 밖·미설정은 OS 기본(macOS·Linux `v3` · Windows `v2`).
- 현재 값: 데몬 전역 값은 `cys status --json` 의 `daemon.pending_input_model`, 그 좌석에 지금 적용되는 값은 경보·사유 파일의 `input_model`.
- **개발 중에 잡은 결함(사용자가 알아 둘 만한 것)**: 첫 구현은 v3 를 모든 좌석에 적용했는데, 적대 검증이 맨 셸(zsh 5.9)에서 사람이 Esc 를 한 번 누르면 30초 뒤 큐 본문이 깨진 채 들어가 줄마다 따로 실행되는 것(엉뚱한 폴더에서 파일 삭제까지)을 재현했습니다 — 그래서 위처럼 '살아 있는 에이전트 좌석'으로 한정했습니다. 2차 검증은 전경이 셸인데도 v3 가 적용되는 좁은 경우(Ctrl-Z 로 멈춘 에이전트·사망 직후 창)를 실측으로 보여, 계수 시점에 PTY 전경 프로세스 그룹을 직접 확인하도록 다시 좁혔습니다.
- **여전히 남는 것**: 글자를 치고 전부 지운 줄은 계수가 남고(감산 없음), 화살표·Tab·Ctrl-A 같은 비문자 키도 계수에 들어가 유령 계수를 만들 수 있습니다 — 화면이 완전히 비고 입력 추천이 없는 좌석은 데몬이 계수만 스스로 되돌리고, 그 밖의 경우의 처방이 §1 의 Ctrl-U 안내입니다. 0.14.42 노트가 적은 완화책(설정 폴더마다 `promptSuggestionEnabled:false` — 인과는 추정)에는 이번 판에서 바뀐 것이 없습니다(입력 추천을 끄는 주입은 넣지 않았습니다 — §12).

## 2-1. 스케줄이 직접 보낸 글이 제출됐는데도 입력줄 계수가 남던 것

**무슨 증상이었나**
- 스케줄 직접 push(하트비트·wakeup 처럼 좌석에 본문과 Enter 를 바로 써 넣는 경로)가 줄을 제출해도 데몬은 그 좌석의 입력줄 미제출 계수를 건드리지 않았습니다. 이미 유령 계수(§2)가 남은 좌석에서는 push 가 제출됐는데도 계수가 그대로라, 큐가 계속 `input_pending` 으로 멈춘 채 갈 수 있었습니다.

**무엇이 바뀌었나**
- 스케줄 push 가 좌석의 쓰기 대기열에 성공적으로 넘겨지면, 같은 입력 게이트 안에서 미제출 계수(와 사람 몫)를 0 으로 계상합니다 — 큐 배달이 줄을 제출할 때와 같은 규약입니다. 보류·큐 전환 판정과 큐 배달 경로는 그대로이고, 보류돼 큐로 돌려진 push·kill-switch 로 거부된 push·넘기기에 실패한 push 는 계수를 건드리지 않습니다.
- 계수가 0 이 아닌 값에서 0 으로 내려갔을 때만 이벤트 `schedule.push_cleared_pending {surface_ref, prev_bytes, prev_human_bytes, job, note}` 가 1건 납니다(계수가 0 인 정상 좌석은 이벤트 없음 · 관측용이라 경보가 아니고 CSO 큐로 가지 않습니다).

**알아 두실 것**
- **되돌리는 법**: 데몬 env `CYS_SCHEDULE_PUSH_COUNTS_SUBMIT=0`(정확히 `0` 만 끔 · 데몬 재시작) — 게이트·계수를 건드리지 않는 종전 동작입니다.
- **한계**: 스케줄 직접 push 한 곳뿐입니다(큐 배달은 종전부터 계상합니다). CEO 자동결재 요청·채널 inbox 지시·부트 감독자 통보·좌석 승계 고지처럼 큐를 거치지 않고 좌석에 바로 쓰는 다른 데몬 내부 주입은 아직 인계 뒤 계수를 계상하지 않습니다(다음 판 후보 — 이 네 곳은 코드로 계상이 없음을 확인했고, 그 경로에서도 같은 정체가 생기는지는 확인하지 못했습니다).

## 3. 로그인을 바꿔도 옛 계정이 주 계정으로 남던 것 — 사이드바 사용량

**무슨 증상이었나** — 다른 계정으로 다시 로그인했는데 옛 계정이 계속 주 계정으로 뜨고, 지난 100% 가 빨갛게 남았습니다(오너 제보).
이름은 폴더 이름뿐이라서, 옛 로그인과 새 로그인이 같은 폴더를 나눠 가지면 둘 다 `좌석` 에 `·7cce` 같은 코드 꼬리표가 붙어 어느 계정이 지금 쓰이는지 알 수 없었습니다.
줄 상한(8)을 넘으면 값이 없는 계정은 이름 없이 개수로만 접혔고, 접힌 한 줄 요약은 주 계정 한 개의 값뿐이라 Claude 와 Codex 를 같이 써도 한쪽만 보였습니다.
오래된 값은 95% 면 빨갛게 외쳤습니다.

**무엇이 바뀌었나**
- **이름**: 별명 → **지금 로그인된** 설정 폴더 이름 → `Claude (이전 로그인)`(다른 제공자는 제공자 이름) 순입니다(`● 사용 중` 인 계정은 이전 로그인이 아니라서 그 계정이 기록해 둔 폴더 이름, 그것도 없으면 `Claude` 를 씁니다). 같은 이름이 둘 이상일 때만 이름 뒤에 ` ·이메일` 꼬리표가 붙고, 🔒 가림을 켜면 Control Center 계정 표와 같은 `#해시` 로 보입니다.
- **`● 사용 중`**: 지금 로그인돼 쓰이는 계정에 붙는 표시입니다(주 계정은 이름 옆 배지, 다른 줄은 이름 앞 점).
- **주 계정**: 사용 중인 계정이 먼저이고, 그다음 최근 30분 안의 값 > 오래된 값 > 지난 기록 순이고, 최근 값끼리는 5시간 사용률이 높은 쪽이, 오래된 값·지난 기록끼리는 더 최근에 관측한 쪽이 먼저입니다. 2분 안팎으로 가르지 않은 것은, 리뷰어 좌석처럼 가끔만 보고하는 계정 때문에 주 계정이 수 분마다 바뀌고 한도에 가까운 계정이 2분만 조용해도 요약에서 밀려나기 때문입니다.
- **오래됨**: 30분 넘게 갱신되지 않은 값과 지난 기록은 경고색 없이 흐리게 적습니다 — 앞의 것은 `오래됨 · N분 전 관측`(1시간이 넘으면 `N시간 전`, 하루가 넘으면 `N일 전`), 복원한 지난 기록은 `지난 기록 · …` 입니다(값과 게이지 폭은 그대로).
- **접힌 한 줄 요약**: 두 제공자 이상이 관측되면 `C 5h12%·7d30% │ X 7d50%` 처럼 제공자별로 보이고, 마우스를 올리면 풀이가 나옵니다. 줄 글자색은 요약에 실린 값들 가운데 가장 높은 심각도(70% 이상 주황 · 90% 이상 빨강)로 정하고, 오래됨 `?` 값과 `5h리셋됨` 은 색에 넣지 않습니다.
- **관측 전**: 값이 없는 계정은 `관측 전` 으로 통일했고, 관측된 계정이 없으면 `관측 전 N계정`, 줄 상한에 잘린 관측 전 계정은 이름을 나열한 접힘 줄로 남습니다.
- **숨기기**: Control Center Live 계정 표 행 끝의 `숨기기`/`보이기` 단추로 계정을 사이드바·KPI 에서 뺍니다.
- **Control Center Live**: 계정 행에 별명·`● 사용 중`·`이전 로그인`(사용 중이 아닌 계정에만)·`관측 전`·`오래됨` 배지가 붙고, 게이지는 리셋이 지난 창에 한해 사이드바와 같은 규칙(폭 0 · `리셋됨` · `재관측 대기` · 경고색 없음)이고, 30분 넘은 값의 게이지는 색을 그대로 두고 행만 흐려집니다. KPI(세션 5h · 주간 7d)의 대표값은 숨기지 않았고 리셋 전이며 (사용 중이거나 최근 30분 안에 관측된 지난 기록 아닌) 값의 최댓값입니다. 그런 값이 하나도 없을 때의 전 좌석 폴백도 옛 로그인의 낡은 값과 리셋 지난 창을 뺍니다(구버전 데몬은 리셋 지난 창만).

**알아 두실 것**
- **별명은 파일로 답니다** — `~/.cys/accounts.json` 의 `aliases`(키 = 계정 ID 또는 이메일, 값 = 별명 · 24자)입니다. 별명을 고치는 화면은 이번 판에 없습니다. Codex·Antigravity·직접 선언한 계정은 계정 ID 가 모두 `"default"` 라서 그 키를 쓰면 전부에 같은 별명이 붙으니 이름표 키(`OpenAI Codex` 등)를 쓰십시오. 데몬을 다시 켤 필요는 없습니다(60초 하한으로, 파일이 바뀌었을 때만 다시 읽습니다).
- **데몬을 켤 때 `~/.cys/accounts.json`(선언 계정·별명 파일)을 막히지 않게 읽습니다** — 데몬은 연결을 받기 전의 기동 단계에서 이 파일을 읽는데, 종전에는 그 자리에 일반 파일이 아닌 것(이름 있는 파이프(FIFO) 등)이 있으면 여는 순간 쓰는 쪽이 올 때까지 멈추는 읽기 때문에 기동이 서 있을 수 있었습니다. 이제 일반 파일만 읽고(상한 1 MiB — 별명의 64KiB 상한과 별개), 일반 파일이 아니거나 1 MiB 를 넘으면 읽지 않고 '선언 계정 없음'으로 보며 기동을 이어 갑니다. 정상 설치에서는 일어나지 않는 병적 입력이라 평소 달라지는 것은 없습니다. 선언 계정은 데몬을 켤 때만 읽으므로 고친 뒤에는 데몬을 다시 켜야 반영됩니다(별명은 위에서 말한 대로 60초 하한으로 다시 읽습니다). `cys usage-accounts` 가 텍스트 모드 끝에 표준 오류로 내는 안내 한 줄(이번 판에서 새로 생김)은 '연결된 데몬 하나의 계정'이라고 말합니다 — 부서 좌석에서 실행하면 그 부서 데몬의 계정입니다(매뉴얼 §15).
- **🔒 가림은 별명을 가리지 않습니다** — 화면 공유 때 사이드바 본문에 그대로 보이므로 별명에 개인 식별자를 쓰지 마십시오.
- **'사용 중'은 cys 창의 좌석 기준입니다** — 외부 터미널에서만 쓰는 계정은 사용 중이 되지 않습니다. 판정은 설정 폴더에 기록된 로그인을 기준으로 합니다.
- 로그인을 바꾼 뒤 표시가 따라오기까지 데몬의 확인 하한 **최대 60초**에 사이드바 조회 간격(최소 30초)이 더해집니다.
- 숨김은 **이 앱의 저장소에만** 저장됩니다(다른 컴퓨터에 전해지지 않고, 경보·데몬에는 영향이 없으며, 최대 64개 키 — 64개째부터는 `숨기기` 가 말없이 무시됩니다). KPI 후보가 남지 않아 전 좌석 폴백이 쓰일 때는 폴백이 숨김을 모릅니다.
- 데몬이 새 키를 보내지 않는 구버전이면 `사용 중`·`이전 로그인`·별명·현재 로그인 폴더 이름만 빠지고(백지는 아닙니다), 신선도 순서·오래됨 표기·제공자별 요약·숨기기·KPI 후보 같은 나머지 새 규칙은 그대로 적용됩니다.
- **되돌리는 법**: 이 화면 변화에는 끄는 노브가 없습니다. 숨김은 `보이기` 로, 별명은 파일에서 `aliases` 를 지우면 됩니다.
- 후보도 폴백 값도 없으면 KPI 는 `0%` 로 보입니다 — 값이 없다는 뜻이지 0% 사용이 아닙니다.

## 4. 로그인을 바꾼 뒤에도 옛 계정의 한도 경보가 30분마다 오던 것

**무슨 증상이었나** — 좌석 설정 폴더의 로그인을 다른 계정으로 바꾼 뒤에도 옛 계정의 "리셋 전" 값(예: 99%)이 리셋 시각까지 30분마다 한도 경보로 CSO 에게 갔습니다. 좌석별 한도 경보도 대화 기록에서 이월된 같은 값을 되살렸습니다 — 이월되는 값에 갱신 시각만 새로 찍혀 값의 나이가 가려졌기 때문입니다.

**무엇이 바뀌었나(오너 결재 규칙)**
- 한도 경보의 입력은 **그 창이 아직 리셋 전이고, 그 값이 "사용 중"인 로그인의 것이거나 관측한 지 30분(1800초) 이하인 것**뿐입니다.
- **판정할 수 없으면 "사용 중"으로 읽어 경보를 지킵니다**(신원 파일 삭제·FIFO·폴더 미상·귀속 없음·좌석 목록 수집 실패·직접 선언한 계정).
- 로그인을 바꾼 옛 계정의 경보는 마지막 관측 30분 뒤 내려가고, 데몬을 다시 켠 뒤 복원된 옛 값은 처음부터 경보를 만들지 않습니다. 빠졌던 경보가 다시 적격이 돼도 마지막 발행에서 30분이 지나기 전에는 다시 내지 않습니다(깜빡임 방지).
- 경보가 빠질 때 이벤트 `usage.alert_resolved {key, reason: stale|cleared}` 가 1건 납니다(CSO 큐로는 가지 않고 지금은 소비자가 없으며, 한도 경보뿐 아니라 **모든 경보 키**에 납니다).
- CSO 큐의 한 줄 요약에 `age=<초>` `in_use=<0|1|na>` `reset=<초>` `held=<초>` 토큰이 붙습니다(정수·열거 값뿐이고 계정·역할 이름은 종전 해시). `in_use=0` 은 '이 데몬의 살아 있는 좌석이 지금 쓰지 않는 계정·좌석의 값'(로그인 전환 직후의 옛 계정 · 그 에이전트의 좌석 없음 · 부서 데몬 좌석만 쓰는 계정 · 데몬을 막 켠 직후)이라는 뜻입니다. CSO 지침은 본문이 `in_use=0 ∧ age>1800` 또는 `reset<0` 이면 그 경보를 신규 작업 제한 판단의 근거로 쓰지 말고 `alert_eligible` 로 다시 확인하라고 한 줄로 정합니다(§8). **그 조건의 경보는 데몬이 이미 걸러 내므로** 기본 설정에서는 오지 않고, 걸러내기가 풀린 데몬(노브 `0` 이거나 1800 보다 크게 올림)에서만 올 수 있습니다 — 그런 데몬에서는 `alert_eligible` 도 같은 노브로 계산되므로 노브 `0` 이면 리셋 전인 경보 입력 창이 모두 `true` 입니다(리셋 지난 창은 노브 `0` 에서도 빠집니다).
- 좌석의 `usage`(`cys status --json` 등)에 `rate_observed_at`·`rate_age_secs`·`rate_in_use`·`rate[].alert_eligible` 이 실려 재확인 경로도 같은 규칙을 말합니다.

**알아 두실 것**
- **새 노브 2개**: `CYS_ACCOUNT_ALERT_STALE_SECS`(기본 1800 · `0` = 규칙 끔 = 0.14.42 동작)와 `CYS_ALERT_SUMMARY_LEGACY=1`(요약을 종전 바이트로 — 요약 문자열을 파싱하는 외부 도구가 있을 때). 둘 다 데몬 환경변수라 **데몬을 다시 띄워야** 적용됩니다.
- 사용 중(또는 판정 불가)인 동안은 나이와 상관없이 그 창의 리셋까지 경보가 이어집니다(7일 창이면 최대 7일).

## 5. 「팀 직접 만들기」 — 경과 시간·지금 단계를 말하고, 느린 컴퓨터에는 손잡이를 줍니다

**무슨 증상이었나**
- 전문가용 ▸ 「팀 직접 만들기」 대기 화면이 「부서를 준비하고 있습니다 — 최대 십여 초 걸릴 수 있어요」 라고 했지만, 실제로는 소켓이 열릴 때까지만 시작부터 23초(이 개발 맥 1회 실측)였고, 느린 컴퓨터의 시간은 실측하지 못했습니다.
- 그 뒤 팀원(부서장·CSO·워커·리뷰어)이 켜지는 동안(이 개발 맥 1회 실측으로 만들기 시작부터 약 5분)은 화면에 아무 안내가 없었고, 첫 자리가 붙기 전의 빈 탭에는 방금 만든 팀에 사실이 아닌 「이 부서는 아직 켜지 않았습니다」 가 보였습니다.
- 느린 디스크 같은 환경에서는 데몬이 소켓을 여는 데 12초가 모자라 '데몬 기동 실패'로 끝날 수 있었고(재현은 실측하지 못했습니다), 그 대기 시간을 늘릴 방법이 없었습니다.

**무엇이 바뀌었나**
- 대기 화면에 **경과 시간**이 1초마다 흐르고(60초부터 `1분 5초` 꼴), 90초부터 「평소보다 오래 걸리고 있습니다 — 그대로 기다려 주세요 …」 로 문구가 바뀝니다.
- 그 아래 줄에 **「지금: <단계>」** 가 나옵니다. 단계는 7가지 — 팀 번호를 잡는 중 · 이미 켜진 데몬이 있는지 확인하는 중(약 12초) · 데몬을 켜는 중 · 데몬이 팩을 설치하는 중(파일 수백 개) · 데몬이 켜졌습니다 — 설정을 심는 중 · 부서장 자리를 여는 중 · 마무리하는 중. 팩의 `cys-dept` 가 단계마다 표준 오류에 `[cys-dept] @stage <키>` 한 줄을 내고 앱이 그 줄을 읽는 즉시 화면을 고칩니다(기존 `[cys-dept] …` 줄의 문구·순서는 그대로, 표준 출력의 "마지막 줄 = 팀 이름" 약속도 그대로).
- 방금 만든 팀(이 세션에서 화면으로 만든 팀 — 대표가 대화 승인으로 만든 팀과 기존 팀을 돌려받은 경우는 제외)의 빈 탭은 60초 동안 「첫 자리를 붙이는 중입니다 — 잠시만 기다려 주세요」 라고 말합니다([지금 켜기] 버튼은 그대로 있고, 60초가 지나도 자리가 붙지 않으면 문구만 종전으로 돌아옵니다).
- 팀이 만들어진 뒤에는 **「팀원을 켜는 중」** 토스트가 뜹니다 — 지금 몇 자리가 붙었는지·경과(분 단위)를 보여 줍니다. 다섯 자리(부서장·CSO·워커·리뷰어 둘)가 모두 붙으면 **「팀 자리가 모두 붙었습니다」**(`자리 5개가 모두 붙었습니다 · 걸린 시간 4분` — 팀이 만들어진 때부터 잰 분 단위 내림, 1분이 안 되면 `1분 미만`)로 한 번 바뀌고 토스트는 수명(60초)대로 사라집니다 — 화면은 자리가 붙었는지만 알 뿐 에이전트가 실제로 준비됐는지는 모르므로 '준비 완료'라고 말하지 않습니다. 15분이 지나도 다섯 자리가 다 붙지 않으면 **「팀원 켜기 — 확인 필요」**(`아직 <N>자리입니다 — Control Center 에서 자리 상태를 확인하세요 · 경과 15분`)를 한 번 알립니다. 15분이 지나도록 그 팀의 좌석 목록을 한 번도 받지 못하면 결과 알림 없이 진행 안내가 수명(60초)으로 사라질 뿐이고, 목록을 받는 첫 주기에 결과를 냅니다. ×로 닫으면 「팀원을 켜는 중」 의 주기 갱신만 멈추고 결과 알림은 그래도 한 번 나옵니다(닫지 않았는데 수명이 먼저 끝나면 다음 점검에서 다시 냅니다). 편성 도구의 결과 알림은 종전처럼 일반 알림(`ℹ 알림`)으로 따로 옵니다. 표시 전용이고 어떤 명령도 보내지 않습니다.
- 실패 문구 끝에 **대기한 초 · 로그 위치 · 손잡이**가 붙습니다: `… 데몬 기동 실패 (소켓 대기 12초 · 로그: <폴더>/cysd.log · 느린 디스크라면 CYS_DEPT_READY_SECS=60 처럼 대기 예산을 늘릴 수 있다)`. 앱은 실패 메시지에서 단계 표지 줄을 뺍니다(사유가 앞 300자 안에 보이도록). 이 「팀 만들기 실패」 안내는 닫기(×) 버튼이 있는 지속 알림이라 60초 동안 떠 있고(종전에는 8초), 팀 만들기를 다시 시작하면 지난 실패 안내는 걷히며 Control Center 알람 탭에는 남습니다.
- 새 노브 `CYS_DEPT_READY_SECS`(정수 12~180, 기본 12): **데몬을 띄운 뒤**의 소켓 대기 시간만 늘립니다. 사전 검사(공칭 12초 — 핑 시간이 더해져 실제로는 약 12.8초)는 고정이라 새 팀마다 더 기다리지 않습니다. 180 을 넘는 값은 12 로 읽습니다 — 부트 폴백이 팀 만들기 호출을 240초에 강제 종료하는데, 실패 경로의 실제 소요가 사전 검사 약 12.8~14초에 노브 × 최대 약 1.18초(반복 1회 약 0.118초)를 더한 값이라 180 이면 최대 약 226초이기 때문입니다.

**알아 두실 것**
- **기본 동작은 그대로입니다**(대기 12초 · 예약 유예 25초). 수정 전·후 `cys-dept` 를 같은 목 환경 14시나리오에서 비교해 종료 코드·표준 출력·핑 횟수가 같음을 확인했습니다.
- **기본값을 올리지 않은 이유**(설계안의 "기본 60초 상향"을 기각): 같은 팀을 뒤따라 만드는 호출이 앞선 생성자를 '부팅 중'으로 믿어 주는 예약 유예(25초)가 사전 검사(약 12.8~14초)와 스폰 뒤 대기(최대 약 12.8~14초)의 합(약 25.6~28초)보다 이미 조금 짧아(그 작은 틈은 0.14.42 에도 있었고 기본 동작은 바꾸지 않았습니다), 대기만 늘리면 그 틈이 노브만큼 벌어져 25~60초 구간에 뒤따라온 호출이 생성자를 죽었다고 보고 데몬을 **중복 기동**합니다. 그래서 노브를 12 보다 크게 올릴 때만 유예가 `노브 + 노브/5 + 17`(소수점 이하는 버림) 까지 함께 올라가 그 틈을 줄이게 했습니다(공칭 기준이라 실제 대기보다 수 초~수십 초 짧을 수 있어 틈을 닫지는 못합니다). 노브를 올렸는데 `CYS_DEPT_RESERVE_GRACE` 가 정수가 아니면 유예가 따라 오르지 못해 `cys-dept` 가 경고 한 줄을 표준 오류에 냅니다. 기본 상향은 Windows 실기 측정 뒤로 미뤘습니다.
- **배너 대신 토스트**(설계안의 탭 위 진행 배너를 기각): 탭 위에 배너를 끼우면 터미널 pane 크기가 바뀌어 전 좌석 PTY 리사이즈가 두 번 일어나기 때문입니다. 다섯 자리가 다 붙지 않은 채 15분이 지나면 「팀원 켜기 — 확인 필요」 를 한 번 알리고 안내를 접습니다(살아 있음을 지어내지 않습니다).
- 구 팩(표지 없음)에서는 단계 줄 없이 경과만 보입니다. 거꾸로 **구 앱 + 새 팩**(팩만 먼저 갱신한 경우)에서는 실패 시 표지 줄 몇 줄이 실패 사유 앞에 끼어, 사유가 앞 300자 안에서 잘릴 수 있습니다(새 앱은 그 줄을 걷어 냅니다).
- 대표가 대화 승인으로 팀을 만들 때(`cys-dept create --team-token`)도 같은 표지 줄이 그 도구 출력에 보입니다 — 안내용이며 동작은 바뀌지 않습니다.

**되돌리는 법**
- 단계 표시를 실시간으로 읽는 것만 끄려면 `CYS_DEPT_CREATE_STREAM=0` — 앱을 다시 시작해야 하고(앱이 가진 값만 읽음) 데몬 재시작은 필요 없습니다. 끄면 대기 화면에 「지금: …」 줄만 빠지고 경과 시간·팀원 안내는 그대로이지만, 단계 표지를 받지 못해 기존 팀을 돌려받은 경우와 새 팀을 구분하지 못하므로 팀원 안내가 성공한 호출마다 종전처럼 뜹니다.
- `CYS_DEPT_READY_SECS` 를 비우면(미설정) 종전 12초입니다 — `cys-dept` 가 실행될 때마다 읽으므로 데몬 재시작은 필요 없습니다(앱 버튼으로 만들 때는 앱이 켜질 때 가진 값이 쓰이므로 값을 바꾼 뒤 앱을 다시 켜야 합니다).

## 6. 인앱 업데이트가 설치되지 않았을 때 알려 줍니다(윈도우는 막히면 즉시 · 그 밖에는 다시 열린 뒤 한 번)

**무슨 증상이었나**
- 제보(Windows 11 Home · 0.14.37 → 0.14.42): 업데이트를 눌렀는데 **경고 없이** 구버전이 그대로 남았습니다. 제보에는 이벤트 3033·3077 이 있었고, 코드 서명도 평판도 없는 설치 파일을 Windows 가 막았을 가능성이 있습니다(원인 확정은 아님).
- 원인 구조: 0.14.42 이하 Windows 의 업데이터(확인한 것은 업데이터 플러그인 2.10.1 이 든 0.14.37·0.14.42)는 설치 파일을 띄운 뒤 결과를 보지 않고 앱을 끝냅니다 — 앱 쪽에는 실패를 알릴 코드가 실행될 틈이 없었고, 다시 열어도 버전만 그대로였습니다. 0.14.43 부터는 앱이 그 결과를 직접 확인합니다(§6-1).

**무엇이 바뀌었나**
- **Windows 는 설치 파일 실행이 막히면 앱을 닫지 않고 즉시 알립니다**(0.14.43 앱에서 시작한 업데이트부터 — 실측과 함께 §6-1).
- 앱이 설치 파일을 받기 직전에 `~/.cys/.update-attempt.json`(`{from, to, at}`)을 적고, 앱이 다시 열릴 때 한 번 판정합니다: 지금 버전이 `from` 그대로이고 기록이 90초 이상이면 알림 한 번 + 기록 삭제, 90초 미만이면 설치기가 아직 도는 중일 수 있어 남은 시간 + 5초 뒤 딱 한 번 다시 봅니다. 재시도·자동 재설치는 없습니다. Windows 는 설치 파일이 뜬 직후 `at` 을 그 시각으로 다시 써서 90초가 받기 시작이 아니라 설치 파일이 뜬 때부터 셉니다(느린 회선에서 받는 데 걸린 시간 때문에 설치기가 도는 중인데도 알림이 일찍 뜨는 일을 줄이려는 것입니다 — 설치가 90초를 넘겨 도는 동안 앱을 다시 열면 여전히 뜰 수 있습니다).
- 알림 「업데이트가 설치되지 않았습니다」 — 첫 줄은 모든 OS 공통(`<받으려던 버전> 업데이트가 설치되지 않았습니다 — 지금 버전은 <지금 버전> 그대로입니다.`), Windows 는 이벤트 뷰어 확인 위치(CodeIntegrity → Operational 의 이벤트 3033·3077)와 설치기의 실패 기록 파일(설치 폴더의 `cys-install-failure.txt`)·받은 설치 파일이 저장되는 임시 폴더 이름까지 알려 주고, 그 밖의 OS 는 홈페이지에서 직접 설치하라고 안내합니다. 0.14.43 에서는 윈도우의 실행 차단이 그 자리에서 알려지므로, 윈도우에서 이 알림이 뜨는 경우는 주로 설치 파일을 받는 중에 앱이 닫혔거나 설치기가 뜬 뒤 실패했을 때입니다.
- Windows 에서 **스마트 앱 컨트롤이 켜져 있으면** [본체 패치 설치] 확인 창 끝에 사실을 알리는 한 문단이 붙고, 알림에도 한 줄이 더 붙습니다. 상태는 레지스트리 값을 `reg query` 로 읽기만 하며, 읽지 못하면 문단 없이 종전 창을 엽니다. **스마트 앱 컨트롤을 끄라는 지시는 어디에도 없습니다**(4551 알림은 확인할 곳과 선택의 결과만 사실로 적습니다 — §6-1).
- 알림은 10분 떠 있고, 닫히지 않은 채 만료되면 OS 알림 배너가 한 번 더 뜹니다(이 알림은 기록을 지우며 한 번만 나오기 때문).

**알아 두실 것**
- **되돌리는 법**: `CYS_UPDATE_VERIFY=0` — 시도 기록을 쓰지도 재시작 뒤에 판정하지도 않습니다(앱 재시작 필요 · 데몬 재시작 불필요). 다만 스마트 앱 컨트롤 사전 고지는 이 노브와 무관해, 스마트 앱 컨트롤이 켜진 Windows 에서는 노브가 0 이어도 확인 창에 그 문단이 붙고, 그 문단이 약속하는 즉시 알림은 `CYS_UPDATE_CHECKED_LAUNCH` 가 켜져 있으면 이 노브와 무관하게 뜹니다(뜨지 않는 것은 다시 열린 뒤의 알림뿐). `0` 외의 값은 켠 채입니다(빈 값은 미설정으로 보아 옛 접두 변수를 확인합니다).
- **효과는 0.14.43 앱에서 시작한 업데이트부터입니다** — 기록은 업데이트를 시작하는 앱이 쓰므로, 0.14.42 이하 앱에서 누른 업데이트(예: 0.14.37 → 0.14.43)는 기록이 없어 알림이 뜨지 않습니다. 윈도우의 즉시 알림도 같습니다 — 옛 앱의 업데이터는 실행 결과를 보지 않아, 스마트 앱 컨트롤이 켜진 PC 에서는 앱이 말없이 닫히고 구버전이 남을 수 있습니다(실측 — §6-1).
- **이 알림은 코드 서명도 평판도 없어서 막히는 것을 풀지 못합니다** — 사실을 알릴 뿐이고 설치는 계속 막힐 수 있습니다. 코드 서명(인증서)은 이번 판에 들어가지 않았습니다(제외 사유는 §12).
- 결정 기록: 플러그인 훅 대신 설치 직전 기록을 택했습니다(호출 직전 기록이 더 단순하고 오류 때 지울 수 있어서).

**같이 정리한 것 — 화면에서 데몬으로 보낸 글이 거부될 때(점검)**: 화면(GUI)이 데몬으로 직접 보내는 글의 '거부' 처리를 읽기 전용으로 점검한 결과 **결함 후보는 0건**이었습니다(거부를 말없이 삼켜 내용이 사라지는 곳도, 상한 없는 자동 재시도도 없음). 다만 다른 팀으로 전출하다 실패했을 때 토스트가 데몬 원문(GUI 에서는 실행할 수 없는 `--queued` 처방 포함)을 그대로 보이던 것을 사람이 읽는 안내로 바꿨고(번역표에 없는 오류는 원문 그대로), 송신 실패를 화면에 알리는 장치를 지키는 소스 핀 3개를 더했습니다.

**무엇이 바뀌었나(0.14.43)**
- **설치 파일을 띄운 결과를 앱이 직접 확인합니다** — 같은 임시 경로·같은 인자·같은 호출로 설치 파일을 띄우되, 실행이 막히면(`ShellExecuteW` 반환값 32 이하) 앱을 **닫지 않고** 임시 설치 파일과 시도 기록을 지운 뒤 곧바로 알림을 띄웁니다. 성공하면 종전과 같이 앱을 끝내되, 그 직후 시도 기록의 기준 시각을 설치 파일이 뜬 시각으로 다시 씁니다(§6). 오류 번호(4551 · 5 · 2/3 · 225 · 1223 · 그 밖)별 제목·본문은 매뉴얼 §11 「설치 파일 실행이 막혔을 때(윈도우)」에 전문이 있습니다. 4551 알림의 제목은 「설치 파일 실행이 차단되었습니다」입니다.
- **설치 전 확인 창의 문단**(스마트 앱 컨트롤이 켜져 있을 때만)의 문구를 바꿨습니다 — 「이 PC 는 Windows '스마트 앱 컨트롤'이 켜져 있습니다. 새 설치 파일에 Windows 가 신뢰하는 코드 서명이나 평판이 없으면 Windows 가 실행을 막습니다(0.14.43 까지의 cys 설치 파일에는 코드 서명이 없습니다). 막히면 업데이트는 설치되지 않고, 이 앱은 닫히지 않은 채 그 사실을 알려 드립니다. 그 경우 홈페이지에서 받은 설치 파일도 같은 이유로 막힙니다. 스마트 앱 컨트롤이 켜져 있는 동안에는 이 앱을 닫으면 다시 열 때도 막힐 수 있습니다.」 새 설치 파일의 서명 여부는 앱이 받기 전에 알 수 없어서 막힌다고 단정하지 않고 "없으면" 으로 적었고, 다음 버전의 서명 여부는 정해지지 않았습니다.
- **되돌리는 법**: 앱 환경변수 `CYS_UPDATE_CHECKED_LAUNCH=0`(정확히 `0` 만 · 앱 재시작) — 종전 경로(업데이터 플러그인 그대로: 결과를 보지 않고 앱 종료)로 돌아갑니다. 그때는 위 문단의 "이 앱은 닫히지 않은 채 그 사실을 알려 드립니다" 가 "지금 설정(CYS_UPDATE_CHECKED_LAUNCH=0)에서는 이 앱이 알림 없이 닫힙니다" 로 바뀌고, 막힌 실행은 앱이 말없이 닫힌 뒤 다시 열렸을 때의 알림(§6)이 맡습니다(앱을 다시 열 수 있을 때). macOS·Linux 는 이 분기가 없습니다.

**그대로인 것**
- 이번 판의 설치 파일에는 코드 서명이 없고, 스마트 앱 컨트롤이 켜진 PC 에서는 코드 서명도 평판도 없는 설치 파일·실행 파일이 막힙니다(홈페이지의 공개 설치 파일 3개가 3/3 막혔고, 다음 버전의 서명 여부는 정해지지 않았습니다) — 이 판은 막혔을 때 **알리는 것까지**입니다(§12 의 코드 서명 항목).
- 스마트 앱 컨트롤이 켜진 동안 앱을 닫으면 다시 열 때도 막힐 수 있습니다(위 실측) — 그래서 알림이 앱을 닫지 말라고 적습니다.
- **cys 는 스마트 앱 컨트롤을 끄라고 권하지 않습니다. 아래는 판단에 필요한 사실입니다.** 끄면 설치할 수 있지만 PC 의 보호 수준을 낮추는 선택이며, Windows 업데이트 상태에 따라 다시 켜지 못할 수 있습니다(Microsoft 안내 기준 — 저희가 직접 재지는 않았습니다). 꺼진 Windows 11 에서는 위 실측처럼 업데이트가 설치됩니다. 확인하는 곳: Windows 보안 → 앱 및 브라우저 컨트롤 → 스마트 앱 컨트롤.

**이전 버전에서 올라올 때의 한계**
- 이 확인은 **0.14.43 앱에서 시작한 업데이트부터** 있습니다. 0.14.42 이하 앱에서 누른 업데이트(예: 0.14.37 → 0.14.43)는 그 앱의 옛 업데이터가 돌아, 스마트 앱 컨트롤이 켜져 있으면 위 실측처럼 앱이 말없이 닫히고 구버전이 남을 수 있으며 앱을 다시 열 수도 없을 수 있습니다. 업데이트 전에 스마트 앱 컨트롤 상태를 확인하는 곳은 위와 같습니다.

**실측의 한계**
- 러너의 Windows 11 은 Enterprise 판 ARM64(x64 에뮬레이션)였습니다. Home 판·x64 네이티브 실기와 제보자 PC 의 이벤트 원문은 보지 못했습니다(같은 Microsoft 정책으로 보지만 Home 판에서 확인하지는 못했습니다).
- 스마트 앱 컨트롤의 '평가' 상태(레지스트리 값 2)는 러너에서 적용되지 않아, 그 상태의 동작(차단 없음)은 Microsoft 문서 근거뿐입니다.
- 설치 파일 실행 모듈 단독 시험은 앱과 같은 함수를 부르는 시험용 드라이버로 했습니다. **0.14.43 앱 전체의 시험(위 표의 마지막 두 줄)은 문구를 고치기 전의 빌드로 한 것입니다** — 화면에 뜬 알림·확인 창 문구는 위에 적은 최종 문구가 아니라 앞선 판의 것이었고(예: 알림에 「이 설치 파일에는 코드 서명이 없습니다」 한 문장이 더 있었고 '서명 없는 프로그램은 실행되지 않습니다' 라고 적혀 있었습니다), 설치 파일이 뜬 직후 시도 기록의 기준 시각을 다시 쓰는 동작도 그 빌드에는 없었습니다. 문구를 고친 뒤의 빌드로는 아직 재지 않았습니다. 시험은 Enterprise 판 ARM64 러너 한 곳에서 했고 업데이트 목록은 버전을 0.14.99 로 적은 시험용입니다(실제 설치 파일은 공개된 0.14.42). 꺼진 상태의 88·56·72초 설치는 옛 업데이터 경로의 실측이고, 앱의 새 경로로 설치한 꺼진 상태 실측은 표의 한 번(약 68초)입니다. 임시 경로·인자·호출이 업데이터 플러그인과 같다는 것은 플러그인 소스와 맞춘 검체로도 확인했습니다 — 플러그인과 다른 점은 창·트레이 정리를 설치 파일을 띄운 직후에 한다는 것과, 설치 파일을 띄운 직후 시도 기록의 기준 시각을 다시 쓴다는 것입니다.
- 앱이 `reg query` 출력을 읽는 부분은 이 러너의 기본 계정에서 읽혀 확인 창에 안내 문단이 붙은 것까지 확인했고, 비관리자 계정과 한국어 Windows 출력은 문서화된 출력 견본으로만 검증했습니다.

## 7. 데몬 로그를 가득 채우던 `ABI producer self-verify critical (Drift)` 줄

**무슨 증상이었나**
- 라이브 0.14.42 데몬 로그의 대부분이 `[cysd] ABI producer self-verify critical (Drift) — falling back to legacy serialization` 한 줄이었습니다(본부 데몬 4,472줄 중 4,412줄 · 부서 데몬도 같은 모양).
- 원인: 데몬이 응답을 직렬화한 뒤 다시 읽어 대조하는데, JSON 라이브러리의 부동소수 읽기가 best-effort 라 17자리 소수가 값에 따라(약 9~12%) 1ulp 어긋나 읽혀 '불일치'로 판정됐습니다 — 부동소수가 실린 모든 응답·이벤트 프레임이 해당했습니다. 응답은 메타 없는 종전 형식으로 폴백해 그대로 나갔고, 진단성만 망가졌습니다('critical' 오보 · 로그 폭주).

**무엇이 바뀌었나**
- 어긋남이 **부동소수 표기 정밀도뿐**이면(구조·키·문자열·정수·불리언은 같고 소수만 상대 4·ε(약 4~8ulp) 이내) 새 분류 `FloatInexact`(복구 가능) — 로그 없이 카운터만 올립니다. 그 밖의 불일치(비객체 응답 · 정수↔실수 표현 변화 포함)는 종전대로 `Drift`(치명) — 카운터 + **프로세스 전체에서 60초에 1줄**(`… (suppressed N since last)` 로 억제 건수 표시, 종전 문구 앞부분은 그대로).
- `org.status` 의 `daemon` 에 `abi_float_inexact_total`·`abi_drift_total`(u64 · 프로세스 기동 뒤 누적)이 가산됐습니다 — `cys status --json` 에서 읽습니다.

**알아 두실 것**
- **프레임 직렬화는 같은 값이면 0.14.42 와 같은 바이트입니다** — 수정 전·후 코드를 같은 입력 60만 건으로 비교해 다른 바이트 0건(`org.status` 에 새 키 2개가 더해진 것은 별개). 판정과 로그·카운터만 바뀝니다. 새 노브는 없습니다.
- `float_roundtrip` 기능을 켜는 설계안은 기각했습니다: 켜면 데몬이 부동소수 프레임에도 길이 표지(`_flen`)를 붙이게 되어, 읽기가 best-effort 인 구 클라이언트(0.14.42 이하 `cys`)가 값에 따라 `abi: LenMismatch` 로 간헐 실패할 수 있기 때문입니다(팩 스크립트의 `cys status --json` 이 자가치유 판정을 오판할 위험).
- 관측: `abi_drift_total` 이 0 이 아니면 진짜 와이어 결함이니 로그와 함께 알려 주세요. `abi_float_inexact_total` 은 부동소수가 실리는 한 평시에도 계속 늘어나는 **정상 신호**라 경보 기준으로 삼지 마세요.

## 7-1. 좌석 밖에서 보낸 메시지의 발신 표시 — `발신 unknown` 대신 `cli:send`

**무슨 증상이었나**
- 재시작 안내 `[DRAIN-VERIFY]` 같은 메시지에 발신 표시가 없다는 제보(Windows 사용자)입니다. 데몬은 발신 좌석을 호출 프로세스에서 **검증**하는데, 좌석(pane) 밖 — 사람 터미널·스크립트·GUI 가 띄운 `cys` — 에서 보낸 요청에는 검증할 좌석이 없어 큐 다이제스트 머리가 `발신 unknown` 으로, 직접 전송 이벤트와 배달 원장의 `from` 이 null 로 남았습니다.

**무엇이 바뀌었나**
- 좌석 밖에서 보내는 `cys` 가 요청의 `from` 에 **표시용 라벨**을 싣습니다 — `cys send` = `cli:send`, 좌석에 본문을 직접 주입하는 경로(지침·과업·사이클 저장 지시·평문 `cys drain` 등) = `cli:inject`, `cys drain --verify` 의 주입 = `cli:drain`. 환경변수 `CYS_SENDER_LABEL=<이름>` 을 주면 `cli:<이름>`(영문·숫자·`.`·`_`·`-` 만 남기고 32자까지)입니다. 좌석 안에서는 종전 그대로입니다.
- **라벨은 표시·원장용이며 권한·게이트 판정에 쓰이지 않습니다.** 데몬은 검증된 신원이 있으면 판정·큐 항목·원장·`surface.input_injected` 에 늘 그것을 쓰고, 라벨은 `cli` 접두가 고정이라 좌석 번호나 `master`·`worker` 같은 역할 이름과 같을 수 없습니다. 이 값을 읽는 곳을 전수 점검해 허가·거부·귀속·접근 제어·게이트가 갈리는 분기가 없음을 확인했고, 그 결과를 실행 검체로 잠갔습니다.
- 보이는 곳: 병합 다이제스트 머리 `[큐 다이제스트 N건 · 발신 cli:send]`, 배달 원장의 `from_label`(직접 전송 경로에는 이번에 가산된 키 — 라벨이 있을 때만), 이벤트 `surface.input_injected` 의 `from`(조용하지 않은 직접 전송만).

**알아 두실 것**
- **표시만 달라지는 세 곳**: ① 다이제스트 머리 `unknown` → 라벨 ② `queue.revive`(만료된 큐 항목을 되살리는 요청)의 거부 사유 문자열 `unknown_from_requires_master` → `label_from_requires_master`(허가·거부 판정은 같고 사유 문자열만) ③ 같은 발신자 병합의 단위(같은 라벨끼리는 묶이고 라벨 항목과 발신 없는 항목은 갈립니다 — 병합 규칙은 그대로).
- **외부 소비자**: 이벤트(`surface.input_injected`·`queue.enqueued`)와 `queue.list` 항목의 `from` 이 null·숫자 대신 문자열일 수 있습니다. 배달 원장의 `from` 은 그대로이고 라벨은 별도 키 `from_label` 에 담깁니다. HUD 브리지(이번 판의 팩)는 `from` 이 좌석 번호(정수·`surface:N`·`N`)일 때만 노드 키를 만들고 라벨 문자열은 키로 쓰지 않으므로, 좌석 밖 발신은 HUD 의 문서 배달 안내 줄에 종전처럼 '외부' 로 표시됩니다.
- **한계**: 라벨이 붙는 것은 좌석 밖의 `cys send`·주입뿐입니다 — GUI 앱이 데몬에 보내는 요청·기동 명령 붙여넣기·`cycle-agent` 의 `/clear` 송신은 이번 판에서 건드리지 않았고, 다른 데몬 좌석에서 보낸 `cys send`(교차 소켓)는 번호 자기신고를 싣고 라벨이 붙지 않습니다. `cli:inject`·`cli:drain` 은 조용한 주입이라 이벤트 없이 원장 `from_label` 에만 남습니다. 구 데몬에 새 `cys` 가 문자열 `from` 을 보내는 조합은 실기로 확인하지 못했습니다.
- **되돌리기**: 라벨 자체를 끄는 노브는 없습니다(`CYS_SENDER_LABEL` 은 `cli:` 뒤 이름만 바꿉니다) — 판 전체 되돌리기.

## 7-2. NPU 전력 표시 — 비공개 라이브러리가 없어져도 데몬은 뜹니다

**무슨 위험이었나**
- Control Center 의 NPU 전력(W) 숫자는 macOS 의 비공개 라이브러리(`libIOReport.dylib`)에서 읽습니다. 데몬은 이 라이브러리를 **링크 속성으로 프로세스에 강하게 묶어** 두었습니다 — 운영체제가 데몬을 시작하는 순간 그 라이브러리를 찾기 때문에, 앞으로의 macOS 에서 라이브러리가 사라지거나 필요한 함수가 하나라도 빠지면 데몬이 시작하자마자 죽습니다(데몬이 못 뜨면 모든 좌석이 함께 닫힙니다). 관측용 숫자 하나가 데몬 기동을 담보로 잡고 있던 셈입니다. 지금의 macOS 에서는 문제가 없었고, 앞으로의 macOS 에 대한 대비입니다.

**무엇이 바뀌었나**
- 그 라이브러리를 데몬이 켜질 때가 아니라 **NPU 전력을 처음 읽을 때** 불러옵니다(`dlopen`). 라이브러리를 열지 못하거나 필요한 함수 8개 가운데 하나라도 없으면 NPU 전력만 꺼지고(값 `null`) 데몬은 그대로 뜹니다. 일부 함수만 쥔 채 진행하지 않습니다 — 없는 함수를 부르면 데몬이 죽거나 거짓 전력값이 나오기 때문입니다.
- `control.hw` 응답의 `npu` 객체에 가산 키 `status`(`ok` 또는 `unavailable`)와 `reason`(쓸 수 없을 때만 — `dylib`·`symbol`·`no_channel`·`subscribe`·`platform`)이 더해졌습니다. 기존 `cores`·`pct`·`watts` 는 그대로입니다(값의 뜻은 매뉴얼 §17).
- 전력 계산(채널 선택·단위 환산·두 시점의 차이)과 CPU·GPU·메모리 표시는 바꾸지 않았습니다.

**알아 두실 것**
- **`status: ok` 는 값을 믿어도 된다는 뜻이 아닙니다** — 라이브러리를 열고 구독을 만드는 데 성공했다는 뜻입니다. macOS 27 에서 NPU 전력이 0 W 로 보이는 현상(0.14.38 노트 §3 이 '정지된 채널을 읽는 관측 결함'으로 적은 것)은 이번 판으로 달라지지 않았습니다 — 같은 맥에서 변경 전 방식을 재현한 독립 탐침과 변경 후 방식을 따로 측정했을 때 NPU 에너지 값이 둘 다 0 이었습니다(그래서 `watts` 도 0).
- 데몬을 켠 뒤 **첫 호출의 `watts` 는 기준 측정이라 `null`** 입니다(종전과 같음). 화면은 `null` 이면 `—` 를 보이고 `status`·`reason` 은 아직 읽지 않습니다(소비자가 없는 가산 키).
- **되돌리는 법**: 이 변경에는 끄는 노브가 없습니다(판 전체 되돌리기). 이 변경이 막는 것은 '라이브러리가 사라진 macOS 에서 데몬이 못 뜨는 일' 하나이고, 평소 동작은 달라지지 않습니다.

## 8. 지침 — 부서장 문단 축소와 문안 정정 (세 지침 모두 크기를 늘리지 않았습니다)

**왜 크기에 신경 썼나** — 지침은 clear 뒤마다 통째로 다시 주입됩니다(v0.14.42 와 견주면 MASTER·CEO_TEMPLATE 은 각 −566 B, CSO 는 −3 B 이고 세 파일 모두 줄 수가 늘지 않았습니다). 0.14.42 발행 전 게이트 수정이 부서장 지침의 `--detach` 문단을 1,053 → 1,972 B 로 키웠고, 자동 압축을 끈 200K 대표(CEO)의 clear 뒤 착지가 +0.2~0.3%p 올라 재검토 드릴 3개가 끝까지 무clear 였습니다(0.14.42 노트 §9-14). 그래서 이번 판은 **역할 지침(CSO·MASTER·CEO_TEMPLATE)의 바이트·줄 수를 늘리지 않는다**는 규칙으로 문서 작업을 했고, 고친 곳마다 같은 문단에서 군말을 줄여 상쇄했습니다.

**무엇이 바뀌었나**
- **부서장 `--detach` 문단 축소**: `MASTER_DIRECTIVE.md` 의 그 한 줄을 지시 조항 10개(호출 꼴·즉시 반환 · 신원·단일 비행 · 동시 2 + 우선 칸 · 결과 수신과 rc 판정 · 결과 전 금지 행동 · detach 는 보류 사유 아님 · 구 데몬 폴백 = 백그라운드 · 전경 대기 금지 · 백그라운드 1콜 중 '사이클 진행 중' 회신 · 백그라운드 없는 CLI 의 600000 전경 예외)를 모두 남긴 채 **1,972 → 1,337 B** 로 줄였습니다. 뺀 것은 내력 표기와 부연뿐입니다. `CEO_TEMPLATE.md` 는 생성기로 같은 바이트를 다시 합성했습니다.
- **`queue.starved` 대응 문장**(MASTER·CSO·CEO_TEMPLATE): ① `CYS_QUEUE_STARVE_ALERT_SECS` 의 기본을 "0=비활성"이라 적던 오기를 정정했습니다 — 코드의 기본은 **600초**이고 `0` 이 끔입니다. ② 종전의 "대응은 원인 해소(연속 출력·사람 입력·queue pause)다" 문장을 경보 요약의 처방 코드(`remedy=<코드>`)를 읽어 사람에게 그대로 전달하라는 문장으로 바꿨습니다 — 코드가 없는 경보(0.14.42 본체가 내는 경보 · 요약이 200바이트에서 잘린 경보)에서는 같은 요약의 `blocked_by` 사유를 전달합니다. ③ LLM 에이전트의 자동 조치 금지 목록을 데몬 상수와 같은 뜻으로 넓혔습니다(강제 배달·드레인·키 주입·동결 해제·항목 삭제) — "강제 배달은 사람 운영자 전용" 이라는 종전 단정은 그대로 두고 `queue.depth_high` 경보와 겹쳐도 같다고 덧붙였습니다.

- **계약 검체**: 부서장 문단 축소에 맞춰 조항 핀을 3항에서 7항으로 늘려(핀을 지우거나 약화하지 않고 가산) 종전에는 핀이 없던 조항 4개를 새로 잡았고, 이번 문안에는 지침 문구를 데몬 코드와 대조하는 핀(기본값 600초 · `remedy=` 토큰 · 요약에 `blocked_by` 가 늘 실리는 꼴 · 금지 목록 · 요약 토큰 · 나이 상한 1800초 · `alert_eligible` 키와 판정 규칙의 모양 · 두 경보 이름)과, 종전부터 있던 "사람 운영자 전용"·"(Return 한정 큐잉)" 및 새 "처방 코드가 없으면 `blocked_by`" 구절을 하나씩 지우면 붉어지는 낱말 핀을 더했습니다.

**알아 두실 것**
- 이 두 지침(`MASTER_DIRECTIVE.md`·`CSO_DIRECTIVE.md`)은 사용자 소유라 **`cys pack-merge` 로 한 번 병합**하셔야 발효됩니다(맨 위 안내). `CEO_TEMPLATE.md` 는 시스템 소유라 자동 갱신됩니다.

- 압축한 문안을 실제 에이전트가 사이클 집행에서 어떻게 읽는지는 아직 보지 못했습니다.
- 문단 안의 `단일 전체 시한 570초` 는 데몬 코드의 값과 짝을 이룹니다 — 이 구절을 더 줄이면 코드 쪽 검체가 붉어집니다.

## 10. 새로 생긴 것 · 바뀐 계약

**와이어 호환: 가산이 기본입니다** — 기존 키·이벤트·표의 이름과 뜻은 그대로이고(예외 둘: 한도 경보 요약의 창 라벨 — 아래 계약 변경 ⑦, 좌석 밖 발신의 `from` 이 null 대신 문자열 라벨 — 아래 ⑩), 키를 모르는 쪽(구버전)은 새 키를 무시합니다. 데몬이 새 키를 보내지 않는 구버전이면 화면에서 `사용 중`·`이전 로그인`·별명·현재 로그인 폴더 이름만 빠지고 나머지 새 규칙은 그대로 적용됩니다. **데몬 로그 수정(§7)은 프레임 직렬화 바이트가 0.14.42 와 같습니다**(판정·로그·카운터만 바뀜 · `org.status` 의 새 키 2개는 별개).

- **새 CLI 명령·RPC 메서드·팩 훅은 없습니다.** 새로 생긴 것은 아래 가산 키·이벤트·파일뿐이고, 팩의 `cys-dept` 는 새 `cys` 동사를 부르지 않습니다.
- **`cys usage-accounts` 텍스트 열**: 기존 세 열의 모양은 그대로이되(리셋이 지난 창에는 3열 안에 `(리셋됨)` 이 붙으므로 3열 문자열을 파싱하는 도구는 유의) 같은 줄 뒤에 ` | ● 사용 중`/`○` · ` | 현재: …` · ` | N초/분/시간 전[ · 오래됨]` · ` | 별명: …` 이 이 순서로 붙습니다. 표준 출력에는 계정 행만, 안내 한 줄은 표준 오류로 나옵니다(매뉴얼 §15).
- **`usage.accounts` 행**(`control.dashboard.accounts` 포함) 가산 키: `in_use`·`rate_observed_at`·`rate[].alert_eligible`·`current_profiles`·`alias` — 기존 키·표시 승자 불변. 앱이 본부·부서 데몬 응답을 합칠 때 `current_profiles` 는 합집합, `in_use` 는 하나라도 `true` 면 `true`(아니면 하나라도 모름이면 모름, 전부 `false` 면 `false`), `alias` 는 이긴 행에 없을 때 진 행의 값을 이어받습니다.
- **좌석 `usage`**(`surface.list`·`org.status`·`control.dashboard` 의 `fleet[]`) 가산 키: `rate_observed_at`·`rate_age_secs`·`rate_in_use`·`rate[].alert_eligible` — 보고 때의 계정 ID 는 내보내지 않습니다.
- **한도 경보**(`alert.account_rate`·`alert.rate_limit`)의 `detail` 가산 키 `observed_at`·`age_secs`·`in_use`·`reset_in_secs`·`held_secs`, CSO 큐 요약 토큰 `age=`·`in_use=`·`reset=`·`held=`. 새 이벤트 `usage.alert_resolved {key, reason}`(category `usage` · 비라우팅).

## 11. 이관(업그레이드) 주의

1. **`cys pack-merge` 가 필요합니다**(맨 위 참고) — `MASTER_DIRECTIVE.md`·`CSO_DIRECTIVE.md` 는 `.new` 로만 옵니다. 병합 뒤 `cys pack-merge`(인자 없이)의 대기 목록에 두 파일이 더 없으면 끝난 것입니다(CEO 로 승격된 설치는 MASTER 를 병합하지 않아도 됩니다 — 맨 위).
2. **데몬 env 노브는 데몬을 다시 켜야 반영됩니다** — `CYS_PENDING_INPUT_MODEL`(프로세스 시작 때 한 번만 읽음)·`CYS_QUEUE_STARVED_HINT_LEGACY`·`CYS_ACCOUNT_ALERT_STALE_SECS`·`CYS_ALERT_SUMMARY_LEGACY`·`CYS_SCHEDULE_PUSH_COUNTS_SUBMIT`.
   앱이 읽는 노브(`CYS_DEPT_CREATE_STREAM`·`CYS_UPDATE_VERIFY`·`CYS_UPDATE_CHECKED_LAUNCH`)는 앱을 다시 시작해야 하고, `CYS_DEPT_READY_SECS` 는 `cys-dept` 가, `CYS_SENDER_LABEL` 은 호출하는 `cys` 가 실행될 때마다 읽습니다.
3. **새 기능은 새 데몬이 뜬 뒤부터** 적용됩니다. 업데이트 직후 아직 다시 뜨지 않은 구버전 데몬은 새 키를 보내지 않고, 화면은 그때 `사용 중`·`이전 로그인`·별명처럼 새 키가 있어야 하는 표시만 빠지고 나머지 새 규칙은 그대로 적용됩니다(백지는 아닙니다).
   구 데몬의 경보에는 처방 코드(`remedy_code`)가 없어 큐 막힘 토스트는 `막힘 사유: <blocked_by>` 만 보입니다. 새 CLI + 구 데몬이면 `cys queue list` 의 새 안내 줄은 처방 부분만 생략되고 조회는 죽지 않습니다. 구 CLI + 새 데몬이면 표(stdout)와 `--queued` 폴백은 종전 그대로입니다.
4. **「업데이트 미설치」 알림은 0.14.43 앱에서 시작한 업데이트부터** 효과가 있습니다 — 기록을 업데이트를 시작하는 앱이 쓰므로, 0.14.42 이하 앱에서 누른 업데이트(예: 0.14.37 → 0.14.43)는 기록이 없어 알림이 뜨지 않습니다. 윈도우의 **설치 파일 실행 즉시 알림**(§6-1)도 같습니다 — 옛 앱의 업데이터는 실행 결과를 보지 않아, 스마트 앱 컨트롤이 켜진 PC 에서는 앱이 말없이 닫히고 구버전이 남을 수 있습니다(실측).
5. **팩과 앱을 따로 갱신한 조합**: 구 팩(표지 없음) + 새 앱이면 「팀 직접 만들기」 대기 화면에 단계 줄 없이 경과만 보입니다. 구 앱 + 새 팩이면 만들기가 실패할 때 표지 줄 몇 줄이 실패 사유 앞에 끼어 사유가 앞 300자 안에서 잘릴 수 있습니다.
6. **별명**을 쓰시려면 `~/.cys/accounts.json` 에 `aliases` 를 직접 적습니다(§3). 쓰지 않으면 달라지는 것이 없습니다.
7. **Windows**: 입력줄 계수 모델의 기본은 v2 라서 계수 동작이 바뀌지 않습니다(§2 · §15).
8. **좌석 밖에서 보낸 `cys send`·주입의 발신을 읽는 스크립트**가 있다면 이벤트·`queue.list` 의 `from` 이 null 대신 `cli:send` 같은 문자열일 수 있고(배달 원장의 `from` 은 그대로 — 라벨은 `from_label` 키), 큐 다이제스트 머리는 `발신 unknown` 대신 라벨입니다(§7-1).
9. **0.14.42 본체에 이 팩만 받은 경우** 큐 정체 경보에 처방 코드(`remedy=`)와 한도 경보의 새 토큰(`age=`·`in_use=`·`reset=`·`held=`)이 실리지 않습니다 — 그때는 경보의 `blocked_by` 사유를 사람에게 전달합니다. 새 지침의 `remedy=` 문장도 코드가 없을 때를 그렇게 안내합니다(§8).

### 12-1. 설계 중 검토하고 채택하지 않은 것(결정 기록)

사용자에게 보이는 동작에 영향이 있는 결정만 추렸습니다. 그 밖의 구현 선택(로그 키 단위 · 신원 캐시 정리 · 좌석별 계수기 분리 등)은 여기에 싣지 않았고, 원본 작업 기록은 공개 저장소에 없습니다.

| 검토한 안 | 택한 쪽 | 이유 |
|---|---|---|
| 부동소수 직렬화에 `float_roundtrip` 기능을 켜기(설계안 권고) | 부동소수 허용 비교 + 조용한 폴백 + 카운터 | 켜면 데몬이 부동소수 프레임에도 길이 표지를 붙이게 되어 읽기가 best-effort 인 구 클라이언트(0.14.42 이하 `cys`)가 값에 따라 간헐 실패합니다. 와이어 바이트를 0.14.42 와 같게 둡니다 |

### 13-1. 큐 막힘 · 입력줄 계수

**알려진 한계**

### 13-2. 사이드바 사용량 · 계정 · 한도 경보

**알려진 한계**

- 이미 떠 있는 Claude Code 가 로그인 전환 뒤 어느 계정으로 소비하는지(자격 재적재)를 실기로 확인하지 못했습니다. '사용 중'을 설정 폴더의 지금 로그인으로 좁게 정의한 것은 그 불확실성 아래의 선택이고(경보를 덜 붙드는 쪽이며 판정 불가만 경보를 지키는 쪽으로 읽습니다), 틀리면 옛 계정의 진짜 경보가 30분 뒤 빠질 수 있습니다(노브 `0` 으로 되돌림). 넓은 정의(좌석의 마지막 보고 계정)를 쓰지 않은 이유는, 기본 구성에서는 모든 좌석이 한 폴더를 나눠 써 재로그인 뒤에도 유휴 좌석이 옛 계정을 계속 '사용 중'으로 만들어 수정 효과가 사라지기 때문입니다.
- 살아 있는 Claude 좌석이 없는 데몬은 모든 Claude 계정을 '사용 중 아님'으로 읽습니다(막 켠 뒤 좌석 복원 전의 30분 넘은 복원값은 보류됐다가 복원되면 다음 점검에 울림).
- 부서 데몬의 좌석은 본부 데몬의 '사용 중' 판정에 들어가지 않습니다(본부 데몬 경보에서 빠질 수 있고 부서 데몬은 자기 입력으로 따로 경보).
- 로그인 전환 표시·판정은 최대 60초 늦습니다. 신원 파일을 다시 쓰는 도중에 읽으면 그 폴더가 60초 동안 누구의 것도 아니어서 `이전 로그인` 이 잠깐 보일 수 있습니다.
- 처음 보는 계정으로 로그인하면 그 계정의 줄은 첫 응답 보고가 들어올 때 생깁니다(그동안 옛 계정이 `Claude (이전 로그인)`). 이름 규칙 밖 설정 폴더는 '지금 로그인된 폴더' 에 나타나지 않습니다.
- 신원 파일을 읽는 디스크가 응답하지 않으면(멈춘 네트워크 드라이브 등) 데몬의 감시 틱이 그 읽기에서 멈춥니다 — 한도 경보 점검이 큐 배달·에이전트 사망 감지·데드맨 점검과 같은 틱 안에서 차례로 돌기 때문에 그 점검들도 함께 서고, 사용량 조회·`cys status`·Control Center 호출도 같은 파일을 읽어 그 호출이 멈출 수 있습니다(전역 락은 쥐지 않아 다른 호출은 막지 않음). 이번에 새로 생긴 노출입니다.

### 13-3. 「팀 직접 만들기」

**측정하지 못한 것**

**알려진 한계**

- 예약 유예 식(`값 + 값/5 + 17`초)은 반복 1회를 약 0.118초(이 개발 맥에서 핑 대신 가벼운 명령으로 잰 값)로 본 공칭 계산이라, 핑이 더 느린 컴퓨터에서는 실제 대기가 수 초~수십 초 더 걸려 유예를 넘을 수 있습니다 — 큰 값을 쓸 때는 `CYS_DEPT_RESERVE_GRACE` 도 함께 올리세요. 노브를 올렸는데 `CYS_DEPT_RESERVE_GRACE` 가 정수가 아니면 유예가 따라 오르지 못하고 경고 한 줄이 표준 오류로 나갑니다.
- 새 이름의 사전 검사(약 12초 — 생성 시간의 절반 가까이)는 줄이지 않았습니다(경합 분석이 필요해 0.14.44 후보). 띄운 데몬이 소켓을 열기 전에 죽어도 대기 시간이 다 지나야 실패로 알립니다.
- 「지금 N자리」는 그 탭에 붙은 자리 수라 데몬이 아는 수와 입양 지연(최대 3초)만큼 어긋날 수 있고, 편성 도구의 결과 알림은 이 안내를 바꾸지 않고 종전처럼 일반 알림 토스트(`ℹ 알림`)로 따로 오므로 두 알림이 서로 다른 시점에 보일 수 있습니다. 화면은 자리가 붙었는지만 알기 때문에 「팀 자리가 모두 붙었습니다」 뒤에도 에이전트가 실제로 준비되지 않았을 수 있습니다.
- 이 안내는 이 세션에서 화면으로 새로 만든 팀에만 뜹니다 — 대표가 대화 승인으로 만든 팀·앱을 다시 켜며 복원된 팀에는 뜨지 않습니다. 같은 카탈로그 팀이 이미 있어 기존 팀을 돌려받은 경우에도 뜨지 않습니다(그 호출이 새 데몬을 띄웠을 때만 새 팀으로 칩니다 — `spawn` 단계 표지를 받았으면 새 팀이고, 단계 표지를 한 번도 받지 못해 구분할 수 없는 경우(단계 표지를 내지 않는 구 팩 · `CYS_DEPT_CREATE_STREAM=0` · 표지가 유실된 경우)에는 새 팀으로 보고 종전처럼 뜹니다).

### 13-4. 업데이트 알림 · 윈도우 11 스마트 앱 컨트롤(§6 · §6-1)

**측정하지 못한 것 · 한계**

- 스마트 앱 컨트롤 강제 모드에서의 실제 차단과 `ShellExecuteW` 가 돌려주는 값(반환 5 · 오류 4551)은 Windows 11 러너에서 실측했고, 설치 파일 실행 모듈은 진짜 스마트 앱 컨트롤에서 단독으로 확인했으며, 0.14.43 앱 전체는 진짜 [Update] 단추로 돌려 봤습니다(꺼짐: 설치 후 앱 재기동 · 켜짐: 앱이 닫히지 않은 채 4551 알림 — §6-1). 실측하지 못한 것: **문구를 고친 뒤의 빌드**(앱 전체 시험의 화면 문구는 고치기 전 판의 것이었습니다 — 문구를 고친 뒤의 빌드로는 아직 재지 않았습니다) · 설치 파일이 뜬 직후 시도 기록의 기준 시각을 다시 쓰는 동작의 실기 · 다시 열린 뒤의 「업데이트가 설치되지 않았습니다」 알림 화면(Windows 실기) · 앱이 `reg query` 출력을 읽는 부분 가운데 비관리자 계정에서 읽히는지와 한국어 Windows 출력(문서화된 출력 견본으로만 검증 — 이 러너의 기본 계정에서는 읽혀 확인 창 문단이 붙었습니다) · '평가' 상태(값 2) · Home 판과 x64 네이티브 실기.
- 설치기가 뜨기 전 다운로드 도중에 앱을 껐더라도 다음에 열릴 때 90초가 지났다면 같은 알림이 한 번 뜹니다(첫 문장은 사실이고 Windows 문단은 "막았을 수 있습니다"라고만 말함). macOS 에서 설치 뒤 무결성 검증이 실패해 오류가 난 경우에도 기록이 남아 알림이 한 번 더 뜰 수 있습니다. 시계가 한참 앞섰다 돌아온 드문 경우는 판정이 보류된 채 남습니다.
- 10분 안에 못 보고 OS 배너마저 놓치면 알람 이력(앱이 켜져 있는 동안의 목록)에만 남습니다.
- 이 알림은 앱이 다시 열릴 때 판정하므로, 앱을 다시 여는 것 자체를 Windows 가 막으면 뜰 수 없습니다(실측 — §6-1).
- 즉시 알림(§6-1)은 0.14.43 앱에서 시작한 업데이트부터 있습니다 — 옛 앱의 업데이터는 말없이 닫힐 수 있습니다.

### 13-5. 데몬 로그 거짓 'critical' 수정

**측정하지 못한 것 · 한계**

- 로그 줄 수 감소 효과는 라이브 데몬 로그로 직접 재지 못했습니다(격리 검체와 60만 건 비교로만 확인). 허용 폭(약 4~8ulp)은 현재 JSON 라이브러리 읽기의 실측 최대 오차(2ulp) 기준이라, 라이브러리가 바뀌어 오차가 커지면 `Drift` 로 보일 수 있습니다 — 그래도 이제 60초 1줄·카운터라 폭주하지 않습니다.
- 진짜 `Drift` 원천은 남습니다(비객체 응답 · 매우 깊은 중첩의 재파싱 한도 초과) — 다만 이제 카운터로 보입니다.

### 13-6. 지침

- 부서장 문단 축소의 **효과는 측정하지 못했습니다**(실 드릴 재측정 불가 — '회귀 해소'가 아니라 '완화')이고, 압축한 문안을 실제 에이전트가 사이클 집행에서 어떻게 읽는지도 아직 보지 못했습니다(§8).

### 13-7. 스케줄 push 계수 · 발신 표시 · 부팅 때 파일 읽기

**알려진 한계**

- 스케줄 push 계수 계상은 스케줄 직접 push 한 곳뿐입니다(큐 배달은 종전부터 계상) — CEO 자동결재 요청·채널 inbox 지시·부트 감독자 통보·좌석 승계 고지의 직접 주입은 아직 계상하지 않습니다(다음 판 후보 · §2-1).
- 발신 표시 라벨은 좌석 밖의 `cys send`·주입에만 붙습니다 — GUI 앱이 데몬에 보내는 요청·기동 명령 붙여넣기·`cycle-agent` 의 `/clear` 송신은 종전대로이고, 다른 데몬 좌석에서 보낸 `cys send`(교차 소켓)는 번호 자기신고를 싣고 라벨이 붙지 않아 받는 쪽 큐 머리가 계속 `발신 unknown` 일 수 있습니다. `cli:inject`·`cli:drain` 은 조용한 주입이라 이벤트 없이 원장 `from_label` 에만 남습니다.
- 선언 계정 파일 보호 가운데 이름 있는 파이프를 열다가 멈추지 않게 하는 부분은 macOS·Linux 에서만 작동합니다 — Windows 는 일반 파일 여부 판정만 하고, 비정규 경로(파이프·장치)의 실기는 하지 못했습니다(§3).

**측정하지 못한 것**

- 구 데몬에 새 `cys` 가 문자열 `from` 을 보내는 조합의 실기(§7-1) · 스케줄 push 계수 계상을 실제 Claude Code 좌석에서 본 효과(검체는 합성 좌석에서 돌렸습니다).

### 13-8. NPU 전력 표시(§7-2)

**알려진 한계**

- **`status: ok` 는 값의 신뢰가 아닙니다 — macOS 27 의 0 W 현상은 그대로입니다.** 읽기 초기화가 성공했다는 뜻일 뿐이고, 정지된 채널을 읽어 0 W 로 보이는 것을 가려내는 판정은 이번 판에 넣지 않았습니다(Control Center 는 여전히 0.0W 를 보일 수 있습니다).
- 윈도우·리눅스의 `control.hw` 도 같은 가산 키를 내며 `status` 는 `unavailable`, `reason` 은 `platform` 입니다(NPU 전력은 macOS 전용).

**측정하지 못한 것**

- **서명·공증된 설치본의 데몬에서 시스템 라이브러리를 실제로 열 수 있는지**는 확인하지 못했습니다 — 시험은 서명하지 않은 디버그 빌드에서만 했습니다(이 맥에서는 라이브러리 열기·구독이 실제로 성공했습니다). 시스템 라이브러리라 막히지 않을 것으로 보지만 코드 읽기 근거일 뿐이어서 발행 뒤 실기 확인 항목에 올렸습니다. 실패해도 데몬은 뜨고 NPU 전력만 꺼집니다.
- 사유 `no_channel`·`subscribe` 는 이 기계(채널이 있는 맥)에서 만들 수 없어 실행 검체가 없고, 종전 실패 경로와 1:1 인 것을 코드로만 확인했습니다. `dylib`·`symbol`·`platform` 은 검체로 실행해 확인했습니다.
- CI 에서 처음 돌게 된 NPU 전력 검체(브랜치 CI 의 macOS 레인 · 윈도우 건강성)와 데몬 실행 파일의 `otool -L` 링크 확인 단계는 GitHub 러너에서 아직 실행해 보지 못했습니다(§14). 링크 확인은 '강하게 묶이지 않았는가' 만 보며, 서명·공증된 설치본의 데몬이 시스템 라이브러리를 실제로 여는지는 위와 같이 확인하지 못했습니다.

## 15. Windows

- **입력줄 계수(§2)**: Windows 기본은 종전(v2)이라 이번 판에서 계수 동작이 바뀌지 않습니다. 같은 증상(빈 입력줄 Esc·Backspace 뒤 큐 멈춤)은 그대로이고, 막히면 그 창에서 사람이 Ctrl-U 한 번입니다. 전경 판정도 macOS·Linux 에서만 합니다.
- **큐 막힘 화면 알림·처방·사유 파일(§1)과 사용량·경보(§3·§4)**는 운영체제 공통 코드입니다 — 교차 타입체크(Windows 대상) 오류 0 · 경고 29(기준선과 같은 목록)로 확인했고, **Windows 실기 확인은 아직**입니다(경로 구분자 혼재는 화면이 접습니다 — 타입체크만).
- **「팀 직접 만들기」(§5)**: Windows 에서 앱이 띄운 `bash.exe` 자식의 파이프 거동(단계 표지 스트리밍)과 Git Bash(MSYS) 실행은 시험하지 못했습니다.
- **업데이트(§6 · §6-1)**: Windows 11 러너에서 스마트 앱 컨트롤을 켜고 실측했습니다 — 코드 서명도 평판도 없는 설치 파일·실행 파일은 설치·실행·업데이트 모두 막히고, 0.14.43 은 막혔을 때 앱을 닫지 않고 즉시 알립니다(0.14.43 앱에서 시작한 업데이트부터 · 설치 파일 실행 모듈은 진짜 스마트 앱 컨트롤에서 단독 확인했고, 앱 전체는 진짜 [Update] 단추로 돌려 봤습니다 — 꺼짐은 설치 후 앱 재기동, 켬은 앱이 닫히지 않은 채 4551 알림. 단 그 시험의 화면 문구는 고치기 전 판의 것이고 문구를 고친 뒤의 빌드로는 아직 재지 않았습니다). 스마트 앱 컨트롤 상태를 읽는 `reg query` 부분은 이 러너의 기본 계정에서 읽힌 것까지 확인했고, 비관리자 계정과 한국어 출력은 문서화된 출력 견본으로만 검증했습니다. 코드 서명도 평판도 없어서 막히는 것 자체는 이번 판으로 풀리지 않습니다(코드 서명은 §12).
- **데몬 로그 수정(§7)**은 운영체제 공통입니다 — Windows 대상 타입체크 오류 0.

### Windows 에서 Claude Code 가 전체화면이면 큐 배달이 보류됩니다 — 이번 판은 안내만(기본 동작 불변)

**증상 · 원인**
- 제보: Claude Code 가 전체화면이면 큐(`--queued`) 배달이 막힙니다(`blocked_by` = `alt_screen(전체화면 · 프롬프트 레이아웃 미확인)`).
- 원인: macOS 는 claude 를 띄울 때 `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` 을 늘 실어 전체화면을 끄지만 Windows 는 옵트인(기본 off)이라 주입이 없고 화면 모드를 Claude Code 가 정합니다. 큐 배달은 전체화면에서 양성 유휴 프롬프트 관측이 있을 때만 통과하는데 Windows(ConPTY)에서 그 증거가 성립하는지는 실측한 적이 없습니다.

**이번 판에서 한 것 · 지금 쓸 수 있는 방법**
- 처방과 안내만 보강했습니다 — 큐 막힘 처방(`remedy`)의 `alt_screen` 코드가 `/tui default` 와 Windows 옵트인 파일 안내를 싣고, USER-MANUAL 의 문제 해결 표에 증상·원인·지금 쓸 수 있는 방법을 적었습니다. **게이트 판정·기본값은 그대로입니다.**
- 지금 쓸 수 있는 방법: ① Claude Code 안에서 `/tui default`(Claude Code 문서: 클래식 화면으로 전환하고 `tui` 설정을 저장) ② 빈 파일 `~/.cys/win-no-alt-screen` 을 만들고 `cys launch-agent` 로 새 pane(이미 열린 pane·GUI 가 연 pane 에는 실리지 않음) ③ 급한 메시지는 `--queued` 없이 직접 `cys send`. 이미 쌓인 항목은 디스크(WAL)에 남지만(큐 TTL 기본 6시간) 강제 배달(`cys queue deliver`)로도 풀리지 않습니다(같은 판정).

**하지 않은 것과 이유 · 한계**
- **Windows 기본값(옵트인 off) 승격은 하지 않았습니다** — 기본을 켜면 최악의 경우 `cys boot` 로 띄운 pane 이 한꺼번에 죽는 경로라, 실기 확인(Windows 에서 `cys boot` 4종 노드 정상 기동 · ConPTY 실측)이 먼저입니다. 윈도우는 종전 유지.
- `queue.depth_high` 경보의 `hint` 는 이 사유에서도 `CYS_QUEUE_QUIET_SECS` 조정을 권하지만 그 노브는 전체화면의 출력 정적 3초를 바꾸지 못해 효과가 없습니다(문구 결함 — 이번 판에 고치지 않음).
- `/tui default` 가 cys 좌석(계정별 설정 폴더)에서 어디에 저장되는지는 실기에서 확인하지 못했습니다.

### Windows Defender / SmartScreen 안내 (유지)

Windows 용 설치 파일은 Authenticode 서명이 없어 실행 시 SmartScreen "알 수 없는 게시자" 경고가 뜰 수 있습니다
(**추가 정보 → 실행**으로 진행). 홈페이지의 `SHA256SUMS.txt` 와 대조해 무결성을 확인할 수 있습니다.

스마트 앱 컨트롤이 켜진 Windows 11 에서는 이 경고와 별개로 코드 서명도 평판도 없는 설치 파일의 실행이 차단됩니다(오류 4551 — 실측은 §6-1).

## 16. 업그레이드하실 때

- 본체(GUI·CLI·데몬) 변경이 있는 **바이너리 릴리스**입니다. 홈페이지(www.cysinsight.com)에서 설치본을 받아 덮어 설치해 주세요.
- 팩 변경(`cys-dept`·지침)도 `pack.tar.gz` 로 실립니다. 팩 하한은 올리지 않았으므로(0.14.42 유지) 0.14.42 본체를 쓰시는 분은 인앱 무중단 팩 업데이트로도 받으실 수 있습니다(하한 미만인 ≤0.14.41 본체만 받지 못합니다).
- **`cys pack-merge` 를 한 번 돌려 주세요**(맨 위 참고 — `MASTER_DIRECTIVE.md`·`CSO_DIRECTIVE.md`).
- 데몬 env 노브를 쓰신다면 데몬을 다시 켜 주세요(§9 · §11).
- **Windows 11 에서 스마트 앱 컨트롤이 켜져 있다면 업데이트 전에 §6-1 을 먼저 읽어 주세요** — 0.14.42 이하 앱에서 누른 업데이트는 앱이 말없이 닫히고 구버전이 남을 수 있으며 앱을 다시 열 수도 없을 수 있습니다(실측).
- 세션·부서·직원은 유지됩니다.
